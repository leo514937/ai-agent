# P1.5 Day 1 - Compatibility First

优先级：最高。

目标：先让旧拓扑兼容新字段，尽量不动路由语义，不破坏现有行为。Day 1 的产出不是新拓扑，而是“新字段已经能稳稳挂在旧拓扑上”。

## 这一天的定位

Day 1 是整个 P1.5 的地基，核心原则是：

- 先保留旧行为
- 再补新字段
- 先写兼容镜像
- 后续再让新字段真正驱动路由

这一天完成后，旧流程应该看不出结构性变化，但 state、trace、extra 里已经能看到新架构需要的影子字段。

## 实现要求

- 兼容层要独立于未来的执行层，不要把新旧逻辑揉成一坨
- 新契约先补定义，再补写入，再补消费，保持演进顺序清楚
- 双写逻辑要放在清晰的适配层，不要直接塞进核心业务判断里
- `compose_answer` 先维持旧职责，再逐步拆薄，避免继续膨胀成 God Node

## 范围

- 只做兼容层和数据结构扩展
- 不改顶层图结构
- 不替换 `route_gate`
- 不收敛 `plan_execute_subgraph`
- 不改变现有 SSE 事件名和 payload 风格

## 明确不做什么

- 不删除旧字段
- 不删除旧路径
- 不把标准路径拆出来
- 不让 Planner 介入更多场景
- 不把 review 作为强制中间节点

## 核心目标

### 1. 让新契约“先存在”

这一阶段要先把以下结构补齐：

- `SemanticParseResult`
- `SourceContract`
- `ReviewReport`
- `LoopCounter`
- 扩展后的 `AnswerContract`

这些结构先进入领域模型和 `turn.extra` 镜像，但不要求立刻改变路由结果。

### 2. 让旧拓扑“继续稳定运行”

现有 `load_context -> understand_turn -> route_gate -> ... -> compose_answer -> persist_session -> emit_final` 必须继续保持可用。

### 3. 让 `compose_answer` 先学会双写

`compose_answer` 先继续做旧工作，同时把新字段同步写入：

- 新契约数据
- 新 review 结果
- 新 loop 计数
- 新 source contract 镜像

## 重点任务

### 1. 新增或强化 `SemanticParseResult`

增强版计划要求将自然语言理解结果标准化，避免每个节点重复理解。

建议它至少能表达：

- `primary_intent`
- `top_level_intent`
- `sub_intents`
- `required_facets`
- `optional_facets`
- `forbidden_facets`
- `constraints`
- `target_reference`
- `confidence`
- `missing_slots`

用途：

- 未来 Day 2 的 query merge 和 top-level intent router 的基础
- 现在 Day 1 先作为兼容镜像

### 2. 新增或强化 `SourceContract`

目标是先有模型，不要求立刻重写路由。

建议它至少能表达：

- `required_facets`
- `optional_facets`
- `forbidden_facets`
- `facet_source_map`
- `target_shop_id`
- `candidate_shop_ids`
- `comparison_shop_ids`
- `scope_kind`

用途：

- 未来 Day 3 / Day 4 的能力调度依据
- 现在 Day 1 先作为兼容镜像

### 3. 强化 `AnswerContract`

当前 `AnswerContract` 还不够表达“回答边界”，需要补充：

- `optional_facets`
- `forbidden_facets`
- `answer_style`
- `scope_kind`
- `facet_source_expectations`

兼容策略：

- `required_facets` 保留
- `forbidden_without_evidence` 不删，先作为兼容别名
- 旧 verifier 逻辑可以继续先读老字段

### 4. 新增 `ReviewReport`

Day 1 先把 review 的统一输出格式定义出来。

建议字段：

- `decision`
- `reason`
- `failed_facets`
- `repair_hint`
- `retry_target`
- `retry_count`
- `max_retry_count`
- `target_step_id`
- `extra`

允许的决策先完整定义，但暂不强制全部路径启用：

- `pass`
- `repair_answer`
- `retry_rag`
- `retry_tool`
- `retry_step`
- `replan`
- `degrade`

### 5. 新增或强化 `LoopCounter`

这一阶段只需要把计数结构放好。

建议字段：

- `retry_rag`
- `retry_tool`
- `retry_step`
- `repair_answer`
- `replan`

要求：

- 默认值必须安全
- 没有该字段时旧流程不报错
- 有该字段时不会影响旧路由结论

### 6. 扩展 `TargetShopPolicy`

这一阶段目标不是重写实体消解，而是让结果语义更完整。

需要保证：

- 单店结果稳定
- 仍然能表达 `shop_id / shop_name`
- 逐步能支持 recommendation / comparison / planning 的候选集合表达

Day 1 先关注：

- `candidate_shop_ids`
- `comparison_shop_ids`
- `scope_kind`
- `target_reference_source`

但不改变单店结果的现有含义。

### 7. `compose_answer` 双写新旧字段

这是 Day 1 最关键的落点。

`compose_answer` 仍然是老出口，但它要开始写入：

- `semantic_parse_result`
- `answer_contract`
- `answer_verifier_result`
- `source_contract`
- `review_report`
- `loop_counter`
- 现有 `routing_decision / route_gate / phase3_trace / phase4_trace`

原则：

- 老字段照写
- 新字段附加写
- 不因为新字段改变旧答案风格

## Day 1 输出要求

Day 1 结束后，仓库应该满足：

- 新数据结构已经存在
- 旧拓扑仍然工作
- 旧路由矩阵测试仍然通过
- 新字段已经出现在 state / trace / extra 中
- 新字段的默认值不会扰动旧结果

## Day 1 验收

1. 旧 trace 字段继续可读
2. 旧 `RoutingDecision` 字段继续可读
3. SSE payload 无破坏性变化
4. 现有路由矩阵测试绿色
5. 单店 `TargetShopPolicy` 结果保持不变
6. `turn.extra` 能看到新契约镜像字段
7. 新字段不会改变现有回答内容

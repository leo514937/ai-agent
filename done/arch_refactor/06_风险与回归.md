# 6. 风险与回归

> 本次风险评估聚焦于：如何避免文档把 P0 写成半个 P2，或让旧 `task_type`、fallback 规则和自由字符串状态继续绑架新架构。

---

## 6.1 核心风险总览

| 风险 | 严重度 | 结果 | 缓解措施 |
|---|---|---|---|
| P0 输出未实现 `next_action` | 高 | graph 跳转到不存在或未完成节点，形成 dangling action | P0 只允许 `finish / clarify / fallback`，且 `finish` 只表示进入下一规划/执行阶段 |
| 旧 `task_type` 继续作为最高事实源 | 高 | `CandidateSet / CandidateReview` 被兼容逻辑绕过 | 在 P0 引入 `LocalLifeGoalDraft`，把 `task_type` 降为兼容字段 |
| Candidate 状态自由字符串 | 中 | `resolved / ok / enough` 混用，Review 分支不稳定 | `CandidateStatus / CandidateSource / GoalType` 枚举化 |
| `slot_extractor` fallback 静默覆盖 LLM 语义 | 高 | 规则重新主导语义，偏离设计目标 | fallback 只能补齐字段，必须记录 `semantic_source / candidate_source_origin / fallback_reason` |
| P0 只解决候选，不解决证据 | 中 | 即使候选链路正确，系统仍可能给出事实错误 | 明确 P0 只做候选 sufficiency，P1 负责证据正确性 |
| P1 未及时落地 EvidenceReview | 高 | 继续出现 `unknown_as_false / failed_as_empty` | P0 trace 验收通过后优先进入 P1 |
| 非 `local_life` 被 CandidateSet 污染 | 高 | 普通问答链路变慢或错误 | P0 不修改 `top_intent_router`，非 `local_life` 保持直达 `emit_response` |
| 一次性重构 P0/P1/P2 | 高 | 旧测试大面积回归，问题定位失焦 | 强制分阶段实施与验收，不允许跨阶段一把梭 |
| `_h_target_resolve` 规则堆叠搬进 `CandidateResolver` | 中 | 名义分层，实则形成新规则大函数 | `CandidateResolver` 继续拆分 explicit/context/discovery/mixed，并受测试约束 |
| ToolResult 结构不统一 | 中 | `unknown / failed / timeout` 判断继续依赖隐式字段 | 前置统一 `ToolStatus + error_type + retriable + source` |

---

## 6.2 P0 未实现动作悬空风险

### 问题

如果 P0 继续输出：

- `expand_search`
- `replan_evidence`

但 graph 中并没有对应落地节点，就会形成 dangling action。

### 缓解

1. P0 文档只允许 `finish / clarify / fallback`
2. `expand_search` 最多作为后续阶段预留枚举
3. 不允许 P0 graph 跳转到未实现节点
4. `finish` 只表示候选阶段通过，不表示最终回答完成

---

## 6.3 旧 task_type 继续绑架架构

### 问题

如果 P0 完全依赖旧 `task_type`，那么 `SemanticFrame → CandidateSpec` 之间仍没有真正的新抽象层，旧硬分流仍会绕过 CandidateSet 新链路。

### 缓解

1. 在 P0 增加 `LocalLifeGoalDraft`
2. `task_type` 只能作为兼容字段
3. `candidate_source / candidate_limit / evidence_needs` 优先来自 LLM `SemanticFrame`

---

## 6.4 fallback 重新主导语义

### 问题

如果 `slot_extractor` fallback 允许静默改写：

- `candidate_source`
- `candidate_limit`
- `required_facets`
- 核心 comparison / recommendation 意图

那么最终仍会退化成规则主导语义。

### 缓解

1. fallback 只能补齐字段
2. 不能静默覆盖 LLM 核心语义
3. 必须记录：
   - `semantic_source`
   - `candidate_source_origin`
   - `fallback_reason`
   - `execution_trace`

---

## 6.5 Candidate 状态自由字符串风险

### 问题

`resolved / RESOLVED / ok / enough` 混用会直接影响：

1. CandidateReview 分支稳定性
2. trace 可读性
3. 测试断言一致性

### 缓解

1. `CandidateStatus` 枚举化
2. `CandidateSource` 枚举化
3. `GoalType` 枚举化
4. `ReviewStatus / NextAction` 继续保持枚举

---

## 6.6 P0 只解决候选，不解决事实正确性

### 问题

P0 即使解决了“候选不足仍强行比较”，也还不能解决：

1. `unknown_as_false`
2. `failed_as_empty`
3. required facet 缺失仍误答

### 缓解

1. 文档明确 P0 只做候选 sufficiency
2. P1 作为 EvidenceReview 阶段必须尽快落地
3. 不允许长期停留在“只有 CandidateReview、没有 EvidenceReview”的半完成状态

---

## 6.7 非 local_life 污染风险

### 问题

若本地生活新链路扩散到非 `local_life` 分支，会导致：

1. 普通问答链路变慢
2. 误生成 `CandidateSet`
3. 误写入 `candidate_review`

### 缓解

1. P0 不修改 `top_intent_router`
2. 非 `local_life` 仍直接 `emit_response`
3. 增加一组“非本地生活直达测试”

---

## 6.8 一次性重构 P0/P1/P2 的风险

### 问题

如果 Codex 在一次实现中把：

1. CandidateSet
2. EvidenceReview
3. DecisionReview
4. Replan

全部一起改，会造成回归范围过大，且问题难以分层定位。

### 缓解

1. 第一轮只改文档
2. 第二轮只实现 P0
3. P0 通过 trace 验收后才能进入 P1
4. P1 通过 `unknown_as_false / failed_as_empty` 验收后才能进入 P2

---

## 6.9 新规则堆叠搬家风险

### 问题

如果 `_h_target_resolve` 名义上变薄，但把原来的 `if/else` 全搬进 `CandidateResolver`，只是把旧问题换了文件名。

### 缓解

1. `CandidateResolver` 继续拆成 `explicit / context / discovery / mixed`
2. 每个分支都受单元测试约束
3. 禁止为了某个测试样例继续往单一函数里堆规则

---

## 6.10 回归检查清单

每轮代码落地后至少确认：

1. P0 不输出未实现 `next_action`
2. `task_type` 不再作为本地生活新链路唯一事实源
3. Candidate 状态已枚举化
4. fallback 不静默覆盖 LLM 核心语义
5. 非 `local_life` 仍直达 `emit_response`
6. `ToolResult` 已显式携带 `status / error_type / retriable / source`
7. P0 不解决证据正确性这一事实已在测试和验收中被清楚隔离

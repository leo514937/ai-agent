# 4. 完整改造方案（CandidateSet 驱动的受控 Plan-Execute-Review）

> 当前 LocalLifeAgent 的目标架构，不应再停留在 CandidateSet 驱动的 `Plan-Execute`。
>
> 本次整改后，目标统一升级为：
>
> `CandidateSet 驱动的受控 Plan-Execute-Review LocalLifeAgent`

---

## 4.1 架构升级结论

### 旧目标

```text
规划 → 执行 → 直接回答
```

### 新目标

```text
规划 → 执行 → Observe / Review → Sufficiency Check
     → 判断是否足够
     → 补查 / 扩搜 / 澄清 / 降级 / unsupported / fallback / 回答
```

### 目标主链路

```text
SemanticFrame
→ GoalPlanner
→ GoalReview
→ CandidateResolver
→ CandidateReview
→ EvidencePlanner
→ plan_validator
→ ToolExecute
→ EvidenceBuild / EvidencePack
→ EvidenceReview
→ DecisionPlanner
→ DecisionReview
→ AnswerGenerate
→ AnswerVerifier
→ final_response
→ state_update / trace
```

### 必须明确的边界

1. `Plan-Execute` 不能只做 plan 和 execute，执行后必须进入结构化 Review。
2. `Review` 是执行过程中的观察和决策阶段，不是最终回答润色。
3. `Review` 负责判断当前信息是否足够回答，而不是让 LLM 主观判断“差不多够了”。
4. `AnswerVerifier` 是最终自然语言校验，不能替代过程中的 `GoalReview / CandidateReview / EvidenceReview / DecisionReview`。
5. `plan_validator` 只负责工具计划合法性校验，不负责 sufficiency 判断。
6. `ToolCallGateway` 仍是唯一工具执行入口，LLM 不允许直接调用工具。
7. `top_intent_router` 不在 P0 修改范围内。
8. 非 `local_life` 仍必须直接 `emit_response`。
9. `CandidateSet / CandidateReview` 只作用于 `local_life` 分支。

### 反模式约束

这次整改不是继续在旧链路上追加 `if/else`、关键词判断和特殊 case 修复。

正确方向是通过：

- `CandidateSet`
- `Review Gate`
- `SufficiencyCheckResult`

统一收口问题，而不是靠更多 legacy rule 覆盖主链路。

---

## 4.2 Review 不是单节点，而是一组 Gate

本次设计不新增一个大一统 `review_node`，也不接受再造一个新的 300 行规则函数。

Review 必须拆成分阶段 Gate，每个 Gate 只检查自己阶段的输入输出，并只产出结构化判断与 `next_action`。

| Gate | 位置 | 核心职责 | 不允许做的事 |
|---|---|---|---|
| `GoalReview` | `GoalPlanner` 之后 | 目标是否清晰、可执行、在能力范围内 | 不修改 Goal 事实 |
| `CandidateReview` | `CandidateResolver` 之后 | CandidateSet 是否足够、是否超限、是否重复、是否需要扩搜/澄清/降级 | 不改写候选事实 |
| `EvidenceReview` | `ToolExecute` / `EvidencePack` 之后 | required/optional facet 是否满足，区分 ok/empty/unknown/failed | 不把 failed 改成 empty |
| `DecisionReview` | `DecisionPlanner` 之后 | DecisionPlan 是否覆盖核心问题，是否需要 replan / degrade / fallback | 不自行新增证据 |
| `AnswerReview` / `AnswerVerifier` | `AnswerGenerate` 之后 | 回答是否基于 EvidencePack，是否越界、错排、串店 | 不新增事实 |

### Review 统一约束

1. 每个 Review 只检查自己阶段的输入输出。
2. Review 只能输出结构化判断与 `next_action`。
3. Review 不允许修改 `ToolResult`、`EvidencePack`、`CandidateSet` 的事实值。
4. Review 不能让 LLM 直接新增 `tool_calls`。

---

## 4.3 统一 SufficiencyCheckResult 结构

所有 Gate 统一输出 `SufficiencyCheckResult`。

```python
@dataclass
class SufficiencyCheckResult:
    stage: ReviewStage
    status: ReviewStatus
    next_action: NextAction
    missing_facets: list[str]
    unknown_facets: list[str]
    failed_tools: list[str]
    affected_candidates: list[str]
    reason: str
    confidence: ConfidenceLevel
    trace_payload: dict
```

### stage 枚举

- `goal_review`
- `candidate_review`
- `evidence_review`
- `decision_review`
- `answer_review`

### status 枚举

- `enough`
- `need_more_candidates`
- `need_more_evidence`
- `need_clarification`
- `can_degrade`
- `unsupported`
- `fallback`

### next_action 枚举

- `finish`
- `expand_search`
- `replan_evidence`
- `clarify`
- `degrade_answer`
- `unsupported_answer`
- `fallback`

### 设计约束

1. `status` 和 `next_action` 必须是枚举，禁止自由字符串。
2. `CandidateReview`、`EvidenceReview`、`DecisionReview` 都可以输出 `SufficiencyCheckResult`。
3. 后续节点必须根据 `next_action` 决定继续执行、补查、澄清、降级或回答。
4. `SufficiencyCheckResult` 必须写入 `GraphState.review_results` 和 `execution_trace`。
5. 不允许 LLM 自己拍脑袋判断“信息已经够了”。

### GraphState 建议扩展

```python
review_results = {
  "goal_review": ...,
  "candidate_review": ...,
  "evidence_review": ...,
  "decision_review": ...,
  "answer_review": ...,
}
```

### ToolResult 建议标准化

完整 `EvidenceReview` 落地前，先统一 `ToolResult` 基础字段：

```python
@dataclass
class ToolResult:
    tool_name: str
    status: ToolStatus
    error_type: str | None
    retriable: bool
    source: str
    payload: dict | None = None
```

其中至少要求显式存在：

- `status`
- `error_type`
- `retriable`
- `source`

### trace 至少记录

- `stage`
- `status`
- `next_action`
- `missing_facets`
- `unknown_facets`
- `failed_tools`
- `affected_candidates`
- `reason`
- `confidence`

## 4.4 各节点职责重新对齐

| 节点 | 负责什么 | 不负责什么 |
|---|---|---|
| `top_intent_router` | 判断是否进入 `local_life` 子图 | P0 不改造其行为 |
| `GoalPlanner` | 生成 Goal、goal_type、candidate_source、evidence_needs | 不判断工具能力是否足够 |
| `GoalReview` | 判断 goal 是否清晰、可执行、受支持 | 不直接产出 ToolPlan |
| `CandidateResolver` | 将 CandidateSpec 解析为 CandidateSet | 不决定是否足够回答 |
| `CandidateReview` | 判断候选数量、唯一性、上限、歧义、来源合理性 | 不生成工具调用 |
| `EvidencePlanner` | 根据 CandidateSet + evidence_needs 生成 ToolPlan | 不判断证据是否足够 |
| `plan_validator` | 校验工具是否注册、参数是否合法、预算是否超限 | 不判断信息是否足够回答 |
| `ToolCallGateway` | 执行注册工具 | 不做业务 sufficiency 判断 |
| `EvidenceBuild / EvidencePack` | 汇总 ToolResult 为结构化证据 | 不擅自补结论 |
| `EvidenceReview` | 检查 required/optional facet 是否满足 | 不把 unknown 当 false |
| `DecisionPlanner` | 基于 EvidencePack 生成 DecisionPlan | 不决定证据够不够 |
| `DecisionReview` | 判断是否 finish / replan / degrade / fallback | 不新增 evidence |
| `AnswerGenerator` | 基于 DecisionPlan 表达回答 | 不允许新增事实或改 winner |
| `AnswerVerifier` | 最终回答事实校验 | 不替代过程 Review |

## 4.5 GoalReview 设计

### 位置

`GoalPlanner` 之后，`CandidateResolver` 之前。

### 职责

1. 检查用户目标是否清晰。
2. 检查 `goal_type` 是否可执行。
3. 检查是否属于当前工具能力范围。
4. 检查是否有足够的候选来源描述。
5. 判断是否需要澄清。
6. 判断是否需要 `unsupported / fallback`。
7. 判断是否可以进入 `CandidateResolver`。

### 示例

- 用户：“帮我订座”
  - 当前无 booking 工具。
  - `GoalReview.status = unsupported`
  - `next_action = unsupported_answer`

- 用户：“对比两家 KTV”
  - 没有明确店名，也没有默认附近策略。
  - `GoalReview.status = need_clarification`
  - `next_action = clarify`

- 用户：“附近评分最高的两家 KTV 谁优惠券多”
  - `goal_type = comparison`
  - `candidate_source = discovery`
  - `category = KTV`
  - `sort_by = rating desc`
  - `evidence_needs = coupon_list`
  - `status = enough`

## 4.6 CandidateReview 设计

### 位置

`CandidateResolver` 之后，`EvidencePlanner` 之前。

### 输入

- `Goal`
- `CandidateSet`
- `min_required`
- `max_allowed`

### 职责

1. 判断 `CandidateSet.status` 是否可进入下一阶段。
2. 判断候选数量是否满足最小要求。
3. 判断是否超过系统上限。
4. 判断是否 `ambiguous / not_found`。
5. 判断是否存在重复 `shop_id`。
6. 判断 `mixed candidate` 去重后是否仍满足数量。
7. 判断 `candidate_source` 是否合理。
8. 判断是否需要 `expand_search`。
9. 判断是否需要裁剪。
10. 判断是否需要澄清。
11. 判断是否可以降级回答。
12. 判断是否可以进入 `EvidencePlanner`。

### 必须规则化判断

1. 对比任务至少需要两个有效候选。
2. 单店任务必须绑定唯一明确目标。
3. 推荐任务必须满足最小候选数量。
4. CandidateSet 不得超过 `max_allowed`。
5. `shop_id` 重复必须去重后重检。
6. `discovery comparison` 找不到足够候选时不能强行比较。

---

## 4.7 EvidenceReview 设计

### 位置

`ToolExecute / EvidenceBuild / EvidencePack` 之后，`DecisionPlanner` 之前。

### 输入

- `Goal`
- `CandidateSet`
- `EvidencePack`
- `ToolResult` 列表
- `evidence_needs`
- `required_facets`
- `optional_facets`

### 职责

1. 检查 required facet 是否都已查询。
2. 区分 required facet 和 optional facet。
3. 检查 ToolResult 状态：`ok / empty / unknown / failed / timeout / unsupported`。
4. 判断哪些维度可以确定性回答。
5. 判断哪些维度只能说明 unknown。
6. 判断哪些工具失败不能包装成 empty。
7. 判断是否需要补查工具。
8. 判断是否可以降级回答。
9. 判断是否可以进入 `DecisionPlanner`。

### required / optional 规则

1. 用户显式问到的 facet 一律 `required`。
2. 推荐解释所需但用户没显式问到的 facet 可归为 `optional`。
3. 影响核心决策的 facet 必须提升为 `required`。

### 关键禁止项

1. `empty` 只表示工具成功执行且确定没有数据。
2. `unknown` 表示结果未知，不能说“没有”。
3. `failed` 不能包装成 `empty`。

---

## 4.8 DecisionReview 设计

### 位置

`DecisionPlanner` 之后，`AnswerGenerator` 之前。

### 职责

1. 判断 `DecisionPlan` 是否覆盖用户核心问题。
2. 判断每个 required facet 是否有结论或 unknown 说明。
3. 判断是否错误地产生确定性 winner。
4. 判断是否需要 `next_goal`。
5. 判断是否需要 `replan_evidence`。
6. 判断是否需要 `expand_search`。
7. 判断是否可以 `finish`。
8. 判断是否需要 `degrade_answer`。
9. 判断是否需要 `fallback`。
10. 判断是否进入 `AnswerGenerator`。

### 判断原则

- 证据核心未知时，不允许输出确定性推荐。
- 部分信息不足但核心问题可回答时，允许降级回答。
- `EvidenceReview.need_more_evidence` 时，应转发为 `replan_evidence`，而不是硬答。

---

## 4.9 AnswerReview / AnswerVerifier 设计

### 位置

`AnswerGenerator` 之后，`final_response_build` 之前。

### 职责

1. 校验最终回答是否基于 `EvidencePack`。
2. 检查 `unsupported_fact`。
3. 检查 `shop_id_mismatch`。
4. 检查 `unknown_as_false`。
5. 检查 `tool_failure_hidden`。
6. 检查 `ranking_changed_by_llm`。
7. 检查 required facet 是否遗漏。
8. 检查是否提到了未查询店铺。
9. 检查是否把 optional facet 包装成 required 结论。
10. 必要时 rewrite 或 fallback。

### rewrite 约束

1. rewrite 不能新增事实。
2. rewrite 不能改变 winner。
3. rewrite 不能新增未查询店铺。
4. rewrite 只能基于 `EvidencePack + DecisionPlan` 改写表达。
5. rewrite 最多 1-2 次，仍失败则 fallback。

## 4.10 Review 与 Replan 的关系

Review 不是 Reflection，不做开放式自我反思，只做结构化 sufficiency 判断。

典型流转：

1. `CandidateReview.need_more_candidates`
   - `next_action = expand_search / clarify`
2. `CandidateReview.can_degrade`
   - `next_action = degrade_answer`
3. `EvidenceReview.need_more_evidence`
   - `next_action = replan_evidence`
4. `EvidenceReview.can_degrade`
   - `next_action = degrade_answer`
5. `DecisionReview.enough`
   - `next_action = finish`
6. `DecisionReview.unsupported`
   - `next_action = unsupported_answer`
7. `AnswerVerifier.rewrite_needed`
   - rewrite 1-2 次，仍失败 `fallback`

推荐流程：

```text
Plan
→ Execute
→ Observe / Review
→ if enough: Finish
→ if need_more_candidates: Expand Search or Clarify
→ if need_more_evidence: Replan Evidence
→ if can_degrade: Degrade Answer
→ if unsupported: Unsupported Answer
→ if fallback: Fallback Answer
```

## 4.11 Retry Policy 与 Review 的关系

### 核心原则

1. Retry 只处理临时技术失败。
2. Review / Replan 处理信息不足与能力不足。
3. 语义不足、候选不足、证据 unknown、工具不支持，不应靠 retry 解决。

### 阶段级策略

| 阶段 | 是否 retry | 失败处理 |
|---|---|---|
| `SemanticFrame / GoalPlanner` | 可少量 retry | JSON 非法可 retry；仍失败走规则兜底或澄清 |
| `GoalReview` | 不 retry | `unsupported / clarify / proceed` |
| `CandidateResolver` | 可对工具失败 retry | 搜索失败 retry；候选不足交 CandidateReview |
| `CandidateReview` | 不 retry | `expand_search / clarify / degrade` |
| `EvidencePlanner` | 通常不 retry | ToolPlan 非法交 `plan_validator`；可修正一次 |
| `plan_validator` | 不 retry | 非法计划拒绝或 fallback |
| `ToolExecute` | 最适合 retry | `timeout / 5xx` retry；仍失败标 `unknown/failed` |
| `EvidenceReview` | 不直接 retry | 输出 `replan_evidence / can_degrade / fallback` |
| `DecisionPlanner` | 可少量 retry | 结构非法可 retry；证据不足不 retry |
| `DecisionReview` | 不 retry | `finish / replan / degrade / fallback` |
| `AnswerGenerator` | 可 rewrite | 格式不合格或漏字段时重写 |
| `AnswerVerifier` | 不无限 retry | rewrite 1-2 次；仍失败 fallback |

## 4.12 Review 不能完全交给 LLM

Review 主要由规则和结构化校验完成，LLM 只能辅助语义判断。

### 必须规则化判断

1. CandidateSet 数量是否满足 `min_required`。
2. CandidateSet 是否超过 `max_allowed`。
3. `shop_id` 是否重复。
4. mixed candidate 去重后是否仍满足数量。
5. required facet 是否获取成功。
6. unknown 是否被用于确定性结论。
7. failed 是否被包装成 empty。
8. AnswerPlan 中事实是否都有 EvidencePack 来源。
9. 回答是否提到了未查询店铺。
10. 工具是否注册。
11. 参数是否合法。
12. 工具调用是否超预算。
13. LLM 是否试图直接输出 `tool_calls`。

### LLM 可以辅助

1. 判断目标是否表达清晰。
2. 判断某 facet 是否属于核心问题。
3. 生成澄清问题。
4. 生成降级回答的口语化表达。
5. 辅助判断用户偏好是否影响排序。

### LLM 不允许决定

- “信息差不多够了，可以回答。”

## 4.13 推荐落地模块规划

### P0 优先

  - 定义 `ReviewStatus`
  - 定义 `NextAction`
  - 定义通用辅助函数

  - 实现 CandidateReview
  - 检查数量、状态、重复、超限、来源合理性

### P1 新增

- `planning/evidence_review.py`
  - 实现 EvidenceReview
  - 检查 required/optional facets
  - 区分 `ok / empty / unknown / failed`
  - 支持 `can_degrade`

### P2 新增

- `planning/decision_review.py`
  - 实现 DecisionReview
  - 检查 DecisionPlan 是否足够
  - 支持 `next_goal / replan_evidence / finish / degrade / fallback`

### 可选

- `planning/sufficiency_checker.py`
  - 作为统一入口分发到各 Review
  - 不承担所有业务规则，避免再次变成大函数

## 4.14 P0 / P1 / P2 渐进落地策略

### P0：CandidateSet + CandidateReview 最小落地

目标：

1. 新增 `CandidateSpec / CandidateSet`
2. 新增 `CandidateResolver`
3. 重构 `target_resolve` 为薄调度层
4. 前置新增 `review_policy.py`
5. 前置标准化 `ToolResult` 基础结构
6. 解决 discovery comparison
7. 新增 `CandidateReview`
8. 防止 CandidateSet 不足时强行比较
9. 防止超候选上限
10. 防止 mixed 去重后仍强行比较

P0 不要求：

1. 完整 `EvidenceReview`
2. 完整 `DecisionReview`
3. 多轮 `next_goal`
4. 自动 `replan_evidence`
5. 复杂 `expand_search` loop
6. 修改 `top_intent_router`

目标：

1. 用 `EvidencePlanner` 统一生成 ToolPlan

3. 增加 `EvidenceReview`
4. 区分 required/optional facet

6. 支持 `can_degrade`
7. 防止 `unknown_as_false`
8. 防止 `failed_as_empty`

### P2：GoalPlanner + DecisionPlanner + DecisionReview + Replan

目标：

1. `GoalPlanner` 取代 `task_type` 作为顶层业务目标抽象
2. `DecisionPlanner` 生成 `DecisionPlan`
3. `DecisionReview` 判断 `finish / replan / degrade / fallback`
4. 支持 `next_goal`
5. 支持 `replan_evidence`
6. 支持 `expand_search`
7. 扩展 `SessionState`：
   - `last_candidate_spec`
   - `last_candidate_set`
   - `active_goal`
   - `evidence_cache`
   - `review_results`

## 4.15 旧路由节点降级策略

### P0

- 不删除旧节点
- 只拆 `target_resolve`
- 新增 `CandidateSet / CandidateResolver / CandidateReview`
- 保持现有测试稳定
- 不修改 `top_intent_router`
- 非 `local_life` 仍直接 `emit_response`

### P1

- `facet_plan / comparison_planner` 改为 `EvidencePlanner` 兼容壳
- `route_task` 开始弱化
- `task_plan` 逐步改为统一 ToolPlan 生成

### P2

当 `GoalPlanner + CandidateResolver + EvidencePlanner + DecisionPlanner + Review` 全链路稳定后，再删除或废弃：

- `route_task`
- `_route_task_plan`
- `task_router.py` 中按 `task_type` 的硬分流
- `facet_plan`
- `comparison_planner`
- `answer_plan_build` 旧逻辑
- `target_resolve` 中大量 recommendation / comparison 特判

保留：

- `hard_guard`
- `top_intent_router`
- `semantic_parse`
- `frame_validator`
- `plan_validator`
- `ToolCallGateway`
- `tool_execute`
- `evidence_build`
- `answer_verify`
- `state_update_plan`
- `persist_session_state`
- `emit_response`

原则：

1. 先兼容壳，后删除。
2. 先测试覆盖，后删除。
3. 不要先删路由再重构。

## 4.16 禁止规则堆叠式修复

完整改造过程中，禁止以下做法：

1. 不要继续在 `_h_target_resolve` 中增加大量 `if/elif` 特判。
2. 不要把 discovery / context / mixed comparison 再塞回 `target_resolve`。
3. 不要用关键词规则覆盖 LLM 语义帧。
4. 不要让 `frame_validator / plan_validator` 改写语义。
5. 不要新增 legacy fallback 静默覆盖主链路。
6. 不要把 bug 修成“针对某句测试样例”的硬编码。

修复必须上升到通用结构：

1. 语义解析问题 → 修 `SemanticFrame / prompt / schema`
2. 候选解析问题 → 修 `CandidateSpec / CandidateResolver`
3. 候选 sufficiency 问题 → 修 `CandidateReview`
4. 证据 unknown / failed 问题 → 修 `EvidenceReview`
5. 决策问题 → 修 `DecisionPlanner / DecisionReview`
6. 回答越界问题 → 修 `AnswerVerifier / AnswerGenerator prompt`
7. 工具调用非法 → 修 `EvidencePlanner / plan_validator`
8. 非 `local_life` 路由问题 → 保持 `top_intent_router + emit_response` 现有边界，不把本地生活结构扩散出去

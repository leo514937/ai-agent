# 3. 最小改造方案

> 本文档只定义 P0 的最小落地边界。
>
> 目标不是继续在旧链路上追加 `if/else`、关键词判断和特殊 case 修复，
> 而是用 `LocalLifeGoalDraft + CandidateSet + CandidateReview + review_policy`
> 先把 discovery comparison 和候选 sufficiency 收口。

**总 Effort：P0 稳妥实现约 1 天，P0 + 完整回归约 1.5 天** | **原则：小范围、可验证、不破坏现有测试**

---

## 3.1 P0 的真实目标与非目标

### P0 只允许落地

1. `CandidateSpec`
2. `ResolvedCandidate`
3. `CandidateSet`
4. 轻量 `LocalLifeGoalDraft`
5. `CandidateResolver`
6. `CandidateReview`
7. `review_policy.py`
8. `ToolResult` 最小标准化字段
9. `_h_target_resolve` 薄调度化
10. `review_results.candidate_review` 写入 trace

### P0 解决的问题

1. discovery comparison
2. 候选不足
3. 候选超限
4. 重复 `shop_id`
5. mixed 去重后不足

### P0 不实现完整

1. `expand_search` loop
2. `replan_evidence`
3. `DecisionPlanner`
4. `DecisionReview`
5. `GoalPlanner` 完整版
6. `EvidenceReview` 完整版
7. 完整 graph 重写

### P0 的 `next_action` 边界

P0 阶段 `CandidateReview.next_action` 只允许：

1. `finish`
2. `clarify`
3. `fallback`

如果为了兼容后续阶段保留 `expand_search` 枚举，也只能作为预留，不允许 P0 graph 真正跳转到未实现节点。

这里的 `finish` 只表示“候选阶段通过，可以进入 `EvidencePlanner` 或旧 planner 兼容链路”，不表示直接生成最终回答。

---

## 3.2 P0 的作用域与不变边界

1. `top_intent_router` 不修改。
2. 非 `local_life` 仍必须直接 `emit_response`。
3. `CandidateSet / CandidateReview` 只作用于 `local_life` 分支。
4. 不允许把 CandidateSet 机制扩散到通用聊天、非本地生活问答或其他分支。

---

## 3.3 禁止规则堆叠式修复

P0 不是继续在旧链路上补零散规则。

禁止以下做法：

1. 在 `_h_target_resolve` 中继续追加大量 `if/elif` 特判。
2. 把 discovery / context / mixed comparison 再塞回 `target_resolve` 大函数。
3. 用关键词规则覆盖 LLM 输出的核心语义结论。
4. 让 `frame_validator / plan_validator` 改写语义。
5. 针对某句测试样例做硬编码修复。
6. 把旧规则原样搬进 `CandidateResolver`，形成新的规则堆叠。

每个 bug 都必须先落到结构层定位：

1. `SemanticFrame` 构建问题
2. `LocalLifeGoalDraft` 构建问题
3. `CandidateSpec` 构建问题
4. `CandidateResolver` 问题
5. `CandidateReview` 问题

---

## 3.4 P0 轻量目标抽象：LocalLifeGoalDraft

P0 不完整重写 `GoalPlanner`，但也不能继续完全依赖旧 `task_type`。

因此在 `SemanticFrame → CandidateSpec` 之间增加一个轻量目标抽象：

```python
@dataclass
class LocalLifeGoalDraft:
    goal_type: GoalType
    candidate_source: CandidateSource
    candidate_category: str | None
    candidate_limit: int | None
    evidence_needs: list[str]
    required_facets: list[str]
    optional_facets: list[str]
    max_candidates: int = 5
    source_origin: str = "llm"
```

### 约束

1. P0 不完整重写 `GoalPlanner`。
2. P0 需要用 `LocalLifeGoalDraft` 承接 LLM 语义帧。
3. `task_type` 只能作为兼容字段，不能继续作为唯一事实源。
4. `candidate_source / candidate_limit / evidence_needs` 优先来自 LLM `SemanticFrame`。
5. 规则 fallback 只能补齐字段，不能静默覆盖 LLM 核心语义。

## 3.5 Candidate / Goal / Review 状态枚举

```python
class CandidateStatus(str, Enum):
    RESOLVED = "resolved"
    AMBIGUOUS = "ambiguous"
    NOT_FOUND = "not_found"
    PARTIAL = "partial"
    TOO_MANY = "too_many"
    NEED_CLARIFICATION = "need_clarification"


class CandidateSource(str, Enum):
    EXPLICIT = "explicit"
    CONTEXT = "context"
    DISCOVERY = "discovery"
    MIXED = "mixed"


class GoalType(str, Enum):
    RECOMMENDATION = "recommendation"
    COMPARISON = "comparison"
    SINGLE_SHOP_QUERY = "single_shop_query"
    REFINEMENT = "refinement"
    UNSUPPORTED = "unsupported"
```

要求：

1. `CandidateSet.status` 必须使用 `CandidateStatus`
2. `CandidateSet.source` 必须使用 `CandidateSource`
3. `ReviewStatus / NextAction` 继续使用枚举
4. 文档中不再用自由字符串描述关键状态

## 3.7 candidate_limit 默认值策略

统一为：

```python
candidate_limit: int | None = None
```

默认策略由 `GoalPolicy / LocalLifeGoalDraft` 决定：

1. comparison 默认 2
2. recommendation 默认 3
3. single_shop_query 默认 1
4. `max_allowed` 默认 5
5. 用户显式指定数量时，先尊重用户数量，再由 `CandidateReview` 检查是否超过 `max_allowed`
6. 超过 `max_allowed` 时，不能直接规划全部候选，只能裁剪并说明、澄清或降级

## 3.8 SemanticFrame 与 slot_extractor fallback 边界

`SemanticFrame / intent_parser` 只负责语义字段定义和 LLM 解析提示词。

建议增加：

```python
candidate_source: CandidateSource | None = None
candidate_category: str = ""
candidate_sort_by: list[dict] = Field(default_factory=list)
candidate_limit: int | None = None
candidate_filters: dict = Field(default_factory=dict)
```

### 边界

1. LLM 是 `SemanticFrame` 的主事实源。
2. `slot_extractor` 只能做：
   - 字段补齐
   - 别名标准化
   - 序号引用提取
   - 明显缺失字段的 fallback
3. `slot_extractor` 不允许静默改写：
   - `task_type / goal_type`
   - `candidate_source`
   - `candidate_limit`
   - `required_facets`
   - comparison / recommendation 的核心意图
4. 如果 fallback 参与补齐，必须写入：
   - `semantic_source`
   - `candidate_source_origin`
   - `fallback_reason`
   - `execution_trace`

## 3.9 CandidateResolver 与 CandidateReview

### CandidateResolver

```text
_h_target_resolve -> 薄调度层
  ├── resolve_explicit()
  ├── resolve_context()
  ├── resolve_discovery()
  └── resolve_mixed()
```

约束：

1. `target_resolve` 只负责调度，不负责堆业务特判。
2. discovery / context / mixed 候选解析进入 `CandidateResolver`。
3. `_h_target_resolve` 变薄后，也不能把旧 if/else 规则堆叠原样搬进 `CandidateResolver`。

### CandidateReview

职责：

1. 检查 `CandidateSet.status`
2. 检查 `min_required`
3. 检查 `max_allowed`
4. 去重 `shop_id`
5. mixed 去重后重新检查数量
6. 输出统一 `SufficiencyCheckResult`

P0 典型输出：

- `enough -> finish`
- 候选不足 -> `need_more_candidates + clarify/fallback`
- 候选超限：
  - 允许自动裁剪时 -> `finish`
  - 不允许自动裁剪时 -> `clarify`
- 明显异常 -> `fallback`

补充规则：

1. 候选不足时：
   - `status` 应为 `NEED_MORE_CANDIDATES`
   - P0 的 `next_action` 为 `CLARIFY` 或 `FALLBACK`
   - P2 才允许 `next_action=EXPAND_SEARCH`
2. 候选超限时：
   - 如果允许自动裁剪，则输出 `next_action=finish`
   - 并在 `trace_payload` 中记录：
     - `trimmed=true`
     - `original_count`
     - `kept_count`
   - 如果不允许自动裁剪，则输出 `next_action=clarify`
3. 不建议在 CandidateReview 阶段直接 `degrade_answer`，除非无法继续执行

强约束：

P0 不允许把“候选不足是否还能继续比较”的判断留在：

1. `comparison_planner`
2. `answer_generator`
3. `answer_verifier`

## 3.10 P0 与旧路由的兼容策略

1. 不立刻删除旧节点。
2. 旧 recommendation / single_shop_query 先保持原路径。
3. discovery comparison 优先进入 `LocalLifeGoalDraft + CandidateResolver + CandidateReview`。
4. 旧 `facet_plan / comparison_planner` 暂不重写，只避免让它们承接 sufficiency 判断。
5. `top_intent_router` 保持不变。
6. 非 `local_life` 仍直接 `emit_response`。
7. 旧 `task_type` 仍可作为兼容输入，但不能继续绑架 `CandidateSpec` 与 `CandidateReview` 的判断。

## 3.11 P0 测试要求

### CandidateResolver / CandidateReview 至少覆盖

1. discovery comparison 找到 2 家
2. discovery comparison 只找到 1 家
3. 超过 `max_allowed`
4. mixed 重复 `shop_id`
5. 去重后不足 2 家
6. `candidate_limit=None` 时由 `LocalLifeGoalDraft` 正确补默认值
7. fallback 参与补齐时写入 `semantic_source / candidate_source_origin / fallback_reason`

### 非本地生活直达测试

1. 非 `local_life` 输入不会进入 `CandidateResolver`
2. 非 `local_life` 输入不会生成 `CandidateSet`
3. 非 `local_life` 输入不会写入 `review_results.candidate_review`
4. 非 `local_life` 输入仍直接 `emit_response`

### 测试断言不能只看最终话术

必须断言：

1. `semantic_source`
2. `candidate_source`
3. `candidate_source_origin`
4. `fallback_reason`
5. `CandidateSet`
6. `review_results`
7. `next_action`
8. `trace`

## 3.12 P0 验收标准

1. “对比附近评分最高的两家 KTV，看看谁的优惠券多，营业状态如何”
   - 必须进入 discovery CandidateSet
   - 不允许回复“请补充另一家店名”
   - 找到 2 家才继续
   - 只找到 1 家时 CandidateReview 拦截
2. “附近评分最高的 10 家火锅都详细对比”
   - 必须触发 `max_allowed`
   - 不能直接生成 10 家详细 ToolPlan
3. “第一家和海底捞比”
   - 如果恢复后是同一家，去重后不足 2 家，不能继续比较
4. explicit comparison 不回归
5. recommendation 不回归
6. single_shop_query 不回归
7. 非 `local_life` 不进入 `CandidateResolver`、不生成 `CandidateSet`、不写 `candidate_review`
8. 修复方式体现为结构收口，而不是新增散落规则

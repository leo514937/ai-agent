# 04_任务决策与工具编排层

# 一、层职责

任务决策与工具编排层负责把 `SemanticFrame + ResolvedTarget` 转换成可执行的 `ExecutionPlan`。

它要决定：

- 走哪条任务链路；
- 需要调用哪些工具；
- 工具之间串行还是并行；
- 哪些工具是强依赖；
- 哪些工具是弱依赖；
- 失败后如何降级；
- 推荐和对比如何排序；
- 一轮最多允许多少 ToolCall；
- 多 facet 任务如何展开。

# 二、模块划分

| 模块 | 作用 |
|---|---|
| TaskRouter | 路由到具体任务链路 |
| FacetPlanBuilder | 将多 facet 需求展开为工具需求 |
| ToolRequirementPlanner | 判断需要哪些工具 |
| ParamBuilder | 构造工具参数 |
| ExecutionModePlanner | 决定串行/并行/分阶段并行 |
| DependencyClassifier | 区分强依赖和弱依赖 |
| RankingPolicy | 推荐排序策略 |
| ComparisonToolPlanner | 对比任务工具规划 |
| ComparisonBudgetController | 控制多店对比工具预算 |
| FallbackPolicyBuilder | 生成失败降级策略 |
| ExecutionPlanBuilder | 输出最终执行计划 |

# 三、TaskRouter

任务链路：

```text
capability_flow
recommendation_flow
recommendation_refine_flow
single_shop_flow
coupon_query_flow
open_status_flow
distance_query_flow
comparison_flow
coupon_decision_flow
clarification_flow
invalid_flow
```

示例：

| 输入 | flow |
|---|---|
| 附近推荐火锅 | recommendation_flow |
| 海底捞有券吗 | coupon_query_flow |
| 第一家远吗 | distance_query_flow |
| 便宜一点的呢 | recommendation_refine_flow |
| 海底捞和山城一锅哪个好 | comparison_flow |
| 海底捞有券吗，顺便看现在营业吗 | single_shop_flow + facets |

原则：

1. 顶层 flow 不宜过多；
2. 多 facet 不新增大量 flow，而是在 flow 内通过 FacetPlan 展开；
3. comparison_flow 同时支持两店和多店对比；
4. route 只决定“做什么”，不直接执行工具。

# 四、FacetPlan

多意图、多查询维度统一用 `FacetPlan` 表达。

```json
{
  "primary_flow": "single_shop_flow",
  "facets": [
    {
      "facet": "coupon",
      "required": true,
      "tool": "get_coupon_list"
    },
    {
      "facet": "open_status",
      "required": true,
      "tool": "check_open_status"
    },
    {
      "facet": "distance",
      "required": false,
      "tool": "get_distance_eta"
    }
  ]
}
```

好处：

- “有券吗，顺便看营业”不会丢失子问题；
- 对比任务可以聚焦距离、优惠、营业、价格；
- ToolPlanner 可以稳定映射工具；
- AnswerPlan 可以覆盖用户所有问题。

# 五、工具需求映射

当前工具清单：

```text
resolve_shop
search_shops
get_shop_detail
get_coupon_list
check_open_status
get_distance_eta
```

## 5.1 recommendation_flow

用户示例：

```text
附近有没有适合约会、现在营业、最好有券的火锅？
```

推荐工具：

1. `search_shops`：召回候选；
2. `get_shop_detail`：补评分、人均、地址、标签；
3. `check_open_status`：确认营业状态；
4. `get_coupon_list`：确认优惠；
5. `get_distance_eta`：计算距离和 ETA。

执行模式：

```text
search_shops
  ↓
对候选店分阶段并行调用：
  get_shop_detail
  check_open_status
  get_coupon_list
  get_distance_eta
  ↓
RankingPolicy 排序
```

## 5.2 single_shop_flow

用户示例：

```text
海底捞水晶城店怎么样？
```

需要工具：

- `get_shop_detail`；
- `check_open_status`；
- `get_distance_eta`；
- `get_coupon_list` 可选，除非用户关心优惠。

## 5.3 coupon_query_flow

前置要求：必须已有唯一 `shop_id`。

工具：

- `get_coupon_list`。

## 5.4 open_status_flow

前置要求：必须已有唯一 `shop_id`。

工具：

- `check_open_status`。

## 5.5 distance_query_flow

前置要求：必须已有唯一 `shop_id`。

工具：

- `get_distance_eta`。

origin 固定为北京邮电大学。

## 5.6 comparison_flow

对比任务不需要拆出 `multi_comparison_flow`。

内部根据 `target_count` 和 `comparison_focus` 区分：

```text
comparison_flow
  ├── pairwise_comparison：两店对比
  ├── multi_shop_comparison：三店及以上对比
  └── focused_comparison：只比较距离/券/营业等单一维度
```

多店对比流程：

1. 解析多个 `shop_id`；
2. 判断 `comparison_focus`；
3. 生成工具计划；
4. 批量并行调用工具；
5. 构建 ComparisonMatrix；
6. ComparisonAnalyzer 结构化分析；
7. AnswerPlanBuilder 生成回答计划；
8. AnswerGenerator 自然表达；
9. AnswerVerifier 校验。

# 六、search_shops 召回策略

`search_shops` 是推荐链路的强依赖，它的召回策略必须明确。

## 6.1 默认参数

```json
{
  "center": {
    "name": "北京邮电大学",
    "lat": 39.9609,
    "lng": 116.3581
  },
  "radius_km": 3,
  "limit": 20,
  "category": "火锅"
}
```

## 6.2 召回与过滤原则

1. 默认半径 3km。
2. 若召回为空，可扩大到 5km，但回答中要说明范围扩大。
3. “附近”默认不是绝对硬过滤，而是距离打分核心因素。
4. “必须现在营业”是硬约束。
5. “现在营业的”通常是硬约束。
6. “最好有券”是软偏好，不直接过滤。
7. “必须有券”才是硬约束。
8. “适合约会”默认是场景打分，不直接过滤。
9. 类目先做强匹配，再考虑同义类目扩展，例如火锅/涮肉/串串。
10. search 阶段不宜把所有条件都硬过滤，否则容易召回为空。

## 6.3 空结果策略

如果 search_shops 返回空：

1. 检查是否硬约束过多；
2. 可放宽软偏好；
3. 可扩大半径；
4. 仍为空则明确说明“按当前条件暂时没搜到”；
5. 不允许编造商户。

# 七、ExecutionModePlanner

执行模式：

| 模式 | 场景 |
|---|---|
| single | 单工具查询，例如查券 |
| sequential | 文本店名查券：resolve_shop → get_coupon_list |
| parallel | 多店多个工具并行 |
| staged_parallel | 推荐：先 search，再对候选并行补详情 |

对比任务正确链路：

```text
目标解析阶段：
  resolve_shop / ReferenceResolver
  ↓
拿到唯一 shop_id 列表
  ↓
批量工具查询阶段：
  对多个 shop_id 并行查 detail/coupon/open/distance
```

注意：没有 `shop_id` 之前不能调用单店工具。

# 八、DependencyClassifier

## 8.1 推荐任务依赖

| 工具 | 依赖级别 | 说明 |
|---|---|---|
| search_shops | 强依赖 | 失败则无法推荐 |
| get_shop_detail | 中强依赖 | 失败则结果质量明显下降 |
| check_open_status | 条件强依赖 | 用户要求现在营业时为强依赖 |
| get_coupon_list | 弱依赖 | 失败则优惠未知 |
| get_distance_eta | 条件强依赖 | 用户强调附近/远近时为强依赖 |

## 8.2 对比任务依赖

根据 `comparison_focus` 动态判断：

| focus | 强依赖 | 弱依赖 |
|---|---|---|
| overall | get_shop_detail、部分 open/distance | coupon 可弱依赖 |
| distance | get_distance_eta | get_shop_detail |
| coupon | get_coupon_list | get_shop_detail |
| open_status | check_open_status | get_distance_eta |
| price/value | get_shop_detail | coupon、distance |

unknown 不能直接当作低分，只能降低结论置信度。

# 九、推荐排序公式

MVP 推荐先采用可解释的线性打分，不要一开始做复杂模型。

```text
score =
  0.25 * distance_score
+ 0.20 * open_score
+ 0.20 * category_match_score
+ 0.15 * rating_score
+ 0.10 * coupon_score
+ 0.10 * price_match_score
- risk_penalty
```

## 9.1 维度说明

| 维度 | 说明 |
|---|---|
| distance_score | 距离越近分越高 |
| open_score | 确认营业得高分，未知中性或降权，确认未营业过滤或低分 |
| category_match_score | 品类完全匹配高分 |
| rating_score | 评分归一化 |
| coupon_score | 有券加分，unknown 不加不减，empty 不加分 |
| price_match_score | 与预算/便宜偏好匹配 |
| risk_penalty | 工具失败、信息缺失、低置信解析等惩罚 |

## 9.2 硬过滤与软打分

硬过滤：

- 品类完全不匹配；
- 用户明确要求现在营业，但工具确认未营业；
- 用户明确要求必须有券，但工具确认无券；
- 无效商户；
- 距离严重超出且用户明确“近一点”。

软打分：

- 最好有券；
- 适合约会；
- 评分高；
- 便宜一点；
- 更近；
- mock 偏好。

## 9.3 推荐输出策略

推荐 3 家左右：

1. 最匹配当前需求；
2. 更省钱；
3. 更近或更稳妥。

输出结构：

```json
{
  "items": [
    {
      "shop_id": "shop_001",
      "rank": 1,
      "strategy": "最匹配",
      "reason_codes": ["open_now", "has_coupon", "nearby", "scene_match"],
      "score": 0.91
    }
  ]
}
```

规则：排序由系统完成，LLM 只解释排序结果。

# 十、ComparisonBudgetController

多店对比工具预算：

| 对比数量 | 策略 |
|---|---|
| 2 家 | 完整对比 |
| 3 家 | 可完整对比 |
| 4～5 家 | 优先聚焦用户关心维度 |
| 超过 5 家 | 建议缩小范围，或先粗筛 |

MVP 配置：

```json
{
  "max_full_compare_shops": 3,
  "max_tools_per_shop": 4,
  "max_tool_calls_per_turn": 12,
  "max_parallel_tool_calls_per_turn": 8,
  "turn_deadline_ms": 6000
}
```

# 十二、本层实现注意事项

1. Planner 只生成计划，不直接执行工具。
2. LLM 不直接自由选择不存在的工具。
3. 工具名必须来自 ToolRegistry。
4. 单店工具必须有 `shop_id`。
5. 多 facet 不能丢失用户子问题。
6. 推荐排序要由系统策略完成，不交给 LLM 自由发挥。
7. 对比任务必须先形成 ComparisonMatrix，再让 LLM 表达。
8. 工具预算必须在计划阶段控制，不能无限并行。

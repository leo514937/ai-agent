# 01.5 补全核心协议与执行依赖

## 目标
深化 `ExecutionPlan`, `EvidencePack`, `ResolveShopResult` 的协议定义，避免后续开发中出现编排模糊和验证无锚点。

## 实现细节要求

### 1. EvidencePack (证据包)
作为可信回答的唯一基石，不能只是一段文本，必须高度结构化：
- `target_shop_ids`: list
- `evidence_items`: list，其内部结构 `EvidenceItem` 包含：
  `evidence_id`, `shop_id`, `shop_name`, `facet`, `tool_name`, `call_id`, `result_status`, `field_path`, `value`, `confidence`, `timestamp`, `source_type` (tool/mock/http/db)。
- `unknown_items`: 未知项的列表（告知模型必须澄清未知）。
- `forbidden_claims`: 禁止断言的列表。
- `ranking_snapshot`: 系统排序快照。
- `comparison_matrix`: 用于对比的矩阵数据。

### 2. ExecutionPlan 扩展
支持复杂的阶段并行与批量编排，将 `tool_calls` 扩充为 `ToolCallSpec`:
- 字段包含 `call_id`, `tool_name`, `args`, `target_shop_id`, `required`, `facet`, `depends_on`, `timeout_ms`, `retry_policy`, `fallback_policy`, `group_id`, `max_parallelism`。
- 显式表达推荐阶段流：
  - `stage_1`: search_shops
  - `stage_2`: batch get_shop_detail for top_k_candidates
  - `stage_3`: batch check_open_status / get_coupon_list；推荐流中 distance 默认来自 search_shops，只有单店多 facet 或 search_shops 未返回距离时，才允许调用 get_distance_eta。
  - `stage_4`: ranking_policy

### 3. AnswerPlan 的深度结构化 (支持 Strict Natural)
为了让 `strict_natural` 可控，不再让大模型自由生成，而是将其收束到：
- `answer_type`: single_shop, recommendation, comparison, clarification, error 等。
- `target_shop_ids`: list
- `response_sections`: list
- `allowed_claims`: 结构化许可断言列表 `list[AllowedClaim]`。其结构为：
  `claim_id`, `shop_id`, `facet`, `evidence_ids`, `claim_type`, `value`, `verbalization_hint`。
- `required_claims`: 必须说出的话。
- `must_mention_unknowns`: 必须说明未知的维度。
- `forbidden_claims`: 禁止断言。
- `ranking_snapshot_id`, `comparison_matrix_id`
- `tone`: 语气。
- `fallback_template_type`: 当 AnswerVerifier 超过 `max_rewrite_attempts` 失败时回退的硬模板枚举。

### 4. ResolveShopResult 的细化与隔离
规范状态返回：
- `status`: RESOLVED, AMBIGUOUS, LOW_CONFIDENCE, NOT_FOUND。
- `resolved_shop`: `ShopRef | None` (仅 RESOLVED 时有值)。
- `candidates`: `list[ShopCandidate]` (AMBIGUOUS 必有，NOT_FOUND 必空)。
- `confidence`: float
- `matched_by`: exact, alias, fuzzy, location_hint, history。
- `reason`: string。

### 5. 决策唯一归属表
为防止多个模块互相抢占“决策权”，发生多处 if/else 互相覆盖，建立以下防线归属：
| 决策项 | 唯一负责人 | 其他模块是否可修改 |
| --- | --- | --- |
| `top_intent` | `TopIntentRouter` | `FrameValidator` 只能校验，不能重判 |
| `task_type` | `SemanticParser` | `TaskRouter` 只能消费，不重新识别 |
| `facets` | `SlotExtractor / SemanticParser` | `FacetPlanner` 只能映射工具，不能增删 |
| `shop_id` | `resolve_shop` 工具 | LLM 永远不能生成或编造 `shop_id` |
| 推荐排序 | `RankingPolicy` | LLM 绝对不能更改排序结果 |
| 是否写 `current_shop` | `StateUpdatePlanner` | 其他模块绝对不能直接写 Session |

### 6. ExecutionPlan 校验节点 (PlanReview)
在真正执行工具前，必须通过 `ExecutionPlanValidator` 拦截非法计划，保证 Trace 干净：
| 校验项 | 目的 |
| --- | --- |
| `tool_name` 是否注册 | 防止 LLM 编造虚假工具导致宕机 |
| `args` 匹配 schema | 防止无效调用传给下游导致服务异常 |
| `shop_id` 来自合法 resolve | 彻底阻断 LLM 自造幻觉 `shop_id` |
| `depends_on` 是否成环 | 防止执行计划发生依赖死锁 |
| `required/optional` 标记 | 决定节点失败后是直接中断抛出还是继续降级 |
| `max_tool_calls` 超限 | 严格控制预算膨胀 |
| `forbidden_tools` 检查 | 防止查券意图误调用了大规模全局搜索工具 |

## 本阶段完成标准 (Definition of Done)
1. 对应的 Schema (如 `domain/schemas.py`) 补充编写完毕，具备严格的类型及组合校验（如状态为 AMBIGUOUS 时如果 candidates 为空则 Pydantic 报错）。
2. 提供 `tests/test_01_5_schemas.py` 覆盖各种协议格式及非法校验拦截。

## 阶段完成后的收尾

- 检查 `ExecutionPlan / EvidencePack / AnswerPlan / ResolveShopResult` 是否都已经有唯一归属。
- 确认没有重复字段、双版本协议或冲突语义。

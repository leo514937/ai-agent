# 03_上下文与目标解析层

# 一、层职责

上下文与目标解析层负责把 `SemanticFrame` 中的语义目标补全成可执行对象。

它要解决：

- 用户说“这家”指谁；
- 用户说“第一家”指谁；
- 用户说“便宜一点”是在上一轮推荐上收敛，还是新推荐；
- 用户说“海底捞”是哪家门店；
- 用户说“和海底捞比呢”时，对比基准是谁；
- 单店任务是否已经拿到唯一 `shop_id`；
- 多候选、低置信、未找到时是否需要澄清。

核心原则：

> 所有需要单店事实数据的任务，必须先得到唯一 `shop_id`。多候选不能默认第一家。

# 二、模块划分

| 模块 | 作用 |
|---|---|
| SessionStateReader | 读取上一轮会话状态 |
| ContextRecovery | 恢复多轮上下文和省略意图 |
| ReferenceResolver | 解析“这家/第一家/第二家”等引用 |
| ShopResolver | 通过 ToolCall 将商户名解析为 shop_id |
| TargetRequirementChecker | 判断任务是否需要目标店 |
| ClarifyDecider | 判断是否需要澄清 |
| ClarificationStateManager | 保存和恢复澄清任务 |
| ResolvedTargetBuilder | 输出统一目标解析结果 |

# 三、SessionState 设计

## 3.1 SessionState Schema

```json
{
  "current_shop": null,
  "last_recommendation_list": [],
  "active_constraints": {},
  "last_task_type": null,
  "pending_clarification": null,
  "last_tool_results_summary": {},
  "comparison_targets": [],
  "comparison_result": null,
  "suggested_shop": null,
  "state_version": 1,
  "updated_at": "2026-06-19T10:00:00+09:00"
}
```

## 3.2 状态生命周期

| 状态字段 | 写入时机 | 过期/清理策略 |
|---|---|---|
| current_shop | 单店任务成功，或用户明确选择某家 | 用户换主题/换品类/多轮超时后清空 |
| last_recommendation_list | 推荐成功 | 保留最近 1～3 轮，超过轮数降权 |
| active_constraints | 推荐/收敛成功 | 新品类、新区域、新明确条件时重置或合并 |
| pending_clarification | 发起澄清时 | 用户完成选择、超时、换主题后清空 |
| comparison_targets | 对比任务成功 | 新对比任务覆盖，换主题清空 |
| comparison_result | 对比任务成功 | 与 comparison_targets 同生命周期 |
| suggested_shop | 推荐或对比给出明确建议时 | 不能直接等同 current_shop |

## 3.3 状态污染控制

1. 推荐返回多家店时，不默认把第一家写入 `current_shop`。
2. 对比完成后，不默认把排名第一写入 `current_shop`。
3. 用户明确说“第一家”“推荐那家”“就它”时，才可以设置 `current_shop`。
4. 用户切换品类，例如“不吃火锅了，推荐烧烤”，应清空或重建 `active_constraints`。
5. 用户切换区域，例如“不在北邮附近，换五道口”，应重建位置约束。
6. `pending_clarification` 存在时，优先判断用户是否在回复澄清。

# 四、ContextRecovery

## 4.1 处理规则

1. “这家 / 它 / 刚才那家”  
   → 尝试绑定 `current_shop` 或上一轮唯一明确对象。

2. “第一家 / 第二家”  
   → 从 `last_recommendation_list` 或 `comparison_result.ranking` 中取对应店铺。

3. “便宜一点 / 近一点 / 有券的”  
   → 继承 `active_constraints`，追加新约束，进入 `recommendation_refine`。

4. “和海底捞比呢”  
   → 使用 `current_shop`、`suggested_shop` 或上一轮明确目标作为对比对象之一，再解析“海底捞”。

5. “那就看它的券”  
   → 继承目标，任务改为 `coupon_query`。

## 4.2 失败情况

进入澄清：

- 用户说“这家”，但 `current_shop` 为空；
- 用户说“第一家”，但没有上一轮推荐列表或对比排序；
- 用户说“和海底捞比”，但缺少当前对比基准；
- 用户说“它”，但上一轮有多个对象且没有明确建议；
- `pending_clarification` 已过期，用户回复“1”。

# 五、ReferenceResolver

支持引用类型：

```text
current_shop
rank_index
last_recommendation_item
comparison_ranking_item
suggested_shop
pending_clarification_selection
```

输出示例：

```json
{
  "status": "RESOLVED",
  "shop_id": "shop_001",
  "shop_name": "山城一锅",
  "source": "last_recommendation_list",
  "confidence": 0.95
}
```

失败示例：

```json
{
  "status": "NOT_FOUND",
  "reason": "NO_LAST_RECOMMENDATION_LIST"
}
```

# 六、ShopResolver

ShopResolver 通过 ToolCall 将商户名解析成唯一 `shop_id`。

输入：

```json
{
  "merchant_mention": "海底捞水晶城店",
  "user_location": {
    "name": "北京邮电大学",
    "lat": 39.9609,
    "lng": 116.3581
  },
  "city": "北京"
}
```

调用工具：

```text
resolve_shop
```

输出状态：

```text
RESOLVED
AMBIGUOUS
NOT_FOUND
LOW_CONFIDENCE
TOOL_FAILED
```

规则：

1. 单店任务必须解析成唯一 `shop_id`。
2. 多候选不能默认取第一家。
3. `NOT_FOUND` 不继续调用单店工具。
4. `LOW_CONFIDENCE` 需要澄清。
5. `AMBIGUOUS` 需要澄清。
6. `TOOL_FAILED` 不能说“没有这个店”，只能说暂时无法确认。

# 七、TargetRequirementChecker

| 任务 | 是否需要 shop_id |
|---|---|
| recommendation | 否 |
| recommendation_refine | 否，优先依赖 last_recommendation_list |
| single_shop_query | 是，至少一个 |
| coupon_query | 是，一个 |
| open_status_query | 是，一个 |
| distance_query | 是，一个 |
| comparison | 是，至少两个 |
| coupon_decision | 是，一个或多个 |
| capability | 否 |
| invalid/out_of_scope | 否 |

# 八、澄清与恢复执行

## 8.1 什么时候澄清

需要澄清：

1. 单店任务没有 `shop_id`；
2. 店名解析出多个候选；
3. 店名解析置信度低；
4. 用户说“这家”，但没有 `current_shop`；
5. 用户说“第一家”，但没有 `last_recommendation_list`；
6. 对比任务少于两个对象；
7. 用户问题本身任务不明确；
8. 多店对比中某个商户多候选，且该商户是必须目标。

不需要澄清：

1. 推荐类问题没有具体商户；
2. 附近查询没有用户位置，因为默认位置是北京邮电大学；
3. 用户偏好缺失，因为当前使用 mock 默认偏好。

## 8.2 pending_clarification Schema

```json
{
  "pending_id": "pending_001",
  "original_task_type": "coupon_query",
  "original_semantic_frame": {},
  "candidate_targets": [
    {
      "index": 1,
      "shop_id": "shop_001",
      "shop_name": "海底捞火锅(水晶城购物中心店)",
      "address": "..."
    },
    {
      "index": 2,
      "shop_id": "shop_002",
      "shop_name": "海底捞火锅(学院路店)",
      "address": "..."
    }
  ],
  "expected_reply_type": "candidate_index",
  "created_at": "2026-06-19T10:00:00+09:00",
  "expires_at": "2026-06-19T10:10:00+09:00"
}
```

## 8.3 澄清恢复流程

```text
用户：海底捞有券吗？
  → resolve_shop 返回 AMBIGUOUS
  → 保存 pending_clarification
  → 回复：你说的是哪一家？1...2...

用户：1
  → 优先命中 pending_clarification
  → 选择 candidate_targets[0]
  → 恢复 original_task_type = coupon_query
  → 构造 ResolvedTarget
  → 继续进入任务决策与工具编排层
  → 调用 get_coupon_list
  → 清空 pending_clarification
```

注意：澄清回复不是新的普通用户问题，必须优先走 `ClarificationStateManager`。

```json
  "inherited_constraints": {},
  "warnings": []

```

多店对比：

```json
{
  "task_type": "comparison",
  "target_status": "RESOLVED",
  "targets": [
    {"shop_id": "shop_001", "shop_name": "海底捞"},
    {"shop_id": "shop_002", "shop_name": "山城一锅"},
    {"shop_id": "shop_003", "shop_name": "凑凑"}

  "comparison_focus": "overall"

```

# 十、本层实现注意事项

1. `merchant_mentions` 不是 `shop_id`。
2. `shop_id` 只能来自 `resolve_shop`、上轮状态或明确选择。
3. 多候选不能默认第一家。
4. 工具失败不能伪装成未找到。
5. 上下文恢复要有置信度，低置信不要强行猜。
6. 澄清状态要能恢复原任务，而不是只返回一个问题。
7. 对比任务可以支持 2～3 家完整对比，4～5 家聚焦维度，超过 5 家建议缩小范围。

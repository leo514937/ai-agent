# 01_总览与输入接入层

# 一、架构定位

本系统是一个面向本地生活消费决策的对话式 Agent，目标不是简单聊天，也不是普通搜索框，而是帮助用户完成：

1. 附近找店；
2. 单店信息查询；
3. 优惠券查询；
4. 营业状态查询；
5. 距离和 ETA 查询；
6. 多店对比；
7. 多轮条件收敛；
8. 推荐消费决策。

当前版本采用 **六层架构**，之前 5 个文档中将“输入接入层”和“语义理解层”放在同一份文档里，容易造成“5 个文件 = 5 层”的误解。重构后明确拆成 6 个文档，对应 6 个可实现层级。

# 二、当前版本设计边界

## 2.1 输入边界

当前只支持：

- 文本输入。

暂不支持：

- 语音输入；
- 图片输入；
- 地图选点；
- 卡片点击输入；
- 复杂表单输入。

虽然当前不支持卡片输入，但澄清链路要预留 `pending_clarification`，用户可以通过文本编号回复，例如“1”“第二个”。

## 2.2 位置边界

当前用户位置使用 mock 数据，固定为：

```json
{
  "name": "北京邮电大学",
  "city": "北京",
  "district": "海淀区",
  "lat": 39.9609,
  "lng": 116.3581
}
```

附近推荐、距离、ETA 都基于该 mock 位置计算。

商铺位置信息已经存在于商户库中，包括：

- 商户地址；
- 经纬度；
- 商圈；
- 城市；
- 区域。

当前不设计商铺位置采集模块。

## 2.3 用户信息边界

当前用户信息使用 mock 数据：

```json
{
  "user_id": "mock_user_001",
  "user_location": "北京邮电大学",
  "user_preferences": {
    "price_sensitive": true,
    "preferred_distance_km": 3,
    "likes": ["火锅", "烧烤", "咖啡"],
    "dislikes": []
  }
}
```

暂不接入：

- 真实登录；
- 真实用户画像；
- 真实长期记忆；
- 真实消费历史；
- 真实收藏行为。

回答中不能说“根据你的真实历史偏好”，只能说“我先按你当前位置附近和当前条件筛选”。

## 2.4 数据获取边界

当前版本所有事实数据只通过 ToolCall 获取，不使用 RAG。

| 事实类型 | 数据来源 |
|---|---|
| 店铺信息 | ToolCall |
| 优惠券信息 | ToolCall |
| 营业状态 | ToolCall |
| 距离 ETA | ToolCall |
| 推荐候选 | ToolCall |
| 商户解析 | ToolCall |
| 评论摘要 | 暂不做，或后续通过工具提供结构化摘要 |

LLM 可以做：

- 理解用户问题；
- 提取槽位；
- 恢复上下文；
- 辅助生成工具计划；
- 基于工具结果生成自然表达。

LLM 不能做：

- 编造店铺；
- 编造优惠券；
- 编造营业状态；
- 编造距离；
- 编造价格；
- 编造评分；
- 编造用户偏好。

# 三、六层总体架构

```text
用户文本输入
  ↓
第 1 层：输入接入层
  产出 TurnInput
  ↓
第 2 层：语义理解层
  产出 SemanticFrame
  ↓
第 3 层：上下文与目标解析层
  产出 ResolvedTarget / ClarificationRequest
  ↓
第 4 层：任务决策与工具编排层
  产出 ExecutionPlan
  ↓
第 5 层：工具执行层
  产出 ToolResultSet
  ↓
第 6 层：回答生成与可信校验层
  产出 FinalResponse + StateUpdate
  ↓
更新 SessionState
  ↓
返回用户
```

横切支撑贯穿所有层：

- SessionState；
- GlobalTurnContext；
- TraceLogger；
- MetricsCollector；
- ConfigCenter；
- EvalCaseRunner。

# 四、全局上下文贯穿设计

为了避免各层之间丢信息、重复解析、状态污染，所有层都应围绕同一个 `GlobalTurnContext` 传递。

## 4.1 GlobalTurnContext Schema

```json
{
  "trace_id": "trace_001",
  "turn_id": "turn_001",
  "session_id": "s_001",
  "user_id": "mock_user_001",
  "raw_text": "附近推荐个火锅",
  "normalized_text": "附近推荐个火锅",
  "user_context": {
    "location": {
      "name": "北京邮电大学",
      "lat": 39.9609,
      "lng": 116.3581
    },
    "mock_preferences": {
      "price_sensitive": true,
      "preferred_distance_km": 3
    }
  },
  "session_state_before": {},
  "semantic_frame": null,
  "resolved_target": null,
  "execution_plan": null,
  "tool_result_set": null,
  "evidence_pack": null,
  "answer_plan": null,
  "final_response": null,
  "state_update": null,
  "warnings": [],
  "errors": []
}
```

## 4.2 全局控制原则

1. 每层只补充自己负责的字段，不覆盖上游原始信息。
2. `raw_text` 永远保留，不允许被改写覆盖。
3. `normalized_text` 可用于模型和规则判断，但不能替代原始输入。
4. `trace_id` 必须贯穿所有工具调用和回答校验。
5. `shop_id` 是单店事实调用的唯一强锚点。
6. `unknown`、`empty`、`failed` 必须从工具层一直传到回答层，不允许中途被改写成“没有”。
7. 状态更新只在第 6 层统一规划，不允许中间层随意写 SessionState。
8. LLM 输出必须被 schema 校验，不能直接驱动工具执行。

# 五、第 1 层：输入接入层

## 5.1 层职责

输入接入层负责接收用户文本，并转换为系统统一的 `TurnInput`。

本层不做复杂语义理解，不调用业务工具，不生成最终回答。

## 5.2 模块划分

| 模块 | 作用 |
|---|---|
| TextInputReceiver | 接收用户原始文本 |
| TurnInputBuilder | 构造标准 TurnInput |
| MockUserContextInjector | 注入 mock 用户信息和北京邮电大学位置 |
| BasicInputValidator | 做基础空值和长度校验 |
| RequestTraceInitializer | 初始化 trace_id、turn_id、session_id |

## 5.3 TurnInput Schema

```json
{
  "trace_id": "trace_001",
  "turn_id": "turn_001",
  "session_id": "s_001",
  "user_id": "mock_user_001",
  "input_type": "text",
  "raw_text": "附近推荐个火锅",
  "timestamp": "2026-06-19T10:00:00+09:00",
  "user_context": {
    "location": {
      "name": "北京邮电大学",
      "city": "北京",
      "district": "海淀区",
      "lat": 39.9609,
      "lng": 116.3581
    },
    "mock_preferences": {
      "price_sensitive": true,
      "preferred_distance_km": 3,
      "likes": ["火锅", "烧烤", "咖啡"],
      "dislikes": []
    }
  }
}
```

## 5.4 BasicInputValidator

只做基础判断：

- 空字符串；
- 全空格；
- 超长输入；
- 非文本输入类型；
- 明显非法格式。

更复杂的低信息判断，例如“，”“？？？”“随便”，交给第 2 层 HardGuard。

## 5.5 本层输出

正常输出：

```json
{
  "status": "ok",
  "turn_input": {}
}
```

基础校验失败输出：

```json
{
  "status": "invalid_input",
  "reason": "EMPTY_TEXT",
  "message": "你可以告诉我想找什么店，比如：附近推荐个火锅。"
}
```

# 六、本层实现注意事项

1. 不要在输入层写死业务路由。
2. 不要在输入层调用 `resolve_shop`。
3. 不要在输入层把“海底捞”改写成某个具体门店。
4. 不要在输入层设置 `current_shop`。
5. 所有状态读取放到第 3 层，所有状态写入放到第 6 层。
6. 输入层只负责构造干净、完整、可追踪的 TurnInput。

# 01 场景能力地图与 Query 覆盖

## 1. 场景能力总览

问小团类本地生活助手需要覆盖从简单查询到复杂消费决策的完整链路。能力不应按固定关键词堆叠，而应围绕用户目标、候选商家、工具事实、证据判断和回答生成组织。

核心场景可以分为：

1. 直接回答类
2. 单店查询类
3. 附近推荐类
4. 条件筛选类
5. 场景化推荐类
6. 多店对比类
7. 多轮追问类
8. 工具失败或证据不足类

## 2. 直接回答类

当用户询问系统能力、普通闲聊、通用知识或非本地生活问题时，应走 Direct Answer，而不是强行进入本地生活工具链路。

示例：

- “你能做什么？”
- “怎么使用这个助手？”
- “帮我解释一下 LangGraph。”
- “你是谁？”

处理要求：

- 顶层路由识别为 Direct Answer。
- 不调用本地生活工具。
- 回答简洁自然。
- 如果问题同时包含普通问题和本地生活任务，应识别复合意图，并优先保证本地生活任务可执行。

## 3. 单店查询类

用户围绕某一个商家提问时，系统应解析目标商家，并按用户关注维度调用工具。

示例：

- “海底捞水晶城店怎么样？”
- “山城一锅有券吗？”
- “这家现在营业吗？”
- “这家店离我多远？”
- “这家店适合带老人吗？”

处理要求：

- 必须解析并绑定 shop_id。
- 不允许默认取第一家。
- 根据用户 facet 调用详情、券、营业状态、距离、评价摘要等工具。
- 回答必须说明事实依据和不确定项。

## 4. 附近推荐类

用户表达“附近有什么”“推荐几家”“找一家”等需求时，系统应进入候选发现与推荐链路。

示例：

- “附近有什么好吃的？”
- “推荐几家附近的火锅。”
- “找一家便宜点、评分高、现在营业的店。”
- “附近有没有适合约会的餐厅？”

处理要求：

- 识别品类、位置、距离、预算、评分、优惠、营业状态、场景偏好等约束。
- 生成 CandidateSet。
- 对候选调用必要工具补充证据。
- 根据 EvidencePack 排序和解释。
- 候选不足时说明原因。

## 5. 条件筛选类

用户可能提出多个过滤条件，系统要能拆解、校验并转成工具可执行参数。

示例：

- “找几家人均 100 以下、评分高、离我近的火锅。”
- “附近有没有现在还营业、有团购、别太贵的店？”
- “有没有适合一个人吃、不要排队太久的？”

处理要求：

- 可执行条件进入工具参数。
- 不可直接执行的软偏好进入排序或解释。
- 工具不支持的条件不能假装支持，应在回答中说明依据不足。
- 过滤后无结果时可以放宽部分条件，并说明放宽了什么。

## 6. 场景化推荐类

场景化推荐是问小团类产品的核心体验。用户不会总是说具体指标，而会说“约会”“请客”“带长辈”“朋友聚餐”“一个人吃”。

示例：

- “适合约会的餐厅。”
- “带长辈吃饭哪家稳一点？”
- “适合请客户吃饭的地方。”
- “适合晚上十点以后吃的店。”

处理要求：

- LLM 负责理解场景语义。
- 系统将场景转换成可执行约束和排序维度。
- 例如“约会”可能关注环境、距离、评分、噪音、排队、氛围；“带长辈”可能关注口味稳定、环境安静、交通方便。
- 工具证据不足时必须表达不确定。
- 不允许用简单关键词硬编码替代场景理解。

## 7. 多店对比类

用户比较多个商家时，应进入 comparison 链路。

示例：

- “海底捞和山城一锅哪个好？”
- “这家和第一家比呢？”
- “这三家哪个更适合聚餐？”
- “这几家哪个性价比最高？”

处理要求：

- 明确对比对象。
- 对比对象必须绑定 shop_id。
- 多店数量应有上限。
- 超过上限时应裁剪或追问。
- 对比维度应来自用户目标和工具证据。
- 输出结论时要说明不同选择适合什么用户。

## 8. 多轮追问类

真实用户会大量使用省略表达。系统必须保存上下文并进行指代恢复。

示例：

第一轮：“附近推荐几家火锅。”

第二轮：“便宜一点的呢？”

第三轮：“第一家有券吗？”

第四轮：“这家和海底捞比呢？”

处理要求：

- 保存上一轮 CandidateSet、推荐结果、用户约束和选择上下文。
- 能解析“这家”“它”“第一家”“第二个”“便宜一点”等表达。
- 追问不能被误判为新话题。
- 指代不清时必须澄清。

## 9. 工具失败与证据不足类

系统必须能处理真实环境中的工具失败、空结果和事实不足。

示例：

- 查询商家无结果。
- 优惠券工具返回空。
- 营业状态工具超时。
- 评价摘要缺失。

处理要求：

- 明确区分 empty_result、tool_error、timeout、invalid_argument、insufficient_evidence。
- 不得把失败伪装成成功。
- 可以给出部分回答，但必须说明哪些信息缺失。
- 必要时追问用户是否放宽条件。

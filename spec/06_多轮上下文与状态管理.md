# 06 多轮上下文与状态管理

## 1. 设计目标

本地生活对话天然是多轮的。用户经常先让系统推荐，再围绕候选继续追问。因此系统必须有明确的 SessionState 管理，而不是只处理单轮 query。

目标是支持：

- 多轮指代。
- 候选延续。
- 约束追加。
- 话题切换。
- 澄清恢复。
- 上下文可信清理。

## 2. SessionState 内容

SessionState 建议保存：

- session_id
- user_location
- last_user_goal
- last_semantic_frame
- last_candidate_set
- last_recommendation_list
- last_selected_shop_id
- last_tool_results_summary
- last_evidence_pack_summary
- pending_clarification
- conversation_turns
- updated_at

注意：SessionState 不应保存过多无用原始数据，但必须保留多轮追问所需的候选、选择和约束。

## 3. 多轮指代类型

系统需要解析以下表达：

- “这家”
- “它”
- “这个”
- “第一家”
- “第二个”
- “上面那家”
- “便宜一点的呢”
- “换一家”
- “有券的吗”
- “和海底捞比呢”

## 4. 指代解析规则

指代解析应遵循：

1. 当前轮显式商家优先。
2. 当前轮序号选择优先于历史默认。
3. pending_clarification 优先于普通上下文。
4. 上一轮候选列表可用于“第一家 / 第二家”。
5. “这家”如果无法唯一绑定，必须澄清。
6. 不允许默认绑定到第一家。

## 5. 约束追加

用户追问通常是在上一轮目标基础上追加约束。

示例：

第一轮：“附近推荐几家火锅。”

第二轮：“便宜一点的呢？”

第二轮应理解为：在火锅/附近/上一轮候选或同类候选中，增加价格偏好，而不是新建一个无上下文任务。

常见追加约束：

- 更便宜。
- 更近。
- 评分高一点。
- 要有券。
- 现在营业。
- 适合约会。
- 不要太吵。

## 6. 澄清恢复

当系统进入 pending_clarification 后，下一轮用户可能回答：

- “第一个”
- “第二家”
- “海底捞水晶城店”
- “不是这个，换一个”

要求：

- 优先尝试解析为澄清回复。
- 成功后恢复原始任务继续执行。
- 不应把“第一个”误判成新任务。
- 澄清过期后应清理 pending 状态。

## 7. 话题切换

系统需要识别用户是否换话题。

明显换话题示例：

- 从火锅推荐转为“帮我解释 Java 多线程”。
- 从商家查询转为“你是谁”。
- 从餐厅推荐转为另一个全新地点和品类。

非换话题示例：

- “便宜一点的呢”
- “有券的吗”
- “第一家怎么样”
- “这家和海底捞比呢”

要求：

- 不要用粗糙关键词把“推荐”误判为话题切换。
- 话题切换判断应结合上下文和语义。
- 切换后应清理不相关候选。

## 8. 上下文安全边界

多轮上下文不能导致事实污染。

要求：

- 历史候选过期时应重新查询。
- 历史营业状态、优惠券、距离等实时信息应重新获取或标记可能过期。
- 不能把上一轮工具失败结果当成本轮成功事实。
- 不能跨 session 共享用户上下文。

## 9. 验收场景

必须覆盖以下 E2E：

1. 推荐后问“第一家有券吗”。
2. 推荐后问“便宜一点的呢”。
3. 推荐后问“这家和海底捞比呢”。
4. 多候选澄清后用户回答“第二个”。
5. 没有上一轮候选时用户问“第一家怎么样”，系统应澄清。
6. 用户换话题后上下文不污染新任务。

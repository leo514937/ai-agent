# 07 工程实现约束与反模式

## 1. 总体原则

本项目应优先修主链路、协议、状态、schema、validator、review 和 evidence，而不是通过关键词规则和模板堆叠掩盖问题。

工程实现目标是：

1. 链路清晰。
2. 职责单一。
3. 状态可追踪。
4. 工具可信。
5. 回答有证据。
6. 测试能覆盖真实场景。

## 2. 禁止新增平行链路

禁止为了解决某个 bug 新增一条绕开主图的执行链路。

例如：

- 绕过 LangGraph 直接回答本地生活问题。
- 绕过 ToolCallGateway 调用后端接口。
- 在某个节点里私自做完整推荐流程。
- 新建 legacy fallback 覆盖主链路结果。

正确方式：

- 回到现有 Graph 节点修。
- 回到协议字段修。
- 回到 Planner / Validator / Review 修。
- 回到 EvidencePack 和 Verifier 修。

## 3. 禁止规则堆叠式修 Bug

禁止：

- 针对某个测试句子写 if。
- 针对某个店名写特殊分支。
- 用大量关键词判断复杂语义。
- 用正则替代 LLM 语义理解。
- validator 静默改写 LLM 结果。
- fallback 成为正常路径。

允许：

- 必要 hard guard。
- schema 级约束。
- 数量上限。
- 安全规则。
- 明确可解释的业务边界。

## 4. LLM 使用约束

LLM 可以做：

- 意图识别。
- 槽位抽取。
- 任务规划建议。
- 场景偏好理解。
- 多轮指代理解。
- Review 辅助判断。
- 自然语言表达。

LLM 不可以做：

- 编造工具事实。
- 直接调用未注册工具。
- 生成未校验参数直接执行。
- 在没有 Evidence 的情况下给确定性结论。
- 绕过 AnswerVerifier 输出最终答案。

## 5. Schema 约束

核心协议必须 schema 化。

建议至少包括：

- SemanticFrame
- UserGoal
- CandidateSet
- ToolPlan
- ToolCall
- ToolResult
- EvidencePack
- ReviewResult
- AnswerContract
- VerificationResult

要求：

- 禁止随意 extra 字段。
- 枚举值明确。
- 缺失字段有默认策略。
- 校验失败进入可控错误分支。

## 6. Fallback 约束

Fallback 只能作为异常兜底，不能成为主路径。

Fallback 必须：

- 记录 fallback_reason。
- 记录触发节点。
- 不得覆盖已验证的主路径结果。
- 不得伪造事实。
- 不得隐藏工具失败。

如果某个 fallback 经常触发，应视为主链路缺陷，而不是正常现象。

## 7. Mock 约束

正常运行链路禁止 mock。

测试 fake / stub 必须：

- 只在测试目录或测试配置生效。
- 明确 backend_source。
- 不得被生产配置引用。
- 不得混入端到端真实链路验收。

## 8. 测试要求

修改主链路后，至少应覆盖：

- 单元测试。
- 集成测试。
- 本地生活端到端测试。
- 多轮对话测试。
- 工具失败测试。
- 空结果测试。
- 非本地生活 Direct Answer 测试。

关键样例：

- “你有什么作用？”
- “海底捞水晶城店怎么样？”
- “山城一锅有券吗，环境评价怎么样？”
- “附近有没有适合约会、现在营业、最好有券的火锅？”
- “便宜一点的呢。”
- “第一家有券吗？”
- “这家和海底捞比呢？”
- “这六家哪个好？”

## 9. Trace 要求

每次端到端执行应能看到：

- top_route
- semantic_source
- semantic_frame
- goal_plan
- candidate_set
- tool_plan
- tool_results
- evidence_pack
- review_result
- answer_verification
- fallback_reason
- final_answer

没有 trace 的复杂 bug 不应盲修。

## 10. 提交前检查

每次改动前：

- 先理解现有链路。
- 找到问题发生在哪个节点。
- 判断是语义、规划、工具、证据、review、回答哪一层的问题。

每次改动后：

- 跑相关测试。
- 检查 trace。
- 检查是否引入 mock。
- 检查是否新增规则堆叠。
- 检查最终回答是否有证据支撑。

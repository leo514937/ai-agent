结论先行：`zhida_pro` 更稳定，不是因为它“更聪明”，而是因为它把 **上下文工程** 做成了一个很强的前置约束系统；你现在的项目更像是在运行时不断“补救上下文”。前者是“先把该给模型的上下文准备好”，后者是“先跑起来，再看缺什么”。这两种工程范式，稳定性差很多。

我先直接给你一个对比结论：

| 维度 | `zhida_pro` | 你现在的项目 |
| --- | --- | --- |
| 任务范围 | 更窄，更像“专业版知识查询/搜索问答” | 更泛，带本地生活、追问、工具、动态状态 |
| 上下文策略 | 先配置、再检索、再生成 | 先路由、再尝试检索/工具、失败就澄清或降级 |
| RAG 结构 | 多源召回 + merge + filter + rerank + 长上下文生成 | 检索质量受路由/缺槽/证据门控影响更大 |
| 证据进入模型前的约束 | 很强，且是配置化的 | 有约束，但更多是“运行时 gate” |
| 回答方式 | 模板、提示词、证据、引用都比较固定 | 更依赖当前轮状态，容易 partial / clarify / no_answer |
| 状态一致性 | 单图多 stage，边界更明确 | sequential + langgraph 并存，状态和路径更容易分叉 |

## 为什么 `zhida_pro` 更稳

### 1. 它是在“造上下文”，不是只是在“消费上下文”
`zhida_pro` 的关键不是最后那个生成模型，而是前面的 `RequestConfigLogic` 和整条图的 stage 编排。

它会根据：
- 选了哪些知识库
- 是不是 deep thinking
- 是不是 internal QA
- 当前业务类型是不是 `ZHIDA_PRO_TAB`

动态改：
- 召回数
- 召回源
- prompt
- 模型
- rerank 参数

这在代码里很明显，见 [request_config_logic.go](D:/javacode/hm-dianping/aisp-core-master/pkg/business/zhida_pro/graph/logic/prepare/request_config_logic.go#L61) 和 [stream_chat_zhida_pro_graph.go](D:/javacode/hm-dianping/aisp-core-master/pkg/graph/graph/api/stream_chat_zhida_pro_graph.go#L51)。

这意味着它不是让模型“自己去猜上下文”，而是先把上下文“配置出来”。

### 2. 它的检索链路是完整的，不是单点 RAG
`zhida_pro` 的链路是：

`准备 -> 合法性/安全 -> query merge -> doc router -> agent route -> 多源 recall -> merge -> filter -> rerank -> generate -> answer security -> word security -> response`

看起来很长，但这个长链路的价值在于：
- 每一步都只负责一件事
- 每一步的输入输出都比较固定
- 检索结果会经过多次收敛
- 生成前已经把上下文“清洗”过了

这条链路在 [stream_chat_zhida_pro_graph.go](D:/javacode/hm-dianping/aisp-core-master/pkg/graph/graph/api/stream_chat_zhida_pro_graph.go#L45) 开始就能看到。

换句话说，`zhida_pro` 的 RAG 不是“找回一点文本就喂给模型”，而是“先把证据组织好，再让模型回答”。

### 3. 它的上下文是“结构化业务上下文”，不是“对话文本上下文”
`zhida_pro` 不是单纯依赖聊天历史，它还会在 prepare 阶段装入：
- session info
- chat history
- knowledge base info
- Apollo 配置
- 业务类型
- AB 参数

见 [stream_chat_zhida_pro_graph.go](D:/javacode/hm-dianping/aisp-core-master/pkg/graph/graph/api/stream_chat_zhida_pro_graph.go#L51) 和 [request_config_logic.go](D:/javacode/hm-dianping/aisp-core-master/pkg/business/zhida_pro/graph/logic/prepare/request_config_logic.go#L129)。

所以它上下文不是“聊天记录越多越好”，而是“业务上下文越对，回答越稳”。

## 你现在的项目，为什么会觉得“拿到预期答案很费劲”

### 1. 你的系统更像“高熵任务”，而不是“固定知识问答”
你现在做的是本地生活推荐/查询/工具调用，这种任务天然比 `zhida_pro` 更难：
- 需要地理位置
- 需要门店实体消歧
- 需要动态信息
- 需要工具结果
- 需要静态证据和动态证据拼接
- 还要处理追问、澄清、续聊

这类任务不是“检索到就能答”，而是“上下文是否完整，决定能不能答”。

### 2. 你的路由是在“后置收口”，不是“前置塑形”
你现在的链路里，`load_context -> understand_turn -> route` 之后，很快就会落到：
- `direct_answer`
- `clarify`
- `rag_retrieval`
- `tool_call`
- `rag_plus_tool`

见 [subgraphs.py](D:/javacode/hm-dianping/learning-agent-service/src/learning_agent_service/application/workflow/subgraphs.py#L373)。

问题在于，很多时候这一步已经太早了：
- 还没把 `required_facets` 彻底讲清楚
- 还没把实体锚点、动态信息、静态证据分开
- 还没把“缺的是店名还是位置还是时间”说透

于是后面的 RAG 和 tool 就是在“带着不完整上下文跑”。

### 3. 你的上下文处理是“门控式”的，不是“合同式”的
你当前项目已经有：
- `required_facets`
- `user_need`
- `evidence_quality`
- `partial_grounded`
- `ask_clarification`
- `memory_relevance`

但从实现上看，它更像是运行时 gate，最后在 [compose](D:/javacode/hm-dianping/learning-agent-service/src/learning_agent_service/tools/service.py#L899) 里决定回答模式，而不是从一开始就形成一个强约束的 `AnswerContract`。

所以会出现这种体验：
- 检索到了，但不能放心回答
- 有部分证据，但被 gate 掉了
- 明明只差一个 slot，却变成泛澄清
- 明明是同一家店，却因为实体没对齐而拼错

## 从 context engineering 看，两个项目的本质差异

### `zhida_pro` 的方式
它是：
1. 先识别业务类型
2. 再按业务类型装配上下文
3. 再按业务类型决定召回源和召回强度
4. 再按业务类型决定 prompt 和模型
5. 最后才让模型生成

也就是说，它是在 **build context**。

### 你现在的方式
你更像是：
1. 先接收用户输入
2. 再推断要不要检索/工具/澄清
3. 再看当前上下文够不够
4. 不够就追问或降级
5. 再尝试回答

也就是说，你是在 **repair context**。

这就是为什么 `zhida_pro` 更稳，而你现在的项目更费劲。

## 你现在最该学 `zhida_pro` 的，不是 prompt，而是这三件事

### 1. 把上下文变成“强合同”
不要只说“上下文里有历史、有记忆、有证据”。
要明确到：
- 当前问题需要哪些 `facets`
- 每个 facet 的数据源是什么
- 哪些 facet 必须来自 tool，哪些可以来自 RAG
- 哪些 facet 缺了只能问一次最小澄清

### 2. 把 RAG 从“找文本”升级成“按 facet 取证”
`zhida_pro` 的优势不是它只会检索，而是它知道怎么把检索结果组织成可生成的上下文。

你现在也需要类似的分层：
- 静态事实：RAG
- 动态状态：tool
- 实体锚点：memory / session
- 回答约束：answer contract

### 3. 把回答模式从“有/没有”改成“分级响应”
不要只分：
- 能答
- 不能答

要分：
- `grounded`
- `partial_grounded`
- `ask_clarification`
- `no_answer`

这样系统才不会因为少一个 slot 就“全盘失败”。

如果只从 context engineering 看，你现在的问题不是“模型不行”，而是：

- 检索和工具之间没有完全对齐
- 静态证据和动态证据没有被明确分工
- 回答前缺少一个稳定的 `AnswerContract`

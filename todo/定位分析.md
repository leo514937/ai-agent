# LLM 服务全链路定位分析

## 测试请求

```
message: "推荐附近有什么好吃的"
session_id: "test888"
trace_id: "trace-test5"
```

## 最终结果

> 抱歉，暂时无法处理您的请求，请稍后再试。

总耗时约 **45s**，始终无法返回有效答案。

---

## 完整失败链（6 个断点）

### 断点 1：Semantic Parse — LLM JSON Schema 不合规

**日志**：
```
[LLM_ERROR] node=understanding_subgraph stage=semantic_parse
  attempt=1/2 elapsed_ms=7438
  error_code=LLM_ENUM_OUT_OF_RANGE
```

**第一次调用**（full_prompt，timeout_ms=30000，成功返回）：
DeepSeek 返回的 JSON 中 `ranking_policy` 字段值为 `""`（空字符串），
但 Pydantic schema `SemanticFrame` 期望 `ranking_policy` 是 `dict | None`。

**第二次调用**（repair_prompt，timeout_ms=12000，成功返回）：
DeepSeek 返回的 JSON 中 `preferences` 字段值为 `{"nearby_preferred": true}`（dict），
但 schema 期望 `list[dict]`。

**根因**：`intent_parser.py` 的 `_normalize_semantic_payload()`（第 185-186 行）只对 `isinstance(list)` 做清洗，
`ranking_policy` 和 `preferences` 的类型不对时没有 fallback 处理。
最终语义框架退化到 `diagnostic_rules`，丢失了准确的意图解析。

**影响**：缺失 `candidate_category`、`facets` 等关键字段→搜索没有分类约束。

---

### 断点 2：search_shops — 缺少用户位置

**第一次调用**（planning_subgraph 阶段）：
```
[TOOL_CALL] tool_name=search_shops args={"query": "美食", "location": null, "limit": 3}
[TOOL_RESULT] status=failed
  error_code=SCHEMA_VALIDATION_FAILED
  error_message=Argument 'location' must be a dict
```

**根因**：`user_location` 从未被设置。ChatRequest 未传入 city/位置，
goal_planner 生成了 `candidate_category: "美食"`，但 `location=null`
导致 tool schema 校验失败。

**第二次调用**（execution_review_subgraph 阶段）：
```
[TOOL_CALL] tool_name=search_shops args={"query": "推荐附近有什么好吃的", "location": {}, "limit": 20}
[TOOL_RESULT] status=empty data_size=0
```

**根因**：`location={}` 作为空字典传递，`geocode_location({})` 无法解析任何城市，
`query_shops_by_keyword("推荐附近有什么好吃的")` 只做文本匹配，返回空。

---

### 断点 3：evidence_review LLM — DeepSeek 处理超时

```
[PLAN_LLM_INVOKE] prompt_name=evidence_sufficiency_review
  timeout_ms=8000 max_retries=1
```

**第一次重试**：attempt=1/2，8000ms 超时
**第二次重试**：attempt=2/2，8000ms 超时

```
[EVIDENCE_REVIEW_LLM_FAILED] error_code=LLM_TIMEOUT
  error_message=LLM call exceeded 8000 ms
```

**根因**：evidence_sufficiency_review 的 prompt 包含：
- 完整的 goal_plan（目标、分类、约束）
- evidence_pack（facets, tool_results, grounding_status）
- tool_results（25 个工具调用结果）
- candidate_review

这是一个大型 prompt，DeepSeek API 响应时间超过 8000ms。
8000ms 超时后 fallback 到 deterministic_review，结果为
`missing_facets: ['distance']`。

**影响**：没有 LLM 审查来判断"空的 distance 是因为缺少位置，可以 degrade 安全回答"，
而是强行要求 replan → 再次尝试获取 distance → 陷入死循环。

---

### 断点 4：decision_planner — 空候选集 → unsupported

```
[DECISION_PLANNER_RESULT] decision_type=unsupported
  candidate_count_before_decision=0
  candidate_count_after_decision=0
  caveats=["搜索店铺返回空结果，无法获取任何候选店铺",
           "必需因素 distance 无法获取，无法完成推荐"]
```

**根因**：因断点 2 搜索空结果，加上断点 3 evidence_review 未通过，
decision_planner 在空候选集上运行，只能返回 `unsupported`。

---

### 断点 5：decision_review — insufficient → REPLAN_EVIDENCE

```
[NODE_EVENT] node=decision_review
  status=insufficient
  next_action=REPLAN_EVIDENCE
  reason=evidence_review_action:replan_missing_facets
```

**根因**：decision_planner 报告 unsupported + missing_facets，
decision_review 标记为 insufficient 要求重试。
但系统没有剩余预算或位置信息来真正改进结果。

---

### 断点 6：answer_generate — 确定性回退

```
[NODE_EVENT] node=answer_generate
  answer_source=deterministic_rewrite
  fallback_reason=LLM_ENUM_OUT_OF_RANGE
  fallback_used=true
```

**根因**：answer_generate 的 LLM verbalizer 因为断点 1 的 `fallback_reason`
（源头 semantic_parse 的 LLM_ENUM_OUT_OF_RANGE 被传播）而无法使用，
跌到 `deterministic_rewrite` → 输出"抱歉"模板。

---

## 根因汇总

| # | 根因 | 影响阶段 | 类型 |
|---|------|----------|------|
| 1 | **用户位置缺失**：ChatRequest 无 city/location 参数，session 也无位置上下文 | planning→search_shops | 数据缺失 |
| 2 | **search_shops 未传位置**：goal_planner 生成 plan 时不携带 `user_location` → `location: null` | planning_subgraph | 数据流断裂 |
| 3 | **LLM JSON 输出不合 schema**：DeepSeek 返回的 `ranking_policy`/`preferences` 类型不符 Pydantic schema | understanding_subgraph | LLM 合规性 |
| 4 | **evidence_review LLM 超时**：8000ms 不够，DeepSeek 处理大 prompt 超过 8s | execution_review | 性能/超时 |
| 5 | **empty location 返回空结果**：`location={}` 的 geocode 无法解析城市，varchar 文本搜索无匹配 | execution_review | 搜索能力 |
| 6 | **LLM_ENUM_OUT_OF_RANGE 传播到 answer**：从 semantic_parse 传播到 answer_generate 的 fallback 路径 | answer_generate | 错误传播 |

---

## 最关键瓶颈

**位置数据缺失是所有失败的起点。**

- 一旦 `user_location` 被正确地传入并设置到 session_state，
  `search_shops` 就能搜索到对应城市的店铺，
  `distance` facet 也能被计算，
  evidence_review 和 decision_planner 都有数据可用。

- 超时问题（30000ms 已够 semantic_parse，15000ms 够 goal/decision_planner）
  基本已解决。evidence_review 的 8000ms 超时属于次要瓶颈，
  在位置数据就绪后决策树的分支会更简单，prompt 更小，有望缩短 DeepSeek 响应时间。

---

## 建议修复顺序

1. **P0** 修复数据入口：让 ChatRequest 携带 `city` 并设入 `user_location`
2. **P0** 修复 search_shops 空 location 语义：当 location={} 不应查全库，应返回需要位置信息的错误
3. **P1** 增强 intent_parser.py 的 `_normalize_semantic_payload`：对 `ranking_policy`/`preferences` 做类型容错
4. **P2** evidence_review timeout 提到 20000ms 或增加 retry 次数

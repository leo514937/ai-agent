# 附近推荐缺位置问题定位与修复结果

## 结论

这个问题已经完成主修复。

当前系统对“推荐附近有什么好吃的”这类请求，已经具备下面的行为：

- 有位置时：位置可以从请求入口进入 `user_context` / `user_location`，推荐链路可继续执行。
- 缺位置时：会优先澄清，不再继续无效地跑 `Plan -> Execute -> Review`。
- 工具边界：`search_shops(location=None/{})` 不再静默返回空结果，而是返回 `LOCATION_REQUIRED`。
- Review 阶段：遇到 `LOCATION_REQUIRED` 会收敛到 `CLARIFY`，不再反复 `REPLAN_EVIDENCE`。
- 回答阶段：上游 semantic 诊断错误不会再污染最终澄清文案。

## 原问题拆解

### 1. 契约 bug

- “附近推荐”“距离排序”“多久到”本质依赖位置，但链路里没有把它们声明成强前置条件。
- planning 在缺位置时仍继续规划工具调用。
- review 在缺位置时仍把问题当成可重试证据不足。

这部分是主因。

### 2. 实现 bug

- 请求入口没有稳定把 `client_context.location` 提升到图状态。
- `search_shops` 对 `location=None` / `{}` 没有 typed failure。
- semantic payload 对 `ranking_policy=""`、`preferences=dict/list[str]` 的兼容不足。

### 3. 次要性能问题

- 缺位置时继续跑工具和 review，会制造 45s 左右的无效耗时。
- `REPLAN_EVIDENCE` 在确定性缺参场景没有收益。

## 采取的修复方案

### 1. 位置入口统一

复用现有 `client_context`，没有新增新的顶层请求字段。

当前约定：

```json
{
  "client_context": {
    "location": {
      "location_name": "北京邮电大学",
      "lat": 39.9609,
      "lng": 116.3581,
      "city": "北京"
    }
  }
}
```

入口会把这份位置同时写入：

- `user_context`
- `user_location`

### 2. planning 前置条件收紧

在 `planning_subgraph` 中，对以下信号会判定为位置必需：

- `missing_slot_type` 为位置缺失
- query 含“附近 / 周边 / 距离 / 多久到”
- semantic `nearby_preferred`
- facets 含 `nearby / distance / travel_time / business_area`

如果缺位置，会直接生成 clarification，不再继续 tool planning。

### 3. search_shops typed failure

对 nearby-like 查询：

- `location=None`
- `location={}`

不再视为普通搜索参数，而是返回：

- `result_status=failed`
- `error_code=LOCATION_REQUIRED`

### 4. review 不再无效 replan

`evidence_review` 现在会识别：

- `tool error_code == LOCATION_REQUIRED`

然后直接输出：

- `need_user_location`
- clarification

不再继续 `REPLAN_EVIDENCE`。

### 5. semantic normalize

已补齐：

- `ranking_policy="" | [] | {} -> None`
- `preferences=dict -> list[dict]`
- `preferences=list[str] -> list[dict]`
- `preferences=None -> []`

同时 prompt 示例也已修正。

### 6. answer fallback 污染隔离

clarification 路径下，会过滤纯诊断型 fallback reason，例如：

- `LLM_ENUM_OUT_OF_RANGE`
- `LLM_JSON_PARSE_ERROR`
- `semantic_frame_validation_failed`

所以最终用户看到的是“请提供位置 / 城市 / 商圈”，而不是泛化道歉。

## 当前代码结论

### 已解决

- 缺位置时不再空转完整主链
- 附近推荐会优先澄清
- 空位置不会再被当成 empty result
- review 不再对确定性缺参反复重试
- semantic 脏输出不会直接打穿主流程

### 已部分打通，但仍需真实接口验证

- 有位置时位置状态已经能进入主链
- 测试层面“有位置继续推荐”是通过的
- 但“真实客户端发起 `ChatRequest + client_context.location`，最终稳定把距离/ETA说给用户”还没有做单独的接口级验实

所以目前更准确的表述是：

“位置前置条件”和“位置状态传递”已经修好；“真实线上式距离回复”从代码和测试上基本打通，但还需要一次真实请求验证。

# LLM 服务全链路定位分析

## 测试请求

```
message: "推荐附近有什么好吃的"
session_id: "test888"
trace_id: "trace-test5"
```

## 最终结果

> 抱歉，暂时无法处理您的请求，请稍后再试。

总耗时约 **45s**，始终无法返回有效答案。

---

## 完整失败链（6 个断点）

### 断点 1：Semantic Parse — LLM JSON Schema 不合规

**日志**：
```
[LLM_ERROR] node=understanding_subgraph stage=semantic_parse
  attempt=1/2 elapsed_ms=7438
  error_code=LLM_ENUM_OUT_OF_RANGE
```

**第一次调用**（full_prompt，timeout_ms=30000，成功返回）：
DeepSeek 返回的 JSON 中 `ranking_policy` 字段值为 `""`（空字符串），
但 Pydantic schema `SemanticFrame` 期望 `ranking_policy` 是 `dict | None`。

**第二次调用**（repair_prompt，timeout_ms=12000，成功返回）：
DeepSeek 返回的 JSON 中 `preferences` 字段值为 `{"nearby_preferred": true}`（dict），
但 schema 期望 `list[dict]`。

**根因**：`intent_parser.py` 的 `_normalize_semantic_payload()`（第 185-186 行）只对 `isinstance(list)` 做清洗，
`ranking_policy` 和 `preferences` 的类型不对时没有 fallback 处理。
最终语义框架退化到 `diagnostic_rules`，丢失了准确的意图解析。

**影响**：缺失 `candidate_category`、`facets` 等关键字段→搜索没有分类约束。

---

### 断点 2：search_shops — 缺少用户位置

**第一次调用**（planning_subgraph 阶段）：
```
[TOOL_CALL] tool_name=search_shops args={"query": "美食", "location": null, "limit": 3}
[TOOL_RESULT] status=failed
  error_code=SCHEMA_VALIDATION_FAILED
  error_message=Argument 'location' must be a dict
```

**根因**：`user_location` 从未被设置。ChatRequest 未传入 city/位置，
goal_planner 生成了 `candidate_category: "美食"`，但 `location=null`
导致 tool schema 校验失败。

**第二次调用**（execution_review_subgraph 阶段）：
```
[TOOL_CALL] tool_name=search_shops args={"query": "推荐附近有什么好吃的", "location": {}, "limit": 20}
[TOOL_RESULT] status=empty data_size=0
```

**根因**：`location={}` 作为空字典传递，`geocode_location({})` 无法解析任何城市，
`query_shops_by_keyword("推荐附近有什么好吃的")` 只做文本匹配，返回空。

---

### 断点 3：evidence_review LLM — DeepSeek 处理超时

```
[PLAN_LLM_INVOKE] prompt_name=evidence_sufficiency_review
  timeout_ms=8000 max_retries=1
```

**第一次重试**：attempt=1/2，8000ms 超时
**第二次重试**：attempt=2/2，8000ms 超时

```
[EVIDENCE_REVIEW_LLM_FAILED] error_code=LLM_TIMEOUT
  error_message=LLM call exceeded 8000 ms
```

**根因**：evidence_sufficiency_review 的 prompt 包含：
- 完整的 goal_plan（目标、分类、约束）
- evidence_pack（facets, tool_results, grounding_status）
- tool_results（25 个工具调用结果）
- candidate_review

这是一个大型 prompt，DeepSeek API 响应时间超过 8000ms。
8000ms 超时后 fallback 到 deterministic_review，结果为
`missing_facets: ['distance']`。

**影响**：没有 LLM 审查来判断"空的 distance 是因为缺少位置，可以 degrade 安全回答"，
而是强行要求 replan → 再次尝试获取 distance → 陷入死循环。

---

### 断点 4：decision_planner — 空候选集 → unsupported

```
[DECISION_PLANNER_RESULT] decision_type=unsupported
  candidate_count_before_decision=0
  candidate_count_after_decision=0
  caveats=["搜索店铺返回空结果，无法获取任何候选店铺",
           "必需因素 distance 无法获取，无法完成推荐"]
```

**根因**：因断点 2 搜索空结果，加上断点 3 evidence_review 未通过，
decision_planner 在空候选集上运行，只能返回 `unsupported`。

---

### 断点 5：decision_review — insufficient → REPLAN_EVIDENCE

```
[NODE_EVENT] node=decision_review
  status=insufficient
  next_action=REPLAN_EVIDENCE
  reason=evidence_review_action:replan_missing_facets
```

**根因**：decision_planner 报告 unsupported + missing_facets，
decision_review 标记为 insufficient 要求重试。
但系统没有剩余预算或位置信息来真正改进结果。

---

### 断点 6：answer_generate — 确定性回退

```
[NODE_EVENT] node=answer_generate
  answer_source=deterministic_rewrite
  fallback_reason=LLM_ENUM_OUT_OF_RANGE
  fallback_used=true
```

**根因**：answer_generate 的 LLM verbalizer 因为断点 1 的 `fallback_reason`
（源头 semantic_parse 的 LLM_ENUM_OUT_OF_RANGE 被传播）而无法使用，
跌到 `deterministic_rewrite` → 输出"抱歉"模板。

---

## 根因汇总

| # | 根因 | 影响阶段 | 类型 |
|---|------|----------|------|
| 1 | **用户位置缺失**：ChatRequest 无 city/location 参数，session 也无位置上下文 | planning→search_shops | 数据缺失 |
| 2 | **search_shops 未传位置**：goal_planner 生成 plan 时不携带 `user_location` → `location: null` | planning_subgraph | 数据流断裂 |
| 3 | **LLM JSON 输出不合 schema**：DeepSeek 返回的 `ranking_policy`/`preferences` 类型不符 Pydantic schema | understanding_subgraph | LLM 合规性 |
| 4 | **evidence_review LLM 超时**：8000ms 不够，DeepSeek 处理大 prompt 超过 8s | execution_review | 性能/超时 |
| 5 | **empty location 返回空结果**：`location={}` 的 geocode 无法解析城市，varchar 文本搜索无匹配 | execution_review | 搜索能力 |
| 6 | **LLM_ENUM_OUT_OF_RANGE 传播到 answer**：从 semantic_parse 传播到 answer_generate 的 fallback 路径 | answer_generate | 错误传播 |

---

## 最关键瓶颈

**位置数据缺失是所有失败的起点。**

- 一旦 `user_location` 被正确地传入并设置到 session_state，
  `search_shops` 就能搜索到对应城市的店铺，
  `distance` facet 也能被计算，
  evidence_review 和 decision_planner 都有数据可用。

- 超时问题（30000ms 已够 semantic_parse，15000ms 够 goal/decision_planner）
  基本已解决。evidence_review 的 8000ms 超时属于次要瓶颈，
  在位置数据就绪后决策树的分支会更简单，prompt 更小，有望缩短 DeepSeek 响应时间。

---

## 建议修复顺序

1. **P0** 修复数据入口：让 ChatRequest 携带 `city` 并设入 `user_location`
2. **P0** 修复 search_shops 空 location 语义：当 location={} 不应查全库，应返回需要位置信息的错误
3. **P1** 增强 intent_parser.py 的 `_normalize_semantic_payload`：对 `ranking_policy`/`preferences` 做类型容错
4. **P2** evidence_review timeout 提到 20000ms 或增加 retry 次数

---

# 推荐结果重复门店定位分析

## 问题表象

用户输入"推荐火锅"或"海底捞附近"，推荐列表中出现多个同品牌/同系列门店，
给人"重复"的感觉。例如搜索"海底捞"可能返回：海底捞(牡丹园店)、海底捞火锅(水晶城购物中心店)、
海底捞(A店)、海底捞(B店)、海底捞(C店) 共 6 家，全部被纳入候选并参与排名。

## 核心结论

**不是数据库有店名重复，而是推荐链路的多样性/去重逻辑没收紧。**

数据库 `tb_shop` 中 49 家店铺（hmdp 22 家 + seed 27 家）的店名全部唯一，
没有精确或近似重复。问题出在以下数据流环节：

---

## 全链路逐环节分析

### 环节 1：search_shops → SQL LIKE 召回（无品牌级裁剪）

**代码**：`db_client.py:query_shops_by_keyword`

```sql
WHERE s.name LIKE %s OR s.address LIKE %s OR t.name LIKE %s
```

`SEARCH_LIMIT = 20`。如果用户搜"海底捞"，`LIKE '%海底捞%'` 会返回全部 6 家海底捞门店。
SQL 层面只做 `ORDER BY score DESC, sold DESC`，**没有限制同品牌最多返回 N 家**。

```python
# db_tools.py:search_shops
matched.sort(key=lambda s: s.get("rating", 0), reverse=True)
# ... 距离 enrichment ...
if limit is not None and limit > 0:
    matched = matched[:limit]       # 只截取前 limit 条，不存在去重
```

**影响**：原始搜索结果中同品牌门店全部进入后续链路。

---

### 环节 2：证据规划器（evidence_planner）— dedup_key = shop_id:facet

**代码**：`evidence_planner.py:plan_evidence`

```python
seen: set[str] = set()
for candidate in candidates:
    shop_id = str(candidate.shop_id or "").strip()
    for facet in all_facets:
        dk = _dedup_key(shop_id, facet)   # f"{shop_id}:{facet}"
        if dk in seen:
            continue
        seen.add(dk)
```

这里的去重键是 `shop_id + facet`，作用是**防止同一 shop_id 的同一 facet 被重复执行工具调用**。
完全不处理"不同 shop_id 但名字相似"的情况。

**影响**：不同店 ID 的不同海底捞门店各自独立通过，不会被合并。

---

### 环节 3：推荐证据构建（_build_recommendation_evidence）— 有身份去重但粒度是精确匹配

**代码**：`evidence_builder.py:_candidate_identity_key`

```python
def _candidate_identity_key(candidate) -> tuple:
    # 优先级：
    # 1. (name, address)         —— 名字+地址完全相同
    # 2. (name, branch)          —— 名字+分店名相同
    # 3. (name, lat, lng)        —— 名字+坐标相同
    # 4. (name,)                 —— 仅名字相同（作为 fallback）
    # 5. (shop_id,)              —— 仅 ID 相同
```

**代码**：`evidence_builder.py:_build_recommendation_evidence`

```python
# 第一轮去重：search_result + recommendation_candidates 合并
seen_candidate_keys: set = set()
for candidate in (search_result_candidates or []) + (recommendation_candidates or []):
    identity_key = _candidate_identity_key(candidate_dict)
    if identity_key in seen_candidate_keys:
        continue
    seen_candidate_keys.add(identity_key)
    merged_candidates.append(candidate)

# 第二轮去重：放入 candidates_by_shop_id
seen_candidate_identities: set = set()
for raw_candidate in recommendation_candidates:
    identity_key = _candidate_identity_key(candidate)
    if identity_key in seen_candidate_identities:
        continue
    seen_candidate_identities.add(identity_key)
    shop_id = candidate.get("shop_id")
    if shop_id:
        candidates_by_shop_id[shop_id] = candidate
```

**现状分析**：

| 场景 | 去重键示例 | 是否去重 | 说明 |
|------|-----------|---------|------|
| 海底捞(A店) vs 海底捞(B店) | `("name_address", "海底捞(A店)", "中关村")` vs `("name_address", "海底捞(B店)", "五道口")` | ❌ | 名字和地址都不同 |
| 海底捞(牡丹园店) vs 海底捞火锅(水晶城购物中心店) | `("name_address", "海底捞(牡丹园店)", "花园东路")` vs `("name_address", "海底捞火锅(水晶城购物中心店)", "远大路")` | ❌ | 名字本身就不同 |
| 同一店铺两次出现（重复ID） | `("shop_id", "900007")` 相同 | ✅ | 精确去重有效 |

**结论**：身份去重只能防"同一家店因不同查询路径被重复加入"，
不能防"不同门店但属于同一品牌"。

---

### 环节 4：推荐候选排名（rank_candidates）— 无品牌聚合

**代码**：`ranking_policy.py:rank_candidates`

```python
surviving.sort(key=lambda item: (
    -float(item.get("total_score", 0.0) or 0.0),   # 综合分
    -float(item.get("rating", 0.0) or 0.0),         # 评分
    float(item.get("distance_km", 9999.0) or 9999.0),  # 距离
    str(item.get("shop_id", "")),                    # 店 ID 兜底
))
return surviving[:RECOMMENDATION_FINAL_TOP_K]  # 取前 3
```

`RECOMMENDATION_FINAL_TOP_K = 3`，最终只取前 3 名展示给用户。

**典型场景**：用户搜"推荐火锅"，按综合分排名，前 3 名可能是：

```
1. 海底捞(牡丹园店)   总分 92
2. 海底捞(A店)        总分 88
3. 海底捞(B店)        总分 85
---
4. 川味轩(知春路店)    总分 82   ← 被裁剪
```

**没有对 shop_name 做前缀聚合**，场景相似、评分相近的同品牌门店全部进入 top 3，
用户看到的就是"3 个海底捞"。

### 环节 5：答案合成（RecommendationComposer）— 展示层只按序输出

**代码**：`answer/composers/deterministic.py`

```python
def _format_ranked_shop_lines(items, limit=3):
    lines = []
    for index, item in enumerate(items[:limit], start=1):
        name = _shop_name(item) or f"候选{index}"
        facets = _format_facets(item)
        lines.append(f"第{index}位 {name}：{'；'.join(facets)}")
    return lines

def _unique_names(items, limit=None):    # 仅在 metadata 中使用
    names = []
    for item in items:
        name = _shop_name(item)
        if name and name not in names:
            names.append(name)
    return names
```

```python
class RecommendationComposer:
    def compose(self, plan, ...):
        ranking_items = _extract_ordered_items(plan, keys=("overall_ranking", ...))
        ranking_lines = _format_ranked_shop_lines(ranking_items, limit=3)
        # ...
        metadata["ranking_order"] = _unique_names(ranking_items, limit=5)
```

`_unique_names` 只在 `metadata` 中使用，不影响最终输出的文本内容。
`_format_ranked_shop_lines` 是 **直接按排名顺序输出**，不做品牌聚合。

**影响**：展示层直接输出 top 3，没有机会对重复品牌做压缩。

## 问题根因总结

| # | 根因 | 所在环节 | 当前行为 | 应该做的 |
|---|------|---------|---------|---------|
| 1 | SQL LIKE 无品牌级限制 | search_shops | `LIKE '%海底捞%'` 返回全部 6 家 | 按品牌/名称前缀分组，同品牌最多取 top 2 |
| 2 | 候选去重键粒度是"精确店名+地址" | evidence_builder | `_candidate_identity_key` 用 `(name, address)` | 无 fix → 这层粒度是对的，不能把不同店当一家 |
| 3 | 排名公式无品牌聚合 | ranking_policy | `total_score → rating → distance → shop_id` | 排名后加品牌级多样裁剪，同品牌最多保留 1 家 |
| 4 | `RECOMMENDATION_FINAL_TOP_K=3` 固定取前 3 | ranking_policy | 不管品牌多样性，直接取高分前 3 | 先保证多样性再截断，或裁剪后补位 |
| 5 | 展示层直接按排名输出 | answer composer | `第1位...第2位...第3位...` | 展示前做品牌聚合，多条同品牌合并为 1 条 |
| 6 | 推荐续问直接复用现存列表 | response_subgraph | `last_recommendation_list[:3]` | 续问应触发新搜索或至少对旧列表做多样性重排 |

## 建议修复方案

### 方案 A：排名后裁剪（推荐，改动最小）

在 `ranking_policy.py:rank_candidates` 的 `return` 之前加入品牌级多样性裁剪：

```python
def _dedup_by_brand(candidates: list, max_per_brand: int = 1) -> list:
    """同品牌最多保留 max_per_brand 家，按排名保留最优的。"""
    brand_count: dict[str, int] = {}
    result: list = []
    for item in candidates:
        brand = _extract_brand(item.get("shop_name", ""))
        if brand_count.get(brand, 0) >= max_per_brand:
            continue
        brand_count[brand] = brand_count.get(brand, 0) + 1
        result.append(item)
    return result
```

**优点**：改动集中、影响范围小、不破坏现有排名逻辑
**缺点**：不能补位（被裁剪的品牌不释放名额给其他候选）

### 方案 B：排名后裁剪 + 补位（推荐）

在方案 A 基础上，从剩余候选（ranked_snapshot 之后未进入 top 3 的）中按排名补足到 3 家：

```python
ranked = rank_candidates(candidates, preferences)
# 第一遍：提取多样化的 top 3
diverse = _dedup_by_brand(ranked, max_per_brand=1)
# 如果不够 3 家，从剩余候选中补位
if len(diverse) < 3:
    remainder = [item for item in ranked if item["shop_id"] not in {d["shop_id"] for d in diverse}]
    for item in remainder:
        if len(diverse) >= 3:
            break
        diverse.append(item)
```

### 方案 C：续问触发新搜索（独立修复）

在 `response_subgraph.py:_is_recommendation_refine_follow_up` 为 True 时，
不走 `last_recommendation_list` 的静态展示，而是触发一次携带新约束的 `search_shops` 调用。

**优点**：真正按新条件搜索（如更便宜的价格区间），结果更匹配
**代价**：需要改动 graph 流程，从一个短路径变成完整搜索路径

## 修复优先级

| 方案 | 优先级 | 估计工作量 | 影响范围 |
|------|--------|-----------|---------|
| A：排名后同品牌裁剪 | P1 | ~10 行 | 仅 `ranking_policy.py` |
| B：裁剪 + 补位 | P1 | ~20 行 | 仅 `ranking_policy.py` |
| C：续问触发新搜索 | P2 | 中等 | response_subgraph + planning |

**建议先做方案 B**，P1 优先级，改动集中且收益最明显。

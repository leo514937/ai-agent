# 06_回答生成可信校验与横切验收

# 一、层职责

回答生成与可信校验层负责基于工具结果生成最终回答，并保证回答：

- 自然；
- 准确；
- 不编造；
- 不串店；
- 不答非所问；
- 明确说明未知信息；
- 推荐理由有工具来源；
- 工具失败不伪装成无结果。

核心链路：

```text
ToolResultSet
  ↓
EvidenceBuilder
  ↓
FactSourceBinder
  ↓
RecommendationResultBuilder / ComparisonMatrixBuilder
  ↓
AnswerPlanBuilder
  ↓
AnswerGenerator
  ↓
AnswerVerifier
  ↓
FinalResponseBuilder
  ↓
StateUpdatePlanner
```

# 二、模块划分

| 模块 | 作用 |
|---|---|
| EvidenceBuilder | 构造证据包 |
| FactSourceBinder | 绑定事实来源 |
| RecommendationResultBuilder | 构造推荐结果 |
| ComparisonMatrixBuilder | 构造对比矩阵 |
| ComparisonAnalyzer | 结构化对比分析 |
| AnswerPlanBuilder | 生成回答计划 |
| AnswerGenerator | LLM 自然表达 |
| MissingInfoHandler | 处理 unknown、失败、熔断 |
| AnswerVerifier | 校验最终回答 |
| FinalResponseBuilder | 输出最终响应 |
| StateUpdatePlanner | 规划状态更新 |

# 三、EvidencePack

EvidencePack 是回答事实来源的唯一依据。

```json
{
  "shops": {
    "shop_001": {
      "detail": {
        "source": "get_shop_detail",
        "status": "ok",
        "data": {}
      },
      "coupon": {
        "source": "get_coupon_list",
        "status": "ok",
        "data": []
      },
      "open_status": {
        "source": "check_open_status",
        "status": "unknown"
      },
      "distance": {
        "source": "get_distance_eta",
        "status": "ok",
        "distance_km": 1.2,
        "eta_minutes": 15
      }
    }
  },
  "tool_failures": [],
  "degraded": false
}
```

规则：

1. 没有来源的事实不能进入回答。
2. `unknown` 必须保留到 AnswerPlan。
3. `failed` 不能被包装成“没有”。
4. `empty` 可以表达“工具成功确认暂无”。
5. 每个事实必须绑定 `shop_id`。

# 四、FactSourceBinder

事实与来源映射：

| 事实 | 来源 |
|---|---|
| 店名 | resolve_shop / search_shops / get_shop_detail |
| 地址 | get_shop_detail |
| 评分 | get_shop_detail |
| 人均 | get_shop_detail |
| 优惠券 | get_coupon_list |
| 营业状态 | check_open_status |
| 距离 ETA | get_distance_eta |
| 推荐排序 | RankingPolicy |
| 对比结论 | ComparisonAnalyzer |

没有来源的事实不能进入 AnswerPlan。

# 五、推荐结果构造

```json
{
  "recommendation_type": "nearby_shop_recommendation",
  "based_on_location": "北京邮电大学",
  "items": [
    {
      "shop_id": "shop_001",
      "shop_name": "山城一锅",
      "rank": 1,
      "reason_codes": ["nearby", "open_now", "has_coupon"],
      "known_facts": {
        "distance": "1.2km",
        "eta": "15分钟",
        "open_status": "营业中",
        "coupon_summary": "有可用券"
      },
      "unknown_facts": []
    }
  ]
}
```

规则：

1. 推荐理由必须来自 `reason_codes`。
2. `reason_codes` 必须能追溯到工具字段或 RankingPolicy。
3. unknown 信息不能包装成推荐理由。
4. LLM 只能解释系统排序，不负责重新排序。

# 六、ComparisonMatrixBuilder

多店对比不能直接把原始 ToolResult 交给 LLM。

先构造 ComparisonMatrix：

```json
{
  "comparison_matrix": [
    {
      "shop_id": "shop_001",
      "shop_name": "海底捞",
      "distance": {
        "status": "ok",
        "distance_km": 1.2,
        "eta_minutes": 15,
        "source": "get_distance_eta"
      },
      "open_status": {
        "status": "ok",
        "value": "open",
        "source": "check_open_status"
      },
      "coupon": {
        "status": "ok",
        "value": "has_coupon",
        "source": "get_coupon_list"
      },
      "price": {
        "status": "ok",
        "avg_price": 110,
        "source": "get_shop_detail"
      }
    },
    {
      "shop_id": "shop_002",
      "shop_name": "山城一锅",
      "distance": {
        "status": "ok",
        "distance_km": 0.8,
        "eta_minutes": 10,
        "source": "get_distance_eta"
      },
      "open_status": {
        "status": "unknown",
        "value": null,
        "source": "check_open_status"
      },
      "coupon": {
        "status": "unknown",
        "value": null,
        "source": "get_coupon_list"
      },
      "price": {
        "status": "ok",
        "avg_price": 78,
        "source": "get_shop_detail"
      }
    }
  ]
}
```

状态语义：

| status | 能否确定性比较 |
|---|---|
| ok | 可以 |
| empty | 可以，例如确认暂无券 |
| unknown | 不可以 |
| failed | 不可以 |
| circuit_open | 不可以 |

示例：

- A 店券 `ok`，查到有券；
- B 店券 `unknown`，工具超时。

只能说：

```text
A 店查到有券，B 店优惠信息暂时未知。
```

不能说：

```text
A 店比 B 店更有优惠。
```

除非 B 店状态是 `empty`，即工具成功确认暂无券。

# 七、ComparisonAnalyzer

ComparisonAnalyzer 在 LLM 之前完成结构化分析。

输出：

```json
{
  "dimension_winners": {
    "distance": "shop_002",
    "price": "shop_002",
    "coupon": "shop_001",
    "open_status": ["shop_001", "shop_003"]
  },
  "overall_ranking": [
    {
      "shop_id": "shop_001",
      "rank": 1,
      "reason_codes": ["open_now", "has_coupon", "high_rating"]
    },
    {
      "shop_id": "shop_002",
      "rank": 2,
      "reason_codes": ["nearest", "lower_price", "coupon_unknown"]
    }
  ],
  "uncertainty_notes": [
    "shop_002 的优惠信息未知，不能确认是否有券"
  ],
  "conclusion_confidence": "medium"
}
```

原则：

1. 不让 LLM 自由比较原始工具结果。
2. 先由系统计算维度赢家和综合排序。
3. unknown 维度不做确定性判断。
4. 工具失败时降低结论置信度。
5. 生成可追溯的 `reason_codes`。
6. AnswerGenerator 只能基于 ComparisonAnalyzer 和 AnswerPlan 输出自然语言。

# 八、AnswerPlanBuilder

AnswerPlan 是 LLM 生成自然语言前的结构化约束。

```json
{
  "answer_type": "recommendation",
  "main_message": "我按北京邮电大学附近、火锅、现在营业、优先有券来筛选。",
  "items_to_mention": [
    {
      "shop_id": "shop_001",
      "shop_name": "山城一锅",
      "rank": 1,
      "facts": [
        {
          "text": "距离约 1.2km",
          "source": "get_distance_eta"
        },
        {
          "text": "当前营业中",
          "source": "check_open_status"
        },
        {
          "text": "查到可用优惠券",
          "source": "get_coupon_list"
        }
      ]
    }
  ],
  "must_mention_unknowns": [
    "第二家优惠信息暂时无法确认"
  ],
  "forbidden_claims": [
    "不能说优惠未知的店没有券",
    "不能说营业未知的店正在营业"
  ]
}
```

规则：

1. AnswerGenerator 只能根据 AnswerPlan 写回答。
2. AnswerPlan 中没有的事实不能写。
3. `forbidden_claims` 必须传给 AnswerGenerator。
4. 用户问了多个 facet，AnswerPlan 必须逐个覆盖。
5. required facet 获取失败时，要明确说明无法确认。

# 九、AnswerGenerator

LLM 可以做：

- 组织语言；
- 解释推荐理由；
- 让表达更像真实助手；
- 总结对比结论；
- 提示下一步。

LLM 不能做：

- 新增店铺事实；
- 新增优惠事实；
- 新增营业状态；
- 新增距离；
- 新增评分；
- 把 unknown 说成没有；
- 把工具失败说成无结果；
- 改变系统排序。

# 十、MissingInfoHandler

标准话术：

| 场景 | 话术 |
|---|---|
| 优惠未知 | 优惠信息暂时没有查到，所以我不能确认它现在是否有券。 |
| 营业未知 | 营业状态暂时无法确认，我不能确定它现在是否营业。 |
| 距离未知 | 距离和预计到达时间暂时获取失败，我先不估算距离。 |
| 搜索失败 | 附近商户暂时搜索失败，我不能直接编推荐结果。 |
| 商户未找到 | 我暂时没有找到与你输入匹配的商户，可以换个更完整的店名试试。 |
| 工具熔断 | 这个信息服务暂时不可用，我不能确认该项结果。 |

# 十一、AnswerVerifier 拆分设计

AnswerVerifier 不应完全依赖 LLM，应拆成三层。

## 11.1 规则校验

适合程序判断：

1. 回答中出现的 `shop_id/shop_name` 是否在 EvidencePack 中；
2. 回答中的距离、价格、评分、营业状态是否在 AnswerPlan 中；
3. `unknown` 是否被说成“没有”；
4. required unknown 是否遗漏说明；
5. 工具失败是否被隐藏；
6. 回答是否提到了未查询的商户。

## 11.2 结构化 claim 校验

将回答拆成 claims：

```json
[
  {
    "claim": "山城一锅距离约 1.2km",
    "shop_id": "shop_001",
    "field": "distance",
    "source_required": "get_distance_eta"
  }
]
```

校验：

- claim 是否能被 EvidencePack 支持；
- claim 是否在 AnswerPlan 白名单内；
- claim 是否使用了正确 shop_id；
- claim 是否把不确定信息确定化。

## 11.3 LLM 辅助校验

适合 LLM 辅助判断：

- 是否答非所问；
- 是否语义上暗示了无来源结论；
- 是否表达误导；
- 是否遗漏用户主要问题；
- 是否语气过度肯定。

## 11.4 violation 类型

```text
unsupported_fact
shop_id_mismatch
unknown_as_false
tool_failure_hidden
intent_drift
missing_disclaimer
ranking_changed_by_llm
facet_missing
```

输出：

```json
{
  "verdict": "rewrite",
  "violations": [
    {
      "type": "unknown_as_false",
      "text": "这家没有券",
      "reason": "get_coupon_list timeout, cannot conclude no coupon"
    }
  ]
}
```

# 十二、FinalResponseBuilder

普通回答：

```json
{
  "answer_text": "...",
  "clarification": null,
  "warnings": [],
  "trace_id": "trace_001",
  "state_update": {}
}
```

澄清回答：

```json
{
  "answer_text": "你说的是哪一家海底捞？\n1. 海底捞火锅(水晶城购物中心店)\n2. 海底捞火锅(学院路店)\n\n回复 1 或 2 就可以。",
  "clarification": {
    "pending_id": "pending_001",
    "candidates": []
  },
  "trace_id": "trace_001"
}
```

# 十三、StateUpdatePlanner

状态写入只在本层统一规划。

## 13.1 推荐任务成功

- 保存 `last_recommendation_list`；
- 保存 `active_constraints`；
- 不默认设置 `current_shop`。

原因：推荐返回多家店时，如果默认第一家为 current_shop，后续“这家”容易串店。

## 13.2 单店任务成功

- 设置 `current_shop`；
- 保存 `last_tool_results_summary`；
- 如果来自澄清选择，清空 `pending_clarification`。

## 13.3 用户明确引用第一家

- 设置 `current_shop = 第一家`。

## 13.4 对比任务成功

不建议直接把排名第一的店设置为 `current_shop`。

建议保存：

```json
{
  "last_task_type": "comparison",
  "comparison_targets": ["shop_001", "shop_002", "shop_003"],
  "comparison_result": {
    "ranking": ["shop_001", "shop_002", "shop_003"],
    "recommended_shop_id": "shop_001",
    "dimension_winners": {
      "distance": "shop_002",
      "coupon": "shop_001"
    }
  },
  "suggested_shop": "shop_001",
  "current_shop": null
}
```

后续指代处理：

| 用户追问 | 解析方式 |
|---|---|
| 第一家的券呢 | comparison_result.ranking[0] |
| 推荐那家的券呢 | suggested_shop |
| 第二家远吗 | comparison_result.ranking[1] |
| 这几家哪个有券 | comparison_targets |
| 它有券吗 | 若上下文不明确，应澄清 |

## 13.5 澄清任务

发起澄清：

- 保存 `pending_clarification`。

澄清完成：

- 清空 `pending_clarification`；
- 恢复原任务继续执行。

澄清过期：

- 清空 `pending_clarification`；
- 提示用户重新说明。

# 十五、EvalCaseRunner

## 15.1 基础用例

- 你有什么作用；
- 你好；
- 附近推荐个火锅；
- 附近有没有适合约会、现在营业、最好有券的火锅；
- 海底捞水晶城店有券吗；
- 海底捞水晶城店现在营业吗；
- 海底捞水晶城店离我远吗。

## 15.2 多轮用例

- 附近推荐个火锅 → 第一家有券吗；
- 附近推荐个火锅 → 第一家远吗；
- 附近推荐个火锅 → 便宜一点的呢；
- 单店查询成功 → 这家现在营业吗；
- 附近推荐个火锅 → 第一家和海底捞比呢。

## 15.3 异常用例

- ，；
- 这家有券吗，但没有 current_shop；
- 第一家远吗，但没有 last_recommendation_list；
- 海底捞有券吗，但多候选；
- 不存在的店有券吗。

## 15.4 工具失败用例

- get_coupon_list timeout；
- check_open_status circuit_open；
- get_distance_eta failed；
- search_shops empty；
- resolve_shop ambiguous。

## 15.5 对比专项用例

1. 两店综合对比：海底捞水晶城店和山城一锅哪个好？
2. 三店综合对比：海底捞、山城一锅、凑凑这三家哪个更值得去？
3. 三店距离对比：这三家哪个离北京邮电大学最近？
4. 三店优惠对比：这三家哪个有券？
5. 三店营业状态对比：这三家哪个现在营业？
6. 追问式对比：附近推荐个火锅。第一家和海底捞比呢？
7. 多候选对比：海底捞和凑凑哪个好？如果多门店候选，先澄清。
8. 多店中部分工具失败：A 店券 ok，B 店券 unknown，C 店券 empty，不能把 B 店说成没有券。
9. 营业状态 unknown：不能说该店营业中或已打烊。
10. 重复 shop_id 去重：多个名称解析到同一家店时，要去重并提示。
11. 超过 5 家对比：提示缩小范围，或先按距离/价格/营业状态粗筛。
12. 对比后状态追问：三店对比完成，用户问“第一家的券呢”。
13. 对比后模糊指代：三店对比完成，用户问“它有券吗”，上下文不明确则澄清。

# 十六、最终原则

1. LLM 负责理解和表达，不负责创造事实。
2. 事实只来自 ToolCall。
3. 单店任务必须有唯一 `shop_id`。
4. 多候选不能默认第一家。
5. 推荐排序由系统策略完成。
6. 多店对比必须先构建 ComparisonMatrix。
7. unknown 不能说成没有。
8. 工具失败不能隐藏。
9. 回答必须经过 AnswerPlan 和 AnswerVerifier。
10. SessionState 只能由 StateUpdatePlanner 统一更新。
11. Trace 必须贯穿输入、规划、工具、回答和状态更新全链路。

# 02_语义理解层

# 一、层职责

语义理解层负责把用户文本转换为结构化语义，即 `SemanticFrame`。

这一层需要判断：

1. 用户是不是在问本地生活；
2. 用户要做什么任务；
3. 有没有提到商户；
4. 有没有约束条件；
5. 是不是多轮追问；
6. 是否低信息、无效或越界；
7. 是否包含多个查询 facet。

本层不负责：

- 不解析最终 shop_id；
- 不调用业务工具；
- 不做最终推荐排序；
- 不生成最终回答。

# 二、模块划分

| 模块 | 作用 | 推荐实现方式 |
|---|---|---|
| TextNormalizer | 文本标准化 | 规则 |
| HardGuard | 低信息、安全、无效输入判断 | 规则优先 |
| TopIntentRouter | 顶层意图识别 | 规则兜底 + LLM 分类 |
| LocalLifeIntentParser | 本地生活任务识别 | LLM 主导 + 枚举校验 |
| SlotExtractor | 槽位抽取 | LLM 主导 + schema 校验 |
| MerchantMentionExtractor | 商户名提取 | LLM + 词典/规则辅助 |
| FollowUpDetector | 多轮追问识别 | LLM + 规则 |
| MultiFacetDetector | 多意图/多 facet 识别 | LLM 主导 |
| SemanticFrameBuilder | 构造语义帧 | 程序组装 |
| SemanticFrameValidator | 校验语义帧 | 规则 |

# 三、TextNormalizer

轻量标准化：

- 去除首尾空格；
- 统一中英文标点；
- 全角半角处理；
- 连续空格压缩；
- 轻量同义词归一。

示例：

```text
“海底捞 水晶城 店 有券吗？”
→ “海底捞水晶城店有券吗”
```

注意：不要在这里改写用户意图，不要把简称强行变成具体店名。

# 四、HardGuard

HardGuard 判断输入是否可以继续进入业务链路。

输出类型：

- `safe`：可以继续；
- `invalid`：无效输入；
- `greeting`：问候；
- `capability`：能力询问；
- `out_of_scope`：非本地生活；
- `unsafe`：安全风险。

示例：

| 输入 | 输出 |
|---|---|
| ， | invalid |
| 你好 | greeting |
| 你有什么作用 | capability |
| 附近推荐火锅 | safe |
| 今天天气怎么样 | out_of_scope |

规则：

1. `invalid` 不进入工具链路；
2. `greeting` 不进入工具链路；
3. `capability` 进入能力说明链路；
4. `safe` 才继续本地生活理解；
5. `unsafe` 直接安全拒答。

# 五、顶层意图与本地生活任务

## 5.1 TopIntentRouter

顶层意图枚举：

```text
local_life
capability
chat
invalid
unsafe
out_of_scope
```

不要让所有文本都进入本地生活链路。尤其是：

- 你好；
- 你是谁；
- 你有什么作用；
- 随便输入的符号；
- 天气、新闻、数学题等非本地生活问题。

## 5.2 LocalLifeIntentParser

本地生活任务枚举：

```text
recommendation
single_shop_query
coupon_query
open_status_query
distance_query
comparison
recommendation_refine
coupon_decision
multi_facet_single_shop_query
multi_facet_comparison
unknown_local_life
```

示例：

| 用户输入 | task_type |
|---|---|
| 附近推荐个火锅 | recommendation |
| 海底捞水晶城店有券吗 | coupon_query |
| 这家现在营业吗 | open_status_query |
| 第一家远吗 | distance_query |
| 便宜一点的呢 | recommendation_refine |
| 和海底捞比呢 | comparison |
| 海底捞有券吗，顺便看看现在营业吗 | multi_facet_single_shop_query |
| 海底捞和山城一锅哪个更便宜，哪个有券 | multi_facet_comparison |

# 六、多 facet 任务设计

真实用户经常一次问多个方面，不能强行压成一个 `task_type`。

建议输出 `primary_task + facets`：

```json
{
  "primary_task": "single_shop_query",
  "facets": [
    {"facet": "coupon", "required": true},
    {"facet": "open_status", "required": true},
    {"facet": "distance", "required": false}
  ]
}
```

常见 facet：

- `detail`；
- `coupon`；
- `open_status`；
- `distance`；
- `price`；
- `rating`；
- `scene_match`；
- `value`。

原则：

1. `task_type` 决定主链路；
2. `facets` 决定需要哪些工具；
3. 多 facet 不新增大量顶层路由，而是在 TaskPlanner 中展开；
4. LLM 可以识别 facet，但最终 facet 必须落在枚举中。

# 七、SlotExtractor

槽位分为硬约束、软偏好和排序信号。

```json
{
  "hard_constraints": {
    "category": "火锅",
    "location_type": "nearby",
    "open_now": true
  },
  "soft_preferences": {
    "has_coupon": true,
    "scene": "约会",
    "price_preference": "cheaper"
  },
  "ranking_signals": [
    "distance",
    "coupon",
    "rating",
    "scene_match"
  ]
}
```

约束解释：

| 用户表达 | 处理方式 |
|---|---|
| 必须现在营业 | 硬约束 |
| 现在营业的 | 硬约束 |
| 最好有券 | 软偏好，不强过滤 |
| 必须有券 | 硬约束 |
| 便宜一点 | 排序偏好或 refine 条件 |
| 附近 | 默认基于北京邮电大学，半径 3km |
| 适合约会 | 场景偏好，不直接硬过滤 |

# 八、SemanticFrame Schema

```json
{
  "top_intent": "local_life",
  "task_type": "recommendation",
  "primary_task": "recommendation",
  "facets": [
    {"facet": "open_status", "required": true},
    {"facet": "coupon", "required": false},
    {"facet": "distance", "required": true}
  ],
  "merchant_mentions": [],
  "reference_mentions": [],
  "hard_constraints": {
    "category": "火锅",
    "location_type": "nearby",
    "open_now": true
  },
  "soft_preferences": {
    "has_coupon": true,
    "scene": "约会"
  },
  "ranking_signals": ["distance", "open_status", "coupon", "rating"],
  "follow_up": {
    "is_follow_up": false,
    "follow_up_type": "none"
  },
  "confidence": 0.87,
  "need_context": false,
  "raw_text": "附近有没有适合约会、现在营业、最好有券的火锅？",
  "normalized_text": "附近有没有适合约会现在营业最好有券的火锅"
}
```

## 8.1 字段说明

| 字段 | 说明 |
|---|---|
| top_intent | 顶层意图 |
| task_type | 本地生活任务类型 |
| primary_task | 主任务，用于路由 |
| facets | 多维查询项，用于工具规划 |
| merchant_mentions | 文本中提到的商户名，不代表已解析 shop_id |
| reference_mentions | “这家”“第一家”等引用 |
| hard_constraints | 硬约束 |
| soft_preferences | 软偏好 |
| ranking_signals | 排序信号 |
| follow_up | 是否多轮追问 |
| confidence | 语义解析置信度 |
| need_context | 是否需要读取 SessionState 恢复上下文 |

# 九、LLM 与规则的职责边界

| 环节 | 推荐策略 |
|---|---|
| HardGuard | 规则优先，LLM 不参与或只辅助 |
| TopIntentRouter | 规则兜底 + LLM 分类 |
| LocalLifeIntentParser | LLM 主导，枚举校验 |
| SlotExtractor | LLM 主导，schema 校验 |
| MerchantMentionExtractor | LLM + 词典辅助 |
| FollowUpDetector | 规则识别显式指代，LLM 处理隐式追问 |
| TargetRequirementChecker | 规则决定 |
| ToolRequirementPlanner | 规则/策略决定，LLM 不直接自由决定 |
| RankingPolicy | 系统策略决定 |
| AnswerGenerator | LLM 表达 |
| AnswerVerifier | 规则 + 结构化校验为主，LLM 辅助 |

## 9.1 冲突处理

1. 规则判定 `invalid/unsafe` 时，优先规则。
2. LLM 输出不在枚举内，丢弃并回退 `unknown_local_life`。
3. LLM 置信度低于阈值，进入澄清或安全降级。
4. 用户明确提到商户但 LLM 没抽取，MerchantMentionExtractor 应通过词典/规则补救。
5. LLM 认为是推荐，但存在明确“有券吗/营业吗/远吗”，应生成 facet，而不是丢失子需求。

# 十、SemanticFrameValidator

校验项：

1. `top_intent` 必须在枚举内；
2. `task_type` 必须在枚举内；
3. `facets[].facet` 必须在枚举内；
4. `confidence` 必须在 0～1；
5. `merchant_mentions` 只能是文本提及，不允许直接伪造 shop_id；
6. `hard_constraints` 和 `soft_preferences` 不能互相矛盾；
7. `open_now=true` 时，如果用户只说“最好现在营业”，应转为软偏好；
8. LLM 输出 JSON 失败时，走规则兜底或澄清。

# 十一、本层输出

成功输出：

```json
{
  "status": "ok",
  "semantic_frame": {}
}
```

需要能力说明：

```json
{
  "status": "capability",
  "answer_type": "capability_intro"
}
```

需要澄清：

```json
{
  "status": "need_clarification",
  "reason": "LOW_SEMANTIC_CONFIDENCE"
}
```

# 本地生活服务效果增强需求清单

这份文档整理的是：在不只看 `todo/` 里工程重构项的前提下，从架构层面和需求分析层面，还需要补齐哪些能力，才能让本地生活服务 agent 的效果更稳、更准、更少返工。

核心原则：

- 先定义清楚“服务应该支持什么”，再谈实现
- 先把路由、事实来源、结果链和追问规则定死，再补能力
- 避免把多种职责继续堆到同一个节点里，防止新的架构冗余
- 所有新增能力都要能进入评估闭环，而不是只看“能不能答出来”

## 1. 明确本地生活服务的支持范围矩阵

需要先明确服务到底支持哪些问题类型，哪些不支持，哪些必须追问。

建议至少拆成这些大类：

- 商家详情
- 推荐 / 附近推荐
- 优惠券 / 团购 / 活动
- 营业状态 / 现在是否营业
- 距离 / 位置 / 到店方式
- 比较 / 选择
- 澄清 / 补充信息
- 非本地生活兜底

每一类都要定义：

- 输入需要什么信息
- 输出应该包含什么内容
- 哪些信息可以缺省
- 哪些信息必须追问
- 哪些信息禁止猜测

## 2. 给每个 intent 定义成功标准

不能只写 intent 名称，要把成功标准写清楚。

例如：

- `merchant_detail`
  - 必须命中目标店
  - 不能串店
  - 需要围绕用户关心点输出
- `coupon_query`
  - 必须区分实时券和历史券
  - 必须说明是否可用
- `open_status`
  - 必须给出当前营业判断
  - 如果无法确认，要明确说明不确定
- `nearby_recommendation`
  - 必须和位置绑定
  - 必须能解释推荐理由

## 3. 明确何时追问，何时直接答

需要把追问规则做成统一策略，而不是让各个节点各自决定。

建议先定这些规则：

- 有明确店名但缺少位置时，优先先答店相关内容，再补位置确认
- 只有“附近 / 推荐 / 适合”但没有城市或位置时，优先追问
- 上下文已经足够继承时，不要重复追问
- 连续多轮都在问同一家店时，优先继承上一轮店铺

目标是减少“该追问时不追问”和“该直接答时却一直问”的双向问题。

## 4. 把事实来源优先级彻底定死

需要明确什么信息来自哪里，不能让 LLM 自由补。

建议优先级如下：

1. 实时工具
2. 结构化商家数据
3. 检索到的证据文本
4. LLM 推断

重点保护这些字段：

- 券
- 营业状态
- 距离
- 地址
- 当前店名

这些字段如果没有事实来源，就不要硬答。

## 5. 建立单店和多店两条结果链

单店查询和多店推荐不要继续混在一条主链里。

建议拆成两条清晰链路：

- 单店链
  - 目标店解析
  - 单店证据检索
  - 单店结果生成
- 多店链
  - 候选店生成
  - 排序 / 比较
  - 多店答案组织

这样可以减少“问单店却答成推荐”或者“问推荐却输出一堆单店详情”的混乱。

## 6. 增加比较 / 选择专用能力

像这些问题不能只靠普通推荐硬撑：

- A 和 B 哪个更适合约会
- 哪家更安静
- 哪家更适合带爸妈
- 哪家更便宜

建议显式加入比较能力，输出时至少包含：

- 比较维度
- 每个维度的差异
- 最终建议

## 7. 把自修复回路做成一级能力

如果第一次检索没查到，不能只靠兜底文案结束。

建议具备图级自修复能力：

- 第一次查询失败
- 自动改写 query 再查一次
- 仍失败再追问或兜底

这比单纯的局部重写更有价值，因为它能把“没命中”变成“再试一次”。

## 12. 建立按 intent 分类的黄金集

评估不能只看总分，要按 intent 分层做黄金集。

建议至少覆盖：

- 商家详情
- 优惠券
- 营业状态
- 附近推荐
- 比较 / 选择
- 澄清
- 兜底

每条样本都要带：

- 输入
- 期望路由
- 期望实体
- 期望输出要点
- 不允许出现的错误

## 13. 评估指标不要只看“答没答出来”

需要补足更贴近业务的质量指标。

建议关注：

- 串店率
- 错店率
- 过度追问率
- 兜底率
- 工具调用命中率
- 空召回率
- 实时信息错误率
- 幻觉率

这样才能知道问题是路由错了、数据错了，还是生成错了。

## 14. 做“问题类型 - 失败类型”映射

需要把常见失败模式固定下来，方便定位和修复。

例如：

- 问券却答环境
- 问当前营业却用了历史信息
- 问附近却没追问位置
- 问比较却只答单店
- 问单店却答成推荐

有了这个映射，后面修问题就不会全靠人工猜。

## 15. 答案模板要按任务类型分层

不要所有输出都用同一种模板。

建议至少拆成：

- 单店详情模板
- 券模板
- 营业状态模板
- 推荐模板
- 比较模板
- 澄清模板
- 拒识模板

每种模板都要定义：

- 必答项
- 可选项
- 禁止项
- 长度上限

## 17. 让答复策略更懂场景

同样是“推荐”，不同场景的答复重点不一样。

建议把场景策略也显式化：

- 问环境：优先讲环境再讲综合结论
- 问券：优先讲券再讲是否适合去
- 问约会：优先讲场景适配再给理由
- 问比较：先给对比维度，再给结论

这样输出会更符合用户真实意图。

## 18. 做对话状态机，而不只是会话存储

`persist_session` 只负责存不够，最好明确状态机。

建议维护：

- 当前任务状态
- 当前店铺状态
- 当前追问状态
- 当前比较对象
- 当前待确认信息

这样多轮连续问答会更稳定，也更容易继承上下文。

## 19. 做解释性输出，而不是只给结论

本地生活场景里，用户通常需要“为什么这样说”。

建议答案里保留轻量解释：

- 为什么推荐这家
- 为什么判断它适合约会
- 为什么说这个券可用
- 为什么当前无法确认营业状态

这样能显著提升可信度。

## 20. 做一个产品边界提示

当问题超出当前服务能力时，不要硬答。

建议统一边界提示策略：

- 非本地生活问题
- 缺少位置无法推荐
- 实时券无法确认
- 商家信息过旧

要让用户知道“为什么不能直接回答”，而不是得到看似完整但实际上不可靠的答案。

## 改造时要避免的冗余问题

这份需求补充不是为了再加一层复杂度，而是为了让系统更稳。

改造时要特别避免：

- 静态路由和动态调度同时做同一层决策
- `route_gate` 继续膨胀成半个编排层
- `compose_answer` 继续膨胀成 God Node
- 校验、修正、兜底混进生成节点
- 单店和多店结果链继续互相串扰
- 新增“看起来很智能”的节点，但没有实际评估闭环

## 推荐落地顺序

如果要从效果提升角度先做最值钱的部分，建议顺序是：

1. 支持范围矩阵 + intent 成功标准
2. 事实来源优先级
3. 单店 / 多店双结果链
4. 自修复回路
5. 按 intent 分类的黄金集
6. 问题类型 - 失败类型映射
7. 答案模板分层
8. 场景化答复策略
9. 对话状态机
10. 解释性输出
11. 产品边界提示

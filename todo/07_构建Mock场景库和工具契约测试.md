# 02.5 构建 Mock 场景库和工具契约测试

## 目标
明确定义覆盖各类极端用例的 Mock 数据集，不仅验证正常数据，也要覆盖超时、未知等 15 个长尾场景。

## 实现细节要求

### 1. 测试场景库定义
必须在 `mock_data/shops.json` 或 `MockToolExecutor` 内置对以下 15 个核心场景的支持：
1. **唯一命中店**：海底捞水晶城店
2. **多候选店 (AMBIGUOUS)**：海底捞 A / 海底捞 B / 海底捞 C
3. **别名命中**：搜索“海底捞水晶城” -> 命中全名“海底捞火锅(水晶城购物中心店)”
4. **无券店**：明确 `empty`
5. **有券店**
6. **券查询 timeout 店**
7. **营业中店**
8. **已打烊店**
9. **营业状态 unknown 店**
10. **距离近但评分低店**
11. **评分高但距离远店**
12. **适合约会 tag 店**
13. **不适合约会但有券店**
14. **同名不同地址店**
15. **多店对比中某个维度 unknown 的店**

### 2. E2E 组合行为测试场景 (测验 Agent 主流转)
除了单点场景，还需要预置针对系统状态流的组合用例：
1. **多轮跟随测试**：推荐结果输出后，用户追问“第一家有券吗”。断言其走入 `last_recommendation_list` 取值并查券。
2. **多店回指歧义拦截测试**：推荐结果输出后，用户追问“这家有券吗”。由于此时 `current_shop` 并非确定的一家，断言系统不盲猜第一家，而是发起“你指的是哪一家？”的澄清。
3. **澄清脱离测试**：`pending_clarification` 挂起时，用户输入“算了，附近推荐火锅”。断言原挂起状态被清空，重置进入 `recommendation_flow`。
4. **不完整数据对比测试**：对比场景下 A 店有券，B 店券 unknown，C 店闭店。断言矩阵构建和答复生成时，未知不背判为更差，且明确输出该店信息不明。
5. **强行防幻觉拦截测试**：刻意调大 temperature 或喂错 LLM 提示，迫使其篡改推荐顺序，断言 `AnswerVerifier` 第一时间侦测到 `ranking_changed_by_llm` 并重试或阻断。

### 3. 工具契约验证
验证 Mock 能够稳定返回并由 Gateway 处理：
- 调用 `mock_get_coupon_list` 时如果是场景 6，能稳定抛出 timeout 并让 Gateway 输出带 `TOOL_TIMEOUT` error_code 的 `ToolResult`。

## 本阶段完成标准 (Definition of Done)
1. `mock_data` 中包含满足上述 15 个场景属性的结构化假数据。
2. **完成测试**：`tests/test_mock_scenarios.py` 覆盖对上述店名的单独获取调用，验证各场景返回预期准确无误。
3. **完成测试**：`tests/test_e2e_context_and_verifier.py`，覆盖推荐后序号追问、推荐后“这家”歧义、pending 脱离、对比 unknown、LLM 改排序拦截等核心 E2E 行为测试。

## 阶段完成后的收尾

- 先把 mock 数据和契约测试跑通，再进入真正工具实现。
- 这一阶段的结果应当是“样例稳定可复现”，不是“业务功能已经完整”。

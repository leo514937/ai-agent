# P1.5 Day 2 - Input Coverage & Query Merge

优先级：第二。

目标：增强用户各种输入的覆盖能力，把“输入理解”从路由决策里剥离出来，建立 `request_legality / query_safety / query_merge / top_level_intent_router` 这一层。

## 这一天要解决什么

- 低信息、纯标点、无效 session 先被挡住
- prompt injection / unsafe 先被拦截
- identity / capability / direct_chat / out_of_scope 不再进入本地生活主链路
- 多轮指代先做 query merge，再进入 `resolve_target_shop`
- 让 `SemanticParseResult` 变成后续 contract / router 的统一输入

## 实现要求

- 输入理解层要单独成段，别和路由、RAG、Tool 混写在一个文件里
- `request_legality`、`hard_guard`、`query_safety`、`query_merge` 要分层实现，职责不要交叉
- query merge 要依赖可复用语义结果，不要到处复制相同的指代解析代码
- 安全拦截和语义理解要分开，避免一个函数同时做太多判断

## 明确不做什么

- 不替换 `route_gate`
- 不收敛复杂路径
- 不要求标准路径完整 contract review 已经落地
- 不要求 RAG / Tool / Recommendation 立刻全部节点化

## 新增的输入理解层

### 1. `request_legality`

第一层负责请求合法性，不处理语义。

建议检查：

- session 是否有效
- trace / turn / user 是否合法
- 是否超出系统级拒绝范围
- 是否属于明显非法或不应处理的请求

### 2. `hard_guard`

在请求合法之后，`hard_guard` 处理低信息和明显需要澄清的输入。

建议覆盖：

- 纯标点
- 纯噪声
- 极低信息输入
- 明显缺上下文但无法安全猜测的输入

### 3. `query_safety`

对自然语言输入做安全检测。

建议拦截：

- prompt injection
- 明显越权
- unsafe / malicious payload
- 会污染后续 contract 的输入

### 4. `query_merge_for_local_life`

把多轮上下文、当前轮表述和候选店信息合并成一个更稳的语义输入。

建议 merge 的信息源：

- `current_shop`
- `last_candidates`
- `candidate_shop_ids`
- `comparison_shop_ids`
- `TargetShopPolicy`
- `SemanticParseResult`
- 当前轮 slots / text

### 5. `merged_query_safety`

query merge 之后再做一次安全检查，避免 merge 结果引入新的风险。

### 6. `top_level_intent_router`

把输入先分到更高层级的意图，而不是直接送到 `rag/tool/recommendation`。

建议 top level intents：

- `identity`
- `capability`
- `direct_chat`
- `local_life`
- `recommendation`
- `comparison`
- `planning`
- `document_or_knowledge`
- `math_or_code`
- `out_of_scope`
- `unsafe`

## 重点任务

### 1. 为 direct_chat / out_of_scope / unsafe 建立短路分支

这些输入不应该被误送入本地生活 RAG / Tool / Recommendation。

建议策略：

- `identity / capability` -> 直接能力回答
- `direct_chat` -> 简单自然回复
- `out_of_scope` -> 解释边界
- `unsafe` -> 拒绝或安全兜底

### 2. 让 query merge 先于 target shop 解析

多轮指代必须先合并语义，再 resolve target。

典型情况：

- `第一家有券吗`
- `那西贝呢`
- `这家适合约会吗`
- `刚才那家现在营业吗`

### 3. 让 query merge 产出可复用的语义结果

建议产出：

- merged query
- merged slots
- target reference
- sub intents
- missing slots
- confidence

这部分最好收敛到 `SemanticParseResult` 或与其兼容的结构。

## Day 2 输出要求

Day 2 结束后，输入理解层应该先把以下问题分清楚：

- 这是不是合法请求？
- 这是不是安全输入？
- 这是不是只需要闲聊或能力回答？
- 这是不是本地生活问题？
- 这是不是需要 query merge 的多轮指代？

## Day 2 验收

| 用例 | 期望 |
|---|---|
| `你是谁` | identity / capability answer |
| `你能做什么` | capability answer |
| `谢谢` | direct_chat |
| `帮我写代码` | out_of_scope 或 fallback |
| `，` | hard_guard clarify/reject |
| `第一家有券吗` | query_merge 到候选店具体 shop |
| `那西贝呢` | target 切换到西贝 |
| unsafe / prompt injection | query_safety reject |

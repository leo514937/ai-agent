# P1.5 Day 3 - Router Degradation

优先级：第三。

目标：让 `route_gate` 逐步退化为只负责复杂度判断的 `complexity_router`，并开始把原来的能力分支降级为能力节点，而不是顶层路线。

## 这一天要解决什么

- Router 只看复杂度，不再直接决定 `rag/tool/recommendation/rag_plus_toolcall`
- `execution_mode = clarify / simple / standard / complex` 成为主语义
- 旧 `RoutingDecision` 字段继续可读、可写、可测
- `simple` 场景仍可以直接 ToolCall
- `standard` 和 `complex` 的边界开始清晰

## 实现要求

- Router 退化要通过清晰的模式枚举和镜像字段实现，不要继续在一个函数里堆所有分支判断
- 能力节点要下沉到独立节点或独立服务，不要把 router 变成万能分发器
- `route_gate` 过渡期要保持兼容，但新语义不要继续污染旧分支实现
- 复杂度判断、能力选择、结果修复要解耦，避免一层套一层地写成大泥球

## 明确不做什么

- 不删除 `route_gate`
- 不删除旧路由矩阵测试
- 不让 `standard` 立刻完整进入 contract review 体系
- 不把 `complex` 之前的任务都 Planner 化

## Router 的新语义

建议 `execution_mode` 的判定顺序：

1. `clarify`
2. `simple`
3. `standard`
4. `complex`

含义：

- `clarify`：信息不足，先澄清
- `simple`：单目标、单意图、单步任务，但仍可能使用外部能力
- `standard`：多 facet 或多能力组合，但不需要 Planner
- `complex`：多步骤、多约束、依赖中间结果，需要 Plan-Execute-Review-Replan

## 兼容镜像要求

在写入 `execution_mode` 的同时，必须继续维护：

- `required_action`
- `should_retrieve`
- `should_call_tool`
- `route_candidate`
- `blocked`
- `missing_slots`
- `route_reason`

这样可以保证：

- 现有路由矩阵仍可直接读旧字段
- `route_after_understand` / `route_after_rag` 不被打断
- `compose_answer` 里的兼容逻辑仍然成立

## 重点任务

### 1. `route_gate` 写入 `execution_mode`

这一阶段可以先让 `route_gate` 继续存在，但它的输出重心要改成复杂度分流。

建议实现方式：

- 先计算 `execution_mode`
- 再回填旧字段镜像
- 再维持原有 route trace

### 2. 能力节点下沉

把原本顶层的：

- `rag`
- `tool`
- `recommendation`

逐步降级为能力节点。

它们不再是 Router 的主结果，而是后续 `workflow_executor / direct_or_tool_node / plan_executor` 的可调用能力。

### 3. `rag_plus_toolcall` 退化为兼容别名

增强版计划里，`rag_plus_toolcall` 不应继续作为 canonical 顶层分支。

这一阶段要求：

- 旧值还可以读
- 旧值还可以写
- 但它不再是新的主路由语义中心

## Day 3 输出要求

Day 3 结束后，应该能看到：

- `execution_mode` 已经进入 state / trace
- 旧路由字段仍然可读
- `simple` 场景仍然能直达 ToolCall
- `standard` / `complex` 的语义边界开始生效
- 顶层不再以 `rag_plus_toolcall` 作为 canonical 分支

2. `simple` 场景仍能直达 ToolCall

4. 新的 `execution_mode` 已能落到 state / trace 中
5. 旧 `required_action` 仍可被现有代码消费

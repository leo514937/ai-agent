# P1.5 Day 5 - Complex Path Convergence

优先级：第五。

目标：把旧 `plan_execute_subgraph` 最终收敛到 complex path，只让复杂任务进入 `Plan -> Execute -> Review -> Replan` 闭环。

## 这一天要解决什么

- 只有 complex 任务进入 planner
- 复杂路径的执行、收集、review、replan 形成完整闭环
- review 的回流只发生在 complex path
- standard review 绝不允许回 planner
- retry / replan 必须被预算和上限约束

## 实现要求

- complex path 的 planner、executor、review、replan 要拆成独立节点或独立模块，不要写成一大坨循环函数
- step dispatch 要保持清晰，尽量按 step 类型拆开，而不是在一个方法里写大量 if/else
- retry / replan 计数要集中管理，不要在多个地方重复加计数
- complex path 可以复杂，但代码结构不能乱，必须和图一一对应

## 明确不做什么

- 不在 Day 2 之前整体重写旧 plan 执行图
- 不让 standard review 回 `planner_node`
- 不让 simple path 进入复杂循环
- 不移除旧 trace / SSE / 路由矩阵兼容面

## complex path 的目标结构

建议只在 `execution_mode = complex` 时启用：

- `planner_node`
- `plan_executor`
- `execute_plan_step`
- `collect_step_result`
- `all_steps_done`
- `complex_review`
- `repair_answer / final_answer`

## 重点任务

### 1. `planner_node`

planner 只服务复杂任务，不服务标准任务。

适合进入 planner 的场景包括：

- 跨店比较
- 多步骤依赖
- 需要边执行边修正
- 需要根据中间结果重新组织任务步骤

### 2. `plan_executor`

执行器负责按 step 调度，不负责做顶层路由判断。

建议支持的 step 类型：

- `rag_step`
- `tool_step`
- `recommendation_step`
- `rank_merge_step`

### 3. `collect_step_result`

这个节点负责把每一步的结果收集起来，形成后续 review 可读的中间态。

要保证：

- 每一步的执行结果都可追踪
- step 失败能进入受控回退
- 不丢失当前 step 上下文

### 4. `complex_review`

complex review 是唯一可以和 planner 形成闭环的 review。

允许动作：

- `pass`
- `repair_answer`
- `retry_step`
- `replan`
- `degrade`

这里要和 standard review 明确区分：

- standard review 不回 planner
- complex review 可以 replan

### 5. retry / replan 上限

复杂循环必须有硬上限。

建议至少管理：

- `retry_rag`
- `retry_tool`
- `retry_step`
- `repair_answer`
- `replan`

超限后的默认策略应是：

- 降级
- 不再进入循环

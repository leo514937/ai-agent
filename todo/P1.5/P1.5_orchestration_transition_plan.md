# P1.5 Orchestration Transition Plan

本文件保留为 P1.5 的总索引与迁移导航页。升级版改造计划请以 [P1.5_Orchestration_Transition_Plan_Enhanced.md](./P1.5_Orchestration_Transition_Plan_Enhanced.md) 为总源头，下面的 day 文档是按优先级拆出的执行清单。

## 迁移总目标

把当前 LangGraph 从 `route_gate -> rag/tool/recommendation/plan_execute -> compose_answer` 的粗路由结构，升级为：

- 多层输入理解与安全兜底
- 复杂度分流
- Contract 驱动执行
- RAG / Tool / Recommendation 能力节点化
- Review / Repair / Retry / Degrade 闭环
- Complex Path Plan-Execute-Review-Replan

## 三条迁移原则

1. 旧拓扑先兼容新字段
2. `route_gate` 逐步退化为 `complexity_router`
3. 旧 `plan_execute_subgraph` 最后才收敛到 complex path

## 任何阶段都不能破坏

1. 旧 trace 字段
2. 旧 `RoutingDecision` 字段
3. 现有 SSE 输出
4. 现有路由矩阵测试
5. 单店 `TargetShopPolicy` 结果

## 目标拓扑约束

- `hard_guard` 必须显式保留在 `load_context` 之后
- `simple` 路径必须补 `rule_review`
- `standard` review 不能回 `planner_node`
- `recommendation_reason` 的 source 改为 `mixed/internal`

## 实现风格要求

- 必须实现文档中的图编排结构，不能只写出“看起来复杂”的单文件代码
- 代码和架构要清爽，职责边界要清楚
- 不要无脑把所有逻辑堆到同一个 `.py` 文件
- 能拆分的节点、服务、契约、适配器都要尽可能解耦实现
- 新增能力优先通过小节点、小函数、小契约组合，不要一把写成 God Node
- 兼容层和新架构层要分开，避免旧逻辑和新逻辑互相污染

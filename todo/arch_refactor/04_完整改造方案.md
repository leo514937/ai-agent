# 4. 完整改造方案（LocalLifeAgent Sub-Graph）

> 当最小改造不足以覆盖所有场景时，升级为 CandidateSet 驱动的 Plan-Execute LocalLifeAgent。
>
> 核心思路：将当前的 task_type→fixed flow 重构为 goal_type→CandidateSpec→CandidateSet→EvidencePlan→ToolExecute→DecisionPlan→AnswerPlan→AnswerVerifier。

**总 Effort：~3-5天** | **适合 discovery comparison + refine + context 全场景**

---

## 4.1 核心架构变更

### 当前架构

```
输入 → task_type → task_plan → {facet_plan|comparison_planner}
                    → tool_execute → evidence_build → answer
```

所有 case 在 `task_plan` 之前共享 switch，然后分 2 条路径。
比较和推荐在 `task_plan` 之前就有固定差异。

### 改造后架构

```
输入 → GoalPlanner → CandidateSpec → CandidateResolver → CandidateSet
       → EvidencePlanner → ToolPlan → ToolExecutor → EvidencePack
       → DecisionPlanner → AnswerPlan → AnswerVerifier → Output

其中各阶段均为 **processor pattern**：processor 读 Plan，写更新后的 Plan 和 Evidence/State
```

**关键变化**：
- 不再有 task_type 硬分流，所有 goal 共享候选发现→候选消费→证据→决策管线
- 候选发现（CandidateResolver）和候选消费（EvidencePlanner）分离
- DecisionPlanner 替代当前的 answer_plan_build，支持多轮 decision

## 4.2 新增模块

### 4.2.1 GoalPlanner（planning/goal_planner.py → 新增）

**职责**：将用户输入转换为 Goal：user_intent + candidate_spec + evidence_needs

```python
@dataclass
class Goal:
    intent: str               # recommendation / comparison / single_query / refine / clarify_reply
    primary: str              # 主目标描述
    candidate_spec: CandidateSpec | None  # 候选条件
    evidence_needs: list[str] | None      # 需要获取的证据维度
    context_valid: bool = False           # 是否确认上下文有效
```

**输入**：`GraphState` + `SemanticFrame`
**输出**：`Goal` → 写入 GraphState

**目标样例**：

| 用户输入 | Goal |
|---------|------|
| "对比评分最高的两家KTV" | intent=comparison, candidate_spec=KTV/sort_by:rating desc/limit:2, evidence_needs=[coupon_count, open_status, rank_comment] |
| "海底捞和山城一锅哪个好" | intent=comparison, candidate_spec={explicit_mentions:["海底捞","山城一锅"]}, evidence_needs=[rating, coupon_count] |
| "推荐一家火锅店" | intent=recommendation, candidate_spec={category:"火锅", limit:1}, evidence_needs=[rating, distance, coupon_count] |
| "刚才推荐的第一家怎么样" | intent=refine, candidate_spec={context_ref:"ordinal:1"}, evidence_needs=[] |

### 4.2.2 CandidateResolver（target/candidate_resolver.py → 新增）

**职责**：将 CandidateSpec resolve 为 CandidateSet

```python
@dataclass
class CandidateResolution:
    status: str               # resolved / insufficient / ambiguous / not_found
    candidate_set: CandidateSet
    intermediate_results: list[ToolResult]   # 中间搜索工具的 ToolResult
```

**三种 resolve_ 函数**：

```python
def resolve_explicit(spec, gateway) -> CandidateResolution:
    """显式店名 → resolve_shop() → CandidateSet"""
    shop_ids = [resolve_shop(name) for name in spec.explicit_mentions]
    return CandidateResolution(status="resolved", candidate_set=CandidateSet(...))

def resolve_context(spec, session) -> CandidateResolution:
    """ordinal/deictic → session 恢复 → CandidateSet"""
    candidates = restore_from_session(spec.context_ref, session)
    return CandidateResolution(status="resolved", candidate_set=CandidateSet(...))

def resolve_discovery(spec, gateway) -> CandidateResolution:
    """条件 → search_shops + rank → CandidateSet"""
    results = search_shops(spec.category, spec.sort_by, spec.limit)
    candidates = [ResolvedCandidate(shop_id=r.shop_id, ...) for r in results]
    return CandidateResolution(status="resolved", candidate_set=CandidateSet(...))
```

### 4.2.3 EvidencePlanner（planning/evidence_planner.py → 新增）

**职责**：根据 CandidateSet + evidence_needs 生成 ToolPlan

```python
@dataclass
class ToolPlan:
    calls: list[ToolCall]      # 需要执行的 tool_calls
    dependencies: dict         # call_id → [依赖的 call_ids]
    priority: list[str]        # 执行优先级
    max_concurrent: int = 8

def plan_evidence(candidate_set: CandidateSet, evidence_needs: list[str]) -> ToolPlan:
    """为每个候选的每个证据维度生成 ToolCall。"""
    calls = []
    for candidate in candidate_set.candidates:
        for need in evidence_needs:
            calls.extend(_tool_for_evidence(need, candidate.shop_id))
    return ToolPlan(calls=calls, ...)
```

取代当前 `facet_plan` 和 `comparison_planner` 的 tool_calls 生成逻辑。

### 4.2.4 DecisionPlanner（planning/decision_planner.py → 新增）

**职责**：根据 EvidencePack + Goal 生成 AnswerPlan

```python
@dataclass
class DecisionPlan:
    answer_plan: AnswerPlan
    decision_type: str           # single_recommend / comparison / summary / clarification
    next_goal: Goal | None       # 是否还需要更多搜索（渐进式 discovery）
    session_updates: dict        # 需要更新的 session 状态
```

**取代当前**：
- `answer_plan_build` → DecisionPlanner 的一部分
- 支持渐进式发现（先搜再细化）
- 支持 multi-step comparison（先确定候选，再获取完整证据）

### 4.2.5 SessionState 扩展

```python
class SessionState:
    # ...现有字段不变...
    
    # ★ 新增字段
    last_candidate_spec: CandidateSpec | None       # 上次的候选条件
    last_candidate_set: CandidateSet | None          # 上次的候选集
    active_goal: Goal | None                         # 当前激活的 goal
    evidence_cache: dict | None                      # 缓存的证据（跨轮重用）
```

**用途**：
- refine 时从 `last_candidate_spec` 恢复搜索条件
- context 比较时从 `last_candidate_set` 恢复候选
- `evidence_cache` 减少重复工具调用

## 4.4 新增状态流转

### 标准 comparison 全链路

```
输入
  → semantic_parse(candidate_source="discovery", candidate_category="KTV",
                    evidence_needs=["coupon_list","open_status"])
  → candidate_resolve:
      CandidateSpec(source=discovery, category="KTV", limit=2, sort_by=rating:desc)
      → search_shops("KTV", limit=4, sort_by=rating) → 候选 4 个
      → 选 top 2 → CandidateSet(status=resolved, candidates=[A,B])
  → evidence_plan:
      CandidateSet[A,B] + evidence_needs[coupon_list, open_status]
      → ToolPlan(get_coupon_list(A), get_coupon_list(B), check_open_status(A), check_open_status(B))
  → tool_execute(4 calls, concurrent, semaphore=8)
  → evidence_build:
      每个 shop 的 evidence row + comparison_matrix
  → decision_plan:
      Goal(comparison) + EvidencePack
      → AnswerPlan(comparison_matrix, overall_winner, recommendation)
  → answer_generate → answer_verify → output
```

### discovery comparison 全链路

```
输入："对比评分最高的两家KTV的优惠券"
  → semantic_parse(candidate_source="discovery", ...)
  → candidate_resolve:
      search_shops("KTV", sort_by=rating, limit=4)
      → [KTV_A(4.8), KTV_B(4.5), KTV_C(4.3), KTV_D(4.0)]
      → CandidateSet(resolved, [KTV_A, KTV_B])
  → evidence_plan:
      get_coupon_list(KTV_A), get_coupon_list(KTV_B)
  → tool_execute
  → evidence_build(comparison_matrix: coupon_count)
  → decision_plan:
      比较结果：KTV_A 优惠券多 → 推荐 KTV_A
  → answer_generate → output
```

### refine 全链路

```
输入："刚才推荐的第一家有优惠券吗"
  → semantic_parse(candidate_source="context", ordinal_references=["第一家"])
  → candidate_resolve:
      _resolve_context_targets()
      → session.last_candidate_set.candidates[0] → KTV_A
      → CandidateSet(resolved, [KTV_A])
  → evidence_plan:
      get_coupon_list(KTV_A)
  → tool_execute → evidence_build → decision_plan → answer
```

### 渐进式对比

```
第一轮：
  输入："帮我看看哪家KTV优惠券最多"
  → Goal(recommendation, evidence_needs=[coupon_list])
  → candidate_resolve: search_shops("KTV") → CandidateSet(resolved, [A, B, C, D])
  → evidence_plan: get_coupon_list(A, B, C, D)
  → evidence_build: 优惠券清单
  → decision_plan: KTV_A 优惠券最多 → 推荐 KTV_A，同时保存 full_candidate_set
  → answer: "KTV_A 优惠券最多，共 5 张..."

第二轮：
  输入："那B和C呢？"
  → Goal(comparison, candidate_spec={context_ref:["第二家","第三家"]})
  → candidate_resolve: 从 session.last_candidate_set 恢复 B, C
  → evidence_plan: get_coupon_list(B), get_coupon_list(C)（可能命中 evidence_cache）
  → evidence_build: comparison_matrix
  → decision_plan: B 和 C 对比结果
  → answer: "B有3张，C有2张..."
```

## 4.5 渐进式 CandidateSet

### 为什么需要渐进

某些场景需要先发现候选，再确定哪些证据需要获取：

```python
# 先快速搜索候选，初步判断后再决定详细证据
candidate_set = search_shops(category, sort_by=rating, limit=5)
# 发现候选有 5 个但只有 3 个评分 > 4.0
filtered = [c for c in candidate_set if c.rating > 4.0]
# 决策：是否够 2 个比较？够 → 获取详情证据
if len(filtered) >= 2:
    evidence_plan(filtered[:2], evidence_needs=[...])
```

**实现方式**：
- `CandidateResolver` 只负责候选发现（search_shops + resolve_shop）
- `EvidencePlanner` 只负责候选消费（为每个候选获取证据）
- 之间通过 `CandidateSet` 耦合，允许 `DecisionPlanner` 在第一轮证据不足时触发扩搜

### 渐进触发器

| 条件 | 行动 |
|------|------|
| candidate_set.status=insufficient | 重新搜索（扩展品类/放宽条件） |
| candidate_set.candidates < min_required | 补充搜索 |
| evidence 部分失败 | 降级使用已有证据 |
| evidence 全部失败 | 回退到候选基础信息 |

## 4.6 设计决策记录

### ADR-1：不引入 ReAct / 自循环

**决策**：Agent 不直接循环调用工具，所有工具调用由 EvidencePlanner 预先规划。

**理由**：
- 当前架构的核心优势是确定性的 tool_execute
- LLM-in-loop 会引入不可控的 tool_call 序列
- 安全性下降（LLM 可能决定调用未注册的工具）
- 预规划 + 渐进扩搜覆盖了所有场景

### ADR-2：CandidateSet 跨轮不自动 persist

**决策**：`CandidateSet` 只在当前轮有效，跨轮使用需要通过 `SessionState.last_candidate_set` 显式引用。

**理由**：
- 避免过期数据影响决策（上一轮的候选不一定适用于当前查询）
- user 明确引用时才恢复
- `CandidateSet` 中的 `original_spec` 可以用于判断是否与当前查询匹配

### ADR-3：EvidencePlanner 取代 facet_plan / comparison_planner

**决策**：不再按 task_type 分流，而是统一按 evidence_needs 生成 ToolPlan。

**理由**：
- recommendation 和 comparison 的 tool_calls 没有本质区别（都是 get_shop_detail / get_coupon_list / check_open_status）
- 区别只在于 evidence 如何呈现（推荐 vs 比较），这是 DecisionPlanner 的职责
- 统一生成减少了重复代码，新增证据维度只需扩展 `_tool_for_evidence()`

## 4.7 迁移策略

### Phase 1（最小改造，~1天）
- 引入 CandidateSpec/CandidateSet
- 扩展 SemanticFrame
- 重构 _h_target_resolve
- **保留 task_type 分流**

### Phase 2（证据层合一，~1.5天）
- 引入 EvidencePlanner
- 保持 facet_plan/comparison_planner 作为 EvidencePlanner 后端
- 新增 evidence_needs 字段

### Phase 3（决策层合一，~1.5天）
- 引入 GoalPlanner
- DecisionPlanner 替代 answer_plan_build
- 逐步移除 task_router 固定路由

### Phase 4（渐进发现，~1天）
- CandidateResolver 支持渐进搜索
- evidence_cache 实现
- SessionState 扩展

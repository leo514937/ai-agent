# 6. 风险与回归

> 全面评估改造过程中的风险点、回归场景、安全边界破坏可能性。
> 每个风险标注严重等级和缓解措施。

---

## 6.1 shop_id 串店风险

### 问题

`_h_target_resolve` 中 recommendation 路径使用 `$search_result[0].shop_id` 占位符，
在 tool_execute 时通过 `_resolve_search_placeholders` 绑定 shop_id。
如果 search_shops 的返回结果在多轮执行中变化，后续工具可能绑定不同的店。

```python
# graph_builder.py L960-980
_resolve_recommendation_spec:
    spec = {
        "primary_tool": ...,
        # ★ 占位符绑定：$search_result[0].shop_id
    }
```

### 加重的场景

- discovery comparison 需要先 search_shops 获取候选，再获取证据
- 如果 search_shops 和 evidence tool_calls 不在同一次 tool_execute 中执行（分两轮），
  search_shops 的结果可能在中间被其他操作影响

### 严重等级

⚠️ **中**

### 缓解措施

1. **在同一次 `tool_execute` 中包含 search_shops 和 evidence tool_calls**，借助 `tool_execute` 的 `remaining_specs` 机制确保绑定
2. CandidateResolver 返回的 `ResolvedCandidate.shop_id` 使用真实的 shop_id 字符串，**不使用占位符**
3. 证据获取直接使用 CandidateSet 中 resolve 后的 shop_id，不走 `_resolve_search_placeholders`

## 6.2 LLM 编造候选条件

### 问题

语义解析由 LLM 完成，LLM 可能：
- 编造 `candidate_source`（用户没说的条件）
- 编造 `candidate_category`（猜错品类）
- 编造 `candidate_sort_by`（评分最高 vs 距离最近）

```python
# 用户说："对比这两家店"
# LLM 可能输出：
{
    "candidate_source": "discovery",     # ← 应该为 context
    "candidate_category": "火锅",        # ← 可能猜错
}
```

### 严重等级

⚠️ **中**

### 缓解措施

1. **规则提取器兜底**：`slot_extractor.py` 的规则推断比 LLM 更可靠，当 LLM 输出与规则冲突时以规则为准
2. **新增的 candidate_* 字段都先通过规则提取器设定默认值**，LLM 输出只能覆盖为空的情况
3. **`candidate_source` 优先级**：merchant_mentions ≥ 2 → explicit；ordinal/deictic refs → context；其他 → discovery
4. **plan_validator 校验**：如果 CandidateSpec 要求 sort_by 但候选集没有排序字段，标记为 LOW_CONFIDENCE

### 规则推断优先级

```
merchant_mentions >= 2  →  candidate_source = "explicit"    # 最高
ordinal/deictic refs    →  candidate_source = "context"
query_terms 有品类词    →  candidate_source = "discovery"     # 最低
```

## 6.3 LLM 直接调用工具（ReAct 风险）

### 问题

完整的 Plan-Execute 架构可能引入 LLM-in-loop 趋势。
当前架构的安全核心是 **LLM 不直接调用工具**，所有工具调用必须经过 ToolCallGateway。

### 严重等级

🔴 **高**（触到安全边界）

### 缓解措施

1. **EvidencePlanner 不可由 LLM 直接驱动**：ToolPlan 由规则生成，不是 LLM 输出
2. **DecisionPlanner 只输出 AnswerPlan**：不输出 tool_calls
3. **tool_execute node 不接受 LLM 输出的 tool_calls**：只接受 EvidencePlanner 生成的 ToolPlan
4. **注册所有证据获取工具的 ToolCallGateway 控制**：不可绕过

## 6.4 discovery 搜索质量差导致错误回答

### 问题

```
用户："对比评分最高的两家KTV"
  → search_shops("KTV", sort_by="rating") → [KTV_E(3.5), KTV_F(3.2)]
  → 实际最好的两家是 KTV_A(4.8) 和 KTV_B(4.5)
  → 输出对比结果但数据是错的
```

### 原因

- 当前 mock 实现的 search_shops 可能覆盖不全
- 评分数据可能有偏差
- limit 限制导致遗漏

### 严重等级

⚠️ **中低**

### 缓解措施

1. **CandidateSet 中标注 `warnings`**：当搜索结果的评分远低于预期范围时，添加 warning
2. **回答模板中加入置信度声明**："根据已有数据，附近评分最高的两家是..."
3. **渐进搜索策略**：第一轮获取 top N+2，第二轮筛选确认

## 6.5 SessionState 污染

### 问题

同一 session 中，上一轮的 `last_candidate_set` 可能影响当前轮：
- 用户上一轮搜了火锅，这一轮问 KTV
- context_recovery 恢复火锅的候选去回答 KTV 的问题

### 严重等级

⚠️ **中**

### 缓解措施

1. **CandidateSet 只在同类型的候选之间共享**：检查 `candidate_set.original_spec.category` 是否与当前查询匹配
2. **SessionState 写入规则**：
   - `last_candidate_spec` 只在新查询有明确 candidate_spec 时覆盖
   - refine 时不覆盖（保留原始 spec）
   - 切换品类时清空
3. **context_recovery 判断**：检查上次推荐列表是否与当前查询品类一致

## 6.6 evidence_cache 过期风险

### P2 引入 evidence_cache 后

```
第一轮：获取 shop_A 的 get_coupon_list 结果 → 缓存
第二轮：用户问 shop_A 的问题 → 使用缓存的 coupon_list
        但 shop_A 的优惠券可能已经变了
```

### 严重等级

⬜ **低**

### 缓解措施

1. **evidence_cache 只在同一 session 内有效**
2. **缓存 TTL = 当前轮次**：跨轮后不自动使用缓存
3. **显式引用时才使用缓存**：用户说"刚才那家"等
4. **缓存键包含 tool_name + shop_id + 参数哈希**

## 6.7 `as any` / 类型安全回归

### 问题

`candidate_source` 等新字段在 graph_builder.py 中通过 `state.get("candidate_source", "")` 访问，
类型安全依赖 `GraphState` 的 TypedDict 定义或运行时校验。

### 严重等级

⬜ **低**（如果严格保持类型安全）

### 缓解措施

1. 在 `GraphState` 的 TypedDict/类型声明中加入新字段
2. 不允许使用 `state.get("candidate_source")` 返回 `Any`，使用有类型的 accessor
3. `lsp_diagnostics` 确保 0 类型错误

---

## 6.8 工具执行预算增长

### 问题

当前 recommendation 路径的 tool_calls 数：
- search_shops: 1
- hidden_calls: get_shop_cards(N) + get_shop_review_summary(N) ≈ 2N
- facet_calls: 约 N-5

总计约 3N+1 个 tool_calls（N=推荐列表长度，通常 5-8）

**discovery comparison 路径的 tool_calls 数**：
- search_shops: 1（候选发现）
- get_shop_detail(N) + get_coupon_list(N) + check_open_status(N) ≈ 3N（N=候选数，2-5）

如果两轮都执行，数量可能翻倍。

### 严重等级

⬜ **低**

### 缓解措施

1. **evidence_needs 控制 tool_calls 上限**：不是所有证据维度都获取，只获取需要的
2. **工具执行在同一个 batch 中**：search_shops 和 evidence 在同一次 `tool_execute` 的 `remaining_specs` 中
3. **批量执行的 concurrency 通过 asyncio.Semaphore(8) 控制**，不会过载

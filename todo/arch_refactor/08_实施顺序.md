# 8. 实施顺序

> 实施顺序服务于一个目标：先把 P0 写清楚并独立落地，再进入 P1，再进入 P2。不得跨阶段混改。

---

## 8.1 总体路线图

```text
第一轮：只改文档
第二轮：只实现 P0
第三轮：P0 通过后进入 P1
第四轮：P1 通过后进入 P2
```

```text
P0：LocalLifeGoalDraft + CandidateSet + CandidateReview
→ P1：EvidencePlanner + EvidenceReview
→ P2：GoalPlanner + DecisionPlanner + DecisionReview + Replan
```

实施纪律：

1. 第一轮只允许改文档
2. 第二轮只允许实现 P0
3. P0 通过后才允许 P1
4. P1 通过后才允许 P2
5. 不允许一次性完成 P0/P1/P2

---

## 8.2 P0：最小落地

### 目标

1. 新增 `CandidateSpec / ResolvedCandidate / CandidateSet`
2. 新增轻量 `LocalLifeGoalDraft`
3. 新增 `CandidateResolver`
4. 重构 `_h_target_resolve` 为薄调度层
5. 前置新增 `review_policy.py`
6. 前置标准化 `ToolResult`
7. 新增 `CandidateReview`
8. 写入 `review_results.candidate_review`

### 具体步骤

1. 定义 Candidate / Goal / ToolResult 相关 schema
   - 产出：枚举和 dataclass 稳定
   - 验证：不再依赖自由字符串
2. 引入 `LocalLifeGoalDraft`
   - 产出：`SemanticFrame → LocalLifeGoalDraft → CandidateSpec`
   - 验证：`task_type` 不再作为唯一事实源
3. 定义 `review_policy.py`
   - 产出：`ReviewStage / ReviewStatus / NextAction / SufficiencyCheckResult`
   - 验证：CandidateReview 不再使用临时自由字符串
4. 标准化 `ToolResult`
   - 产出：显式 `status / error_type / retriable / source`
   - 验证：后续 Review 不再依赖隐式错误约定
5. 引入 `CandidateResolver`
   - 产出：`explicit / context / discovery / mixed` 解析能力
   - 验证：能稳定输出 `CandidateSet`
6. 重构 `_h_target_resolve`
   - 产出：从大函数降为薄调度层
   - 验证：旧 explicit comparison / recommendation / single_shop_query 不回归
7. 新增 `CandidateReview`
   - 产出：最小 sufficiency Gate
   - 验证：候选不足、超上限、重复去重后不足时都能拦截
8. 写入 `review_results.candidate_review`
   - 产出：trace 中可回放候选阶段决策
   - 验证：端到端 trace 可见 `stage / status / next_action`
   - 补充：`next_action=finish` 只表示候选阶段通过，可继续进入 `EvidencePlanner` 或旧 planner 兼容链路

### P0 实施约束

1. 不允许继续在 `graph_builder.py` 追加零散业务特判
2. 不允许把 discovery comparison 修回旧 `target_resolve` 大函数
3. 不允许在 `comparison_planner` 临时判断候选是否足够
4. 不允许用关键词规则覆盖 LLM 的核心语义结论
5. 不允许修改 `top_intent_router`
6. 不允许改变非 `local_life` 直达 `emit_response` 链路
7. P0 不允许真实跳转到 `expand_search / replan_evidence` 等未实现节点
8. 候选超限时，如允许自动裁剪，则继续执行并写入 trimming trace；如不允许自动裁剪，则走 `clarify`

### P0 完成标准

1. “对比附近评分最高的两家 KTV，看看谁的优惠券多，营业状态如何”进入 discovery CandidateSet，不要求补店名
2. 只找到 1 家时不能继续比较
3. 对比 10 家时触发 `max_allowed`
4. mixed candidate 去重后不足 2 家时不能比较
5. `candidate_review` 写入 trace
6. explicit comparison 不回归
7. recommendation 不回归
8. single_shop_query 不回归
9. 非 `local_life` 仍直接 `emit_response`
10. `top_intent_router` 行为不变
11. P0 端到端 trace 验收通过后才能进入 P1
12. 候选不足时必须是 `NEED_MORE_CANDIDATES + CLARIFY/FALLBACK`，P0 不得提前引入 `EXPAND_SEARCH`

---

## 8.3 P1：EvidencePlanner + EvidenceReview

### 目标

1. 用 `EvidencePlanner` 统一生成 ToolPlan
2. `facet_plan / comparison_planner` 改为兼容壳
3. 增加 `EvidenceReview`
4. 区分 required / optional facet
5. 区分 `ok / empty / unknown / failed`
6. 支持 `can_degrade`
7. 防止 `unknown_as_false`
8. 防止 `failed_as_empty`

### 完成标准

1. A coupon ok，B coupon unknown 时不能说 A 一定更优惠
2. `check_open_status failed` 时不能说未营业
3. `get_coupon_list failed` 时不能说没有券
4. required facet unknown 时进入 `can_degrade / fallback / replan_evidence`
5. optional facet 缺失时允许降级回答，但必须说明未查询或无法确认
6. `ToolResult.status` 以 `ToolStatus` 枚举形式进入 `EvidenceReview`
7. `unknown_as_false / failed_as_empty` 验收通过后才能进入 P2

---

## 8.4 P2：GoalPlanner + DecisionPlanner + DecisionReview + Replan

### 目标

1. `GoalPlanner` 取代旧 `task_type` 硬分流的顶层控制力
2. `DecisionPlanner` 生成 `DecisionPlan`
3. `DecisionReview` 判断 `finish / replan / degrade / fallback`
4. 支持 `next_goal`
5. 支持 `replan_evidence`
6. 支持 `expand_search`
7. 扩展 `SessionState`

### 完成标准

1. `GoalPlanner / DecisionPlanner / DecisionReview` 真正接管旧硬分流
2. `EvidenceReview.need_more_evidence` 能驱动 `replan_evidence`
3. `CandidateReview.need_more_candidates` 能驱动 `expand_search` 或 `clarify`
4. `DecisionReview` 能判断 `finish / degrade / fallback`
5. `SessionState` 增加 `last_candidate_set / active_goal / evidence_cache / review_results`
6. 旧 `facet_plan / comparison_planner` 降级为兼容壳或逐步删除

---

## 8.5 旧路由节点降级节奏

### P0

1. 不删除旧节点
2. 只拆 `_h_target_resolve`
3. 保持现有测试稳定
4. 不修改 `top_intent_router`
5. 非 `local_life` 仍直接 `emit_response`

### P1

1. `facet_plan / comparison_planner` 改为 `EvidencePlanner` 兼容壳
2. `route_task` 开始弱化
3. `task_plan` 逐步统一

### P2

全链路稳定后再删除或废弃：

1. `route_task`
2. `_route_task_plan`
3. `task_router.py` 中按 `task_type` 的硬分流
4. `facet_plan`
5. `comparison_planner`
6. `answer_plan_build` 旧逻辑
7. `target_resolve` 中大量 recommendation / comparison 特判

---

## 8.6 Failure Handling / Retry 落地顺序

### 第一阶段先做

1. 明确 `ToolResult.status`
2. 明确 `SufficiencyCheckResult.status / next_action`
3. 明确 Review 与 Retry 边界

### 第二阶段再做

1. 在 `ToolExecute` 侧增加有限 retry
2. 在 `AnswerVerifier` 侧增加有限 rewrite

### 明确不做

1. 不对语义不足做 retry
2. 不对候选不足做 retry
3. 不对 unsupported 做 retry

---

## 8.7 每阶段验证纪律

1. 每一阶段都必须先跑单元测试，再跑端到端测试
2. 端到端测试必须断言 `trace`，不允许只看 `final_response`
3. 任何 bug 修复必须先定位到：
   - `SemanticFrame`
   - `LocalLifeGoalDraft`
   - `CandidateSpec`
   - `CandidateResolver`
   - `CandidateReview`
   - `EvidenceReview`
   - `DecisionReview`
   - `AnswerVerifier`
4. 不允许直接在 `graph_builder.py` 继续追加特殊 case

---

## 8.8 回退策略

如果任一阶段发现兼容性问题，按以下顺序回退：

1. 保留旧路由，只让新链路处理新增 discovery comparison 分支
2. 关闭新 Review Gate 的强制生效范围，先记录 trace 再观察
3. 暂缓删除旧节点，维持兼容壳
4. 若 P2 风险过大，先冻结在 P1，不强推多轮 replan

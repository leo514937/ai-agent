# 7. 测试计划

> 测试目标不再只是“CandidateSet 跑通”，而是验证 P0/P1/P2 的阶段边界是否真的稳定，且不会把未实现动作、旧 `task_type` 绑架和 fallback 语义覆盖带入代码实现。

---

## 7.1 测试策略

### 分层目标

| 层级 | 关注点 | 目标 |
|---|---|---|
| 单元测试 | 单个 Review / Planner / Policy / Schema | 规则判断稳定、枚举输出稳定 |
| 组件测试 | 单个 graph node handler | 节点职责不串位 |
| 集成测试 | Candidate → Evidence → Decision 子链路 | `next_action` 传递正确 |
| 端到端测试 | 主链路全流程 | 不会“执行完直接回答” |
| 回归测试 | 现有 explicit comparison / recommendation / single_shop_query | 新改造不破坏已有可用路径 |
| 直达测试 | 非 `local_life` 分支 | 新改造不污染 `top_intent_router → emit_response` 直达链路 |

### 本轮文档整改后的测试重点

1. CandidateReview 是否能拦截候选不足和超上限
2. EvidenceReview 是否能拦截 `unknown_as_false`、`failed_as_empty`
3. DecisionReview 是否能决定 `finish / replan / degrade / fallback`
4. AnswerVerifier 是否仍只做最终事实校验，而不替代过程 Review
5. Retry Policy 是否只用于 transient failure
6. 非 `local_life` 是否仍直接 `emit_response`
7. `task_type` 是否已降为兼容字段，不再绑架 CandidateSet 新链路
8. fallback 是否只补齐字段且正确写入 trace

### 测试断言要求

测试断言不能只看最终话术。

必须按层断言以下结构化结果：

1. `semantic_source`
2. `candidate_source`
3. `candidate_source_origin`
4. `fallback_reason`
5. `CandidateSet`
6. `review_results`
7. `next_action`
8. `ToolPlan`
9. `EvidencePack`
10. `AnswerVerifier` 结果
11. `trace`

## 7.2 LocalLifeGoalDraft / 枚举 / fallback 测试

| # | 场景 | 预期 |
|---|---|---|
| 1 | `SemanticFrame` 提供 `candidate_source / candidate_limit / evidence_needs` | `LocalLifeGoalDraft` 优先继承 LLM 字段 |
| 2 | `task_type` 与 LLM 字段冲突 | `task_type` 只作兼容，不覆盖核心字段 |
| 3 | `candidate_limit=None` 且 comparison | 默认补为 2 |
| 4 | `candidate_limit=None` 且 recommendation | 默认补为 3 |
| 5 | `candidate_limit=None` 且 single_shop_query | 默认补为 1 |
| 6 | fallback 参与补齐 | 写入 `semantic_source / candidate_source_origin / fallback_reason` |
| 7 | fallback 尝试覆盖 `candidate_source` 或核心意图 | 被拒绝或保留 LLM 结果 |
| 8 | Candidate 状态枚举序列化/反序列化 | 不出现自由字符串漂移 |

## 7.3 CandidateReview 测试

| # | 场景 | 预期 |
|---|---|---|
| 1 | discovery comparison 找到 2 家 | `status=enough`, `next_action=finish` |
| 2 | discovery comparison 只找到 1 家 | `status=need_more_candidates`，P0 中只允许 `clarify/fallback` |
| 3 | 对比 10 家但 `max_allowed=5` 且允许自动裁剪 | `next_action=finish`，并写入 `trimmed/original_count/kept_count` |
| 4 | 对比 10 家但 `max_allowed=5` 且不允许自动裁剪 | `next_action=clarify` |
| 5 | mixed candidate 存在重复 `shop_id` | 去重后重新检查数量 |
| 6 | 去重后不足 2 家 | 不能继续比较 |
| 7 | 单店查询解析出多个候选 | `status=need_clarification` |
| 8 | discovery comparison 无结果 | `clarify / fallback` |
| 9 | P0 输出 `expand_search` | 判定为非法阶段输出 |

### 组件测试

1. `CandidateResolver → CandidateReview → EvidencePlanner` 串联时，`need_more_candidates` 不应继续生成比较型 ToolPlan
2. `review_results.candidate_review` 必须写入 `GraphState` 与 trace
3. `CandidateSet / CandidateReview` 只应在 `local_life` 分支出现
4. `next_action=finish` 只表示进入 `EvidencePlanner` 或旧 planner 兼容链路，不表示直接生成最终回答

## 7.4 EvidenceReview 测试

| # | 场景 | 预期 |
|---|---|---|
| 1 | `coupon ok + coupon ok` | `enough` |
| 2 | `coupon ok + coupon empty` | `enough`，允许比较 |
| 3 | `coupon ok + coupon unknown` | `can_degrade`，不能确定 winner |
| 4 | `coupon failed` | 不能当 `empty` |
| 5 | `open_status failed` | 不能说未营业 |
| 6 | optional facet 缺失 | 可以降级 |
| 7 | required facet 缺失 | `need_more_evidence` 或 `can_degrade` |
| 8 | timeout 后 retry 仍失败 | `failed_tools` 或 `unknown_facets` 有记录 |

### 集成测试

1. `ToolExecute → EvidenceBuild → EvidenceReview` 能正确传递 `ToolResult.status`
2. `EvidenceReview.need_more_evidence` 时，后续应进入 `replan_evidence`，而不是直接生成 AnswerPlan

---

## 7.5 DecisionReview 测试

| # | 场景 | 预期 |
|---|---|---|
| 1 | Evidence 足够 | `finish` |
| 2 | Evidence 缺失但可降级 | `degrade_answer` |
| 3 | Evidence 缺失且核心问题无法回答 | `fallback` 或 `clarify` |
| 4 | `EvidenceReview.need_more_evidence` | `replan_evidence` |
| 5 | DecisionPlan 给出 winner 但证据不足 | 被拦截 |
| 6 | Candidate 足够但 required facet 全 unknown | 不能进入确定性回答 |

## 7.6 AnswerVerifier 测试

| # | 场景 | 预期 |
|---|---|---|
| 1 | `unknown_as_false` | 拦截 |
| 2 | `failed_as_empty` | 拦截 |
| 3 | `shop_id_mismatch` | 拦截 |
| 4 | `ranking_changed_by_llm` | 拦截 |
| 5 | 提到未查询店铺 | 拦截 |
| 6 | required facet 遗漏 | rewrite 或拦截 |
| 7 | rewrite 不新增事实 | 通过 |
| 8 | rewrite 超过 1-2 次仍失败 | `fallback` |

边界确认：

1. 它确实还能做最终事实校验
2. 它没有偷偷替代过程 Review 去决定“要不要补查”

## 7.7 Retry Policy 测试

| # | 场景 | 预期 |
|---|---|---|
| 1 | Tool timeout | retry 1-2 次 |
| 2 | retry 后仍失败 | 标记 `failed / unknown`，交 Review 决策 |
| 3 | 候选不足 | 不 retry |
| 4 | unsupported | 不 retry |
| 5 | `plan_validator` 拦截非法工具 | 不进入 ToolExecute |
| 6 | AnswerVerifier rewrite | 最多 1-2 次 |
| 7 | GoalPlanner JSON parse error | 可少量 retry，仍失败走澄清或规则兜底 |
| 8 | P0 `CandidateReview` 输出 `expand_search` | 判定为非法阶段输出，不允许进入 graph 跳转 |

## 7.9 端到端标杆测试

| # | 用例 | 目标 |
|---|---|---|
| 1 | “对比附近评分最高的两家 KTV，看看谁的优惠券多，营业状态如何” | 正常进入 discovery CandidateSet，不要求补店名 |
| 2 | “对比附近评分最高的两家 KTV” 且只找到 1 家 | CandidateReview 拦截，不能强行比较 |
| 3 | “这两家谁优惠券多？” 且一方 `unknown` | EvidenceReview / DecisionReview 阻止确定性 winner |
| 4 | “这家现在营业吗？” 且工具 `failed` | 不能说未营业，只能降级或 fallback |
| 5 | “附近评分最高的 10 家火锅都详细对比一下” | 触发 `max_allowed`，不能直接生成 10 家 ToolPlan |
| 6 | “第一家和海底捞比” 且两者实际同店 | 去重后数量不足，不能继续比较 |
| 7 | “帮我订座” | GoalReview 返回 `unsupported`，不伪造成功 |

## 7.10 与 P0 / P1 / P2 的对应关系

### P0 验收

1. “对比附近评分最高的两家 KTV，看看谁的优惠券多，营业状态如何”
   - 必须进入 discovery CandidateSet
   - 不允许回复“请补充另一家店名”
   - 找到 2 家才继续
   - 只找到 1 家时 CandidateReview 拦截
2. “附近评分最高的 10 家火锅都详细对比”
   - 必须触发 `max_allowed`
   - 不能直接生成 10 家详细 ToolPlan
3. “第一家和海底捞比”
   - 如果恢复后是同一家，去重后不足 2 家，不能继续比较
4. explicit comparison 不回归
5. recommendation 不回归
6. single_shop_query 不回归
7. 非 `local_life` 不进入 `CandidateResolver`、不生成 `CandidateSet`、不写 `candidate_review`
8. P0 只允许 `finish / clarify / fallback`，不输出 dangling `next_action`
9. `finish` 只表示候选阶段通过，可以进入 `EvidencePlanner` 或旧 planner 兼容链路

### P1 验收

1. A 店 coupon ok，B 店 coupon unknown，不能说 A 一定更优惠
2. `check_open_status failed`，不能说未营业
3. `get_coupon_list failed`，不能说没有券
4. required facet unknown 时必须进入 `can_degrade / fallback / replan_evidence`
5. optional facet 缺失时可以降级回答，但必须说明未查询或无法确认
6. `ToolResult.status` 必须进入 `EvidenceReview`

### P2 验收

1. `GoalPlanner / DecisionPlanner / DecisionReview` 真正接管旧 `task_type` 硬分流
2. `EvidenceReview.need_more_evidence` 能驱动 `replan_evidence`
3. `CandidateReview.need_more_candidates` 能驱动 `expand_search` 或 `clarify`
4. `DecisionReview` 能判断 `finish / degrade / fallback`
5. `SessionState` 增加 `last_candidate_set / active_goal / evidence_cache / review_results`
6. 旧 `facet_plan / comparison_planner` 降级为兼容壳或逐步删除

---

## 7.11 最终验收标准

1. Agent 不会在 CandidateSet 不足时强行比较
2. Agent 不会在 required evidence unknown 时输出确定性结论
3. Agent 不会把 `failed` 当 `empty`
4. Agent 能判断“信息足够，可以回答”
5. Agent 能判断“信息不足，需要补查”
6. Agent 能判断“候选不足，需要扩搜或澄清”
7. Agent 能判断“工具不支持，需要说明能力边界”
8. Agent 能在部分信息缺失时降级回答，并明确说明未知项
9. Agent 不会让 LLM 自己判断“差不多够了”
10. `AnswerVerifier` 仍作为最终事实校验，不替代过程 Review
11. Review 结果必须写入 trace
12. `next_action` 必须是枚举，不能是自由字符串
13. Review 不允许修改 `ToolResult / EvidencePack` 事实
14. 回答不能提到未查询、未绑定 `shop_id` 的店铺
15. Retry 只用于 transient failure，不用于语义不足
16. `ToolCallGateway` 仍是唯一工具执行入口
17. `plan_validator` 能阻止非法 ToolPlan 进入 ToolExecute
18. 旧路由节点逐步降级，不允许新旧职责混乱
19. `top_intent_router` 在 P0 不被修改
20. 非 `local_life` 仍直接 `emit_response`
21. `CandidateSet / CandidateReview` 不污染非本地生活分支
22. `candidate_limit` 默认值策略统一为 `None + GoalPolicy/GoalDraft`
23. P0 不输出未实现 `next_action`
24. `task_type` 不再作为本地生活新链路的唯一事实源
25. `slot_extractor` fallback 不静默覆盖 LLM 核心语义
26. CandidateReview 的 `finish` 不被误用为“最终回答完成”

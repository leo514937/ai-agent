# 2. 当前架构问题分析

---

## 2.1 固定路由依赖

### 问题位置

`task_plan` → `route_task()` → `_route_task_plan()` 按 `task_type` 硬编码分流：

```python
# graph_builder.py L2205-2211
def _route_task_plan(state: GraphState) -> str:
    task_type = state.get("task_type")
    task_type_value = task_type.value if hasattr(task_type, "value") else str(task_type or "")
    if task_type_value == TaskType.comparison.value:
        return "comparison_planner"
    return "facet_plan"
```

`task_router.py` 同样硬编码：

```python
if task_type == TaskType.comparison.value:
    return TaskType.comparison.value if resolved_status == "RESOLVED" else TaskType.clarification_reply.value
```

**后果**：comparison 必须在路由前就有 RESOLVED 状态，否则被降级为 clarification_reply。

### 深层问题

- recommendation / comparison / single_shop_query 三路**从 task_plan 开始完全分离**
- 没有共享的"候选发现→候选消费"层
- comparison_planner 接收 `comparison_targets`（shop_id 列表），**不关心这些 shop_id 怎么来的**
- facet_planner 只处理单店的 facets

## 2.2 target_resolve 过早要求 shop_id

### 问题位置

`_h_target_resolve`（graph_builder.py L889-1205）是**最大的规则堆叠**：

```python
def _h_target_resolve(state: GraphState) -> dict:
    # 约 300 行，包含：
    # - recommendation 合成（~20 行）
    # - recommendation_refine 检测（~30 行）
    # - comparison 直接解析（~30 行）
    # - comparison 逐店 resolve（~100 行）
    # - len(resolved_targets) < 2 阻塞（~10 行）
    # - AMBIGUOUS 候选列表构建（~80 行）
```

关键阻塞点（L1199-1205）：

```python
if len(resolved_targets) < 2:
    final_response = _comparison_reason_response("comparison_requires_at_least_two_shops")
    return {
        "resolve_shop_result": ResolveShopResult(status="NOT_FOUND", ...),
        "final_response": final_response,
        ...
    }
```

**这个校验错误覆盖了 discovery-based comparison**：
- explicit 比较（"海底捞和山城一锅"）→ resolved_targets ≥ 2 ✅
- discovery 比较（"评分最高的两家KTV"）→ resolved_targets = 0 ❌ 被阻塞

### 根本原因

target_resolve 承担了过多职责：
1. 判断是否需要比较
2. 解析 explicit shop_id
3. 从上下文恢复引用
4. **校验候选数量**

这些应该在**不同的阶段、由不同的模块**完成。

## 2.3 规则堆叠风险

### _h_target_resolve 中的特殊逻辑

```python
# ★ 前 recommendation 但没有 explicit shop + 有 refs → 仍走 comparison
# ★ "便宜一点的呢" 被硬编码检测为 recommendation_refine
# ★ 隐式"对比推荐列表中的几家"靠 context_recovery 的 resolve_references()
# ★ 每个特殊 case 都是 if/elif 堆叠
```

**当前已堆叠的特殊 case 清单**：

| case | 检测条件 | 处理方式 |
|------|---------|---------|
| 标准 recommendation | task_type=recommendation | 合成 RESOLVED |
| recommendation refine | 无 shop+无 ref+有前序推荐 | 合成 RESOLVED + 强制改 task_type |
| explicit comparison | merchant_mentions ≥ 2 | 直接 resolve 并返回 |
| 带引用的 comparison | ordinal/deictic refs | resolve_references() 恢复 |
| 模糊 comparison | 有 unresolved_targets | 逐个 resolve_shop() |
| 混合 comparison | 部分 resolved + 部分 unresolved | 两者结合 |
| discovery comparison | 只有候选条件无店名 | ❌ 全部阻塞 |

**每次新增一个 case，函数复杂度非线性增长。** 当前 `_h_target_resolve` 约 300 行，是 graph_builder 中最长的函数。

---

## 2.4 discovery-based comparison 被误澄清

### 完整 fallback 链路

用户输入："对比附近评分最高的两家KTV，看看谁的优惠券多，营业状态如何"

```
slot_extractor:
  merchant_mentions = []                    # 没有店名
  comparison_targets = []                     # 没有可解析的 comparison_targets
  ordinal_references = []
  deictic_references = []
  query_terms = ["ktv"]                       # 只在 ranking_signals 中
  need_context = True                         # 因为没有 mentions/refs

target_resolve:
  explicit_mentions = []
  has_structured_refs = False
  → 进入 comparison 分支
  resolved_targets = []                       # 无任何可解析的目标
  unresolved_targets = ["对比附近评分最高的两家KTV"]  # 整句当作查询
  resolve_shop("对比附近评分最高的两家KTV") → NOT_FOUND
  len(resolved_targets) < 2 → true
  → return "对比至少需要两家不同的店，请补充另一家店名。"
```

### 核心矛盾

用户在说"对比 **XXX 条件的** 两家店"——**条件**（附近、KTV、评分最高）在 `ranking_signals` 和 `hard_constraints` 中，
但 target_resolve 只看 `merchant_mentions` / `comparison_targets` / `ordinal_references` / `deictic_references`，
**完全忽略了 ranking_signals 中的候选条件**。

## 2.5 上下文引用恢复的缺陷

### reference_resolver.py 的 _candidate_pool

```python
def _candidate_pool(session_state):
    comparison_targets = [...]       # 上一次比较的目标
    if resolved_comparison: return resolved_comparison
    return last_recommendation_list  # 上一次推荐列表
```

**问题**：
- 只从上一次的 `comparison_targets` 或 `last_recommendation_list` 恢复
- 没有 `last_candidate_set` 来保留**完整的候选元信息**（评分、距离、来源）
- "刚才推荐的几家"在 `_resolve_multi_deictic` 中使用 pool 的前 N 个，但 pool 只含 shop_id/shop_name

### _h_target_resolve 中的上下文检测

```python
# L915-937: 无 explicit shop + 无 ref + 有前序推荐 → recommendation_refine
```
这里的 `prev_recs` 只检查 `last_recommendation_list` 是否有内容，
**不检查候选是否与当前查询的约束匹配**。

## 2.6 状态管理的缺口

### SessionState 缺少的字段

| 需要 | 当前有 | 影响 |
|------|-------|------|
| `last_candidate_spec` | ❌ 无 | refine 时丢失原始搜索条件 |
| `last_candidate_set` | ❌ 无 | 无法恢复完整的候选列表 |
| `active_candidate_spec` | ❌ 无 | 无法判断用户是 refine 还是新查询 |
| `candidate_pool_by_source` | ❌ 无 | 无法追溯候选来源（explicit/discovery/context） |
| `discovery_pending` | ❌ 无 | discovery 候选正在获取中的状态无法传递 |

### 串店风险

`_h_target_resolve` 中 `_resolve_recommendation_spec` 使用 `$search_result[0].shop_id` 占位符，
在执行时才绑定 shop_id。如果 search_shops 结果变化（多轮执行），后续工具可能绑定不同的店。

## 2.7 EvidencePack 的缺口

### 当前 comparison_evidence 的构建流程

```
_build_comparison_evidence()  # evidence_builder.py L249
  → 从 comparison_targets 获取 targets
  → 从 tool_results 逐个填充 row
  → 构建 cells + dimension_winners + overall_ranked
```

**问题**：
- discovery 候选的**候选发现阶段结果**（search_shops 返回的排名、评分）没有进入 ComparisonMatrix
- comparison 回答时只能基于工具结果，但如果候选本身就有问题（搜索质量差），回答会失真
- 没有专门的 `ComparisonMatrixBuilder`，逻辑散落在 `_build_comparison_evidence` 中

### 回答中的 unknow 风险

`_facet_claims_for_status()` 定义了一些 forbidden claims，
但 `unknown` 状态在回答模板中可能被忽略或误解——当前靠 `AnswerVerifier` 事后校验，
而不是从 EvidencePack 层面确保 unknown 不可回答。

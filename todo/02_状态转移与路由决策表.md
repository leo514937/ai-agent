# 00.5 状态转移与路由决策表

定义各核心节点不同返回状态下的下一跳、Session 写入规则与 Emit（发出回答）行为。

| 当前节点 | 状态 | 下一步 | 是否写入 Session | 是否可回答 (Emit) |
| --- | --- | --- | --- | --- |
| `semantic_parse` | `JSON parse fail` | `clarification` (若重试失败) | 否 | 是 |
| `semantic_parse` | `task_type缺失/越界` | `frame_validator` 修正或拒 | 否 | 是 |
| `resolve_shop` | `RESOLVED` | `task_plan` | `current_shop` 可写 | 否 |
| `resolve_shop` | `AMBIGUOUS` | `write pending_clarification -> clarify_response` | `pending_clarification` 写入 | 是 |
| `resolve_shop` | `LOW_CONFIDENCE` | `clarify_response` | `pending_clarification` 写入 | 是 |
| `resolve_shop` | `NOT_FOUND` | `no_answer` / `suggest_search` | 不写 `current_shop` | 是 |
| `tool_execute` | `required_tool unknown / failed` | `fallback_answer` | 不更新 | 是 |
| `tool_execute` | `optional_tool unknown / failed` | `continue evidence_build` | 记录 unknown 传下游 | 是 |
| `tool_execute` | `circuit_open` | `fallback_answer` | 不更新 | 是 |

## 2. 状态写入策略表 (Session Write Strategy)

明确每种回答结束后到底写什么、不写什么、清什么，杜绝状态污染。

| 场景 | 写 current_shop | 写 last_recommendation_list | 写 pending_clarification | 清 pending |
| --- | --- | --- | --- | --- |
| 单店查券成功 | 是 | 否 | 否 | 是 |
| 单店多 facet 成功 | 是 | 否 | 否 | 是 |
| 附近推荐成功 | 否 | 是 | 否 | 是 |
| 多店对比成功 | 否 | 可选 (一般不写) | 否 | 是 |
| resolve_shop AMBIGUOUS | 否 | 不变 | 是 | 否 |
| 用户澄清成功 | 视原任务而定 | 视原任务而定 | 否 | 是 |
| 用户换话题 | 视新任务而定 | 视新任务而定 | 否 | 是 |
| 工具 unknown / failed | 不更新目标 | 不更新推荐结果 | 否 | 视情况而定 |

## 阶段完成后的收尾

- 检查所有状态是否都有下一跳，尤其是 `clarification / fallback / emit` 分支。
- 确认没有“状态有了但下一步没写”的断点。

# 01 语义理解层全面检验

> 适用范围：`semantic/intent_parser.py`、`semantic/top_intent_router.py`、语义帧 schema、LLM parser/fallback、prompt contract、语义解析测试与评估集。

## 0. 命名纠偏与功能判断

| 项目 | 结论 |
|---|---|
| 模块名写错 | `ScenarioPlanner` 不是语义层的真实模块名；真实代码入口是 `semantic/intent_parser.py` 和 `semantic/top_intent_router.py`。 |
| 功能等价存在 | 是。顶层意图路由、语义帧解析、LLM/fallback、schema 校验都已有对应实现。 |
| 真缺口 / 细节不到位 | 当前没有证据表明需要新增单独的语义规划模块；文档里的主要问题是把“语义理解”误写成了 `ScenarioPlanner` 这种上层抽象名。 |

## 1. 检验目标

语义理解层要证明三件事：

1. 用户自然语言能被稳定转换为结构化语义帧。
2. LLM 可以主导理解，但不能输出失控字段、非法枚举或绕过后续规划层。
3. 规则 fallback 只作为降级和安全兜底，而不是偷偷覆盖 LLM 主路径。

本层的核心验收问题是：

- 顶层意图是否能正确区分本地生活、闲聊、能力介绍、越界请求、未知问题？
- 本地生活语义是否能提取 intent、facet、shop mention、constraints、comparison targets、recommendation need？
- 多 facet 查询是否能保持结构化，而不是压成一段文本？
- LLM parse 失败、低置信度、非法 JSON、schema 不合法时，是否有可观测 fallback？
- 语义结果是否足够支持后续 planner，而不是后续节点再大量猜测？

## 2. 代码走查清单

重点检查以下文件和职责：

| 文件/模块 | 检查重点 | 风险 |
|---|---|---|
| `semantic/intent_parser.py` | 是否输出稳定 schema；facet 是否枚举化；LLM/fallback 标记是否完整 | LLM 输出漂移、字段污染 |
| `semantic/top_intent_router.py` | 是否只做顶层意图，不承担业务解析 | 顶层规则过多，抢二级语义职责 |
| `domain/schemas.py` | SemanticFrame 是否 forbid extra；枚举是否完整 | schema 松散导致下游污染 |
| `llm/prompts/*` | 是否明确 JSON-only、禁止编造、禁止执行工具 | LLM 越界 |
| `tests/test_prompt_contract.py` | prompt 与 schema 是否有契约测试 | prompt 改坏后无感知 |

## 3. AI Harness 检验重点

本层 harness 不能只测 happy path，需要覆盖 LLM 不稳定性。

### 3.1 必须具备的 fake LLM 类型

| Fake 类型 | 目的 |
|---|---|
| `SpyLLM` | 证明 LLM 是否被调用、调用几次、输入 prompt 是否正确 |
| `PoisonFallbackLLM` | 证明 fallback 没有偷偷接管主路径 |
| `MalformedJsonLLM` | 验证非 JSON 是否安全 fallback |
| `ExtraFieldsLLM` | 验证 schema 是否 forbid extra |
| `InvalidEnumLLM` | 验证非法 intent/facet 是否被拒绝 |
| `LowConfidenceLLM` | 验证低置信度是否澄清或 fallback |
| `ContradictoryLLM` | 验证冲突语义是否由 validator/后续 planner 收敛 |

### 3.2 Harness 必须记录的字段

建议每次语义解析输出都记录：

```text
semantic_source: llm / rule_based / fallback_rules / fake_llm / real_llm
llm_called: true / false
llm_backend: openrouter / mock / rule_based
parse_status: ok / fallback / schema_error / json_error / low_confidence
fallback_reason: string
intent: enum
facets: list
constraints: object
shop_mentions: list
comparison_targets: list
recommendation_need: object
```

## 4. Context 检验重点

语义理解层不能直接乱读历史上下文，但必须能接收上下文输入。

检查点：

1. 当前轮显式信息优先于历史上下文。
2. 多轮追问如“便宜一点的呢”“那这家呢”“和海底捞比呢”能标记为 follow-up，而不是新独立查询。
3. 语义层只输出上下文需求或上下文引用，不直接篡改 session。
4. 语义层输出要区分：
   - 当前轮显式店铺
   - 历史推荐候选
   - pending clarification 候选
   - 用户序号选择
5. 语义层不得把 unresolved mention 直接当成 resolved shop_id。

## 5. 测试用例矩阵

| 场景 | 输入 | 期望 |
|---|---|---|
| 能力介绍 | `你有什么作用` | 顶层 intent=capability/help，不进本地生活工具链 |
| 单店 facet | `海底捞火锅(水晶城购物中心店）环境怎么样，有券吗` | shop mention + facets=environment,coupon |
| 推荐 | `附近有没有适合约会、现在营业、最好有券的火锅` | recommendation intent + scene=dating + open_now + coupon + cuisine=火锅 |
| 对比 | `海底捞和山城一锅哪个好` | comparison targets=2 |
| 多轮省略 | `便宜一点的呢` | follow_up=refine_recommendation，继承上轮推荐上下文 |
| 指代对比 | `这家和海底捞比呢` | follow_up=comparison，deictic target unresolved 或从 context 补齐 |
| 非 JSON | fake LLM 返回普通文本 | parse_status=json_error，fallback 可观测 |
| 额外字段 | fake LLM 返回未知字段 | schema_error 或字段被拒绝 |
| 非法枚举 | intent=`buy_ticket_now` | validator reject/fallback |
| 低置信度 | confidence=0.2 | clarify 或 fallback |

## 7. 通过标准

严格通过需要满足：

- LLM 主路径、规则 fallback、schema error、json error 都能被 trace 区分。
- SemanticFrame 字段稳定，非法字段不会污染后续 planner。
- 顶层路由不会把能力介绍、闲聊误送到本地生活工具链。
- 单店、推荐、对比、多轮省略都能输出足够结构化的语义帧。
- LLM 不能直接产出工具执行结果或用户最终回答。

## 8. 常见 P0/P1/P2

| 等级 | 问题 |
|---|---|
| P0 | LLM 语义层直接决定工具执行或编造工具结果 |
| P0 | SemanticFrame 允许任意 extra 字段并被下游信任 |
| P1 | 规则 fallback 覆盖 LLM 结果但 trace 看不出来 |
| P1 | 多轮省略不能标记 follow-up，导致上下文丢失 |
| P1 | 推荐/对比语义混淆，后续 planner 大量补救 |
| P2 | facet 命名不统一，测试只覆盖中文 happy path |

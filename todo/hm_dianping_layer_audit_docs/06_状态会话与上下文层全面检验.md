# 06 状态会话与上下文层全面检验

> 适用范围：`domain/graph_state.py`、状态转移表、`session/store.py` 中的 `InMemorySessionStore`、`target/clarification.py`、`target/context_recovery.py`、pending clarification、多轮指代、session read/write。

> 说明：这里没有单独的 `ClarificationAgent` 类，澄清与候选恢复由 `target/clarification.py` 中的函数和 `graph_builder.py` 节点协作完成。

## 0. 命名纠偏与功能判断

| 项目 | 结论 |
|---|---|
| 模块名写错 | `ClarificationAgent` 不是实际类名；状态字段里应使用 `comparison_targets`，不是 `last_comparison_targets`；trace 字段应使用 `reference_resolution_source`，不是 `context_resolution_source`。 |
| 功能等价存在 | 是。session 读写、pending clarification、指代恢复、对比补全、状态更新都能在现有模块找到对应实现。 |
| 真缺口 / 细节不到位 | 暂未发现必须新增独立会话/上下文模块的硬缺口；主要问题是文档里的抽象名称、字段名和真实代码不一致。 |

## 1. 检验目标

状态与会话层决定 Agent 是否真的能多轮对话。

必须证明：

1. 每轮开始能 load session，每轮结束能 save session。
2. 当前轮信息、历史推荐、pending clarification、用户选择之间有清晰优先级。
3. “这家”“第一个”“便宜一点的呢”“和海底捞比呢”能正确恢复上下文。
4. 换话题能清理或隔离旧上下文。
5. Context 不会越权替用户做选择。

## 2. 代码走查清单

| 文件/模块 | 检查重点 |
|---|---|
| `domain/graph_state.py` | 字段是否完整；是否区分 current/session/pending |
| `session/store.py` 中的 `InMemorySessionStore` | load/save 时机；session_id 隔离 |
| `target/clarification.py` | AMBIGUOUS 时写 pending；序号恢复 |
| `target/context_recovery.py` | 省略、指代、约束继承、对比补全 |
| `planning/state_update_planner.py` | 状态更新是否根据工具/解析状态正确进行 |
| `engine/graph_builder.py` | session 节点位置是否正确 |
| `observability/trace.py` | `reference_resolution_source` 是否可观测 |

## 3. Context 核心语义

建议明确以下上下文优先级：

```text
当前轮显式 shop_id / shop mention
→ pending clarification 用户选择
→ 当前轮显式约束
→ 上一轮推荐/对比候选
→ session persistent preference
→ 默认 mock 用户位置
```

不能做的事情：

- 多候选时默认选择第一家。
- 用户未明确选择时，把“这家”绑定到不唯一候选。
- 换话题后继续沿用旧候选。
- 把历史推荐候选当作真实最新工具结果。

## 4. AI Harness 检验重点

上下文层要用多轮 conversation harness，而不是单轮单测。

### 4.1 必备多轮脚本

| 脚本 | 轮次 | 期望 |
|---|---|---|
| 澄清恢复 | `海底捞怎么样` → 返回多候选 → `第一个` | 选中 pending 第一个 |
| 推荐收敛 | `附近火锅` → `便宜一点的呢` | 继承火锅候选，加价格约束 |
| 指代单店 | 推荐列表 → `这家有券吗` | 若唯一 anchor 则查券，否则澄清 |
| 指代对比 | 推荐列表 → `这家和海底捞比呢` | deictic 不唯一时澄清 |
| 换话题 | 火锅推荐 → `你有什么作用` | 清理/隔离本地生活 context |
| 序号越界 | 多候选 3 个 → `第 5 个` | 提示无该候选 |
| 约束覆盖 | `附近火锅` → `不要太贵` → `环境好一点` | 约束逐步更新 |

### 4.2 Harness 必须记录

```text
session_id
turn_id
loaded_session_snapshot
saved_session_snapshot
pending_clarification
last_recommendation_list
comparison_targets
reference_resolution_source
context_recovery_status
follow_up_kind
inherited_constraints
cleared_context_reason
```

## 5. 状态转移验收

重点检查以下状态转换：

| 条件 | 期望状态更新 |
|---|---|
| resolve_shop AMBIGUOUS | 写入 pending_clarification |
| 用户序号选择合法 | 清 pending，写 selected shop |
| 用户序号选择非法 | 保留 pending，提示重选 |
| 推荐成功 | 写 last_recommendation_list |
| 对比成功 | 写 comparison_targets |
| 工具失败 | 不覆盖有效历史上下文 |
| 换话题 | 清理或挂起本地生活上下文 |
| 新显式店铺 | 覆盖旧 deictic anchor |

## 8. 通过标准

严格通过需要满足：

- 多轮上下文恢复有系统性 harness。
- pending clarification 能写入、恢复、清理。
- 当前轮显式信息优先。
- 换话题不会误伤或污染。
- context source 可 trace。
- 上下文不会绕过 resolver / validator。

## 9. 常见 P0/P1/P2

| 等级 | 问题 |
|---|---|
| P0 | 上下文直接伪造 shop_id 或工具结果 |
| P1 | 多候选默认选第一家 |
| P1 | pending clarification 不清理或被误清理 |
| P1 | “推荐第一个”被换话题规则误伤 |
| P1 | 多 session 串话 |
| P2 | context source 只能事后推断 |

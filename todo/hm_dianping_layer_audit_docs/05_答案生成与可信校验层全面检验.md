# 05 答案生成与可信校验层全面检验

> 适用范围：`answer/llm_verbalizer.py`、`answer/b2_mini_verifier.py`、`answer/verifier.py`、`answer/generator.py`、`answer/final_response_builder.py`、Few-Shot prompt、模板 fallback、事实边界校验、最终回答契约。

> 说明：这里没有单独的 `composer` 模块；答案生成和降级输出主要在 `answer/generator.py` 与 `answer/final_response_builder.py`。

## 0. 命名纠偏与功能判断

| 项目 | 结论 |
|---|---|
| 模块名写错 | `composer` 不是实际模块名；“AnswerVerifier”也不是独立类，真实入口是 `answer/verifier.py` 的 `verify_answer` 和 `answer/b2_mini_verifier.py` 的 `B2MiniVerifier`。 |
| 功能等价存在 | 是。答案生成、LLM 表达、事实校验、模板 fallback 都有对应实现。 |
| 真缺口 / 细节不到位 | 当前更像是“抽象命名不准”，而不是功能缺失；若文档要求额外新增 `AnswerVerifier` 类，现有代码更适合补测试或补文档映射，而不是新造一层。 |

## 1. 检验目标

答案生成层要让回答自然、口语化、有场景感，同时不能突破事实边界。

必须证明：

1. LLM 只负责表达和组织语言，不负责创造事实。
2. 最终回答只基于 ToolResult / EvidencePack / DecisionPlan。
3. Verifier 能拦截店铺幻觉、属性越界、未知信息说谎、工具失败后装知道等问题。
4. LLM 生成失败或 verifier 不通过时有模板 fallback。
5. 用户能看到清晰、可信、不过度模板化的回答。

## 2. 代码走查清单

| 文件/模块 | 检查重点 |
|---|---|
| `answer/llm_verbalizer.py` | 输入是否只包含 grounded facts；是否禁止新增事实 |
| Few-Shot prompt | 是否示范“未知就说未知”“工具失败就说明” |
| `answer/b2_mini_verifier.py` 中的 `B2MiniVerifier` | 事实边界是否覆盖 |
| `answer/verifier.py` 中的 `verify_answer` 逻辑 | 是否逐 claim 绑定证据或做事实一致性检查 |
| `answer/generator.py` / `answer/final_response_builder.py` | verifier 失败后是否有可用降级答案 |
| `answer/generator.py` | 是否还存在大量硬编码模板拼接 |
| `agent.py` / `observability/trace.py` | 是否记录 `answer_source`、`answer_verify_passed`、`answer_verify_violations`、`answer_fallback_reason` |

## 3. AI Harness 检验重点

答案层是最需要 AI harness 的部分，因为 LLM 很容易“说得像真的”。

### 3.1 必备 fake verbalizer

| Fake LLM | 用途 |
|---|---|
| HonestLLM | 正常表达 grounded facts |
| HallucinatingShopLLM | 编造不存在店铺 |
| HallucinatingCouponLLM | 工具无券却说有券 |
| OverclaimLLM | 把 unknown 说成确定 |
| AttributeLeakLLM | 编造环境/服务/评分 |
| ToolFailureIgnoringLLM | 工具失败仍给确定答案 |
| LongVerboseLLM | 检查回答是否过长、信息密度低 |
| UnsafeStyleLLM | 检查是否违反风格或安全边界 |

### 3.2 Verifier 必测 claim

| Claim 类型 | 期望 |
|---|---|
| 店铺名称 | 必须来自 evidence |
| 优惠券 | 必须来自 coupon tool |
| 营业状态 | 必须来自 open_status tool |
| 距离/ETA | 必须来自 distance_eta tool |
| 评分/人均 | 必须来自 shop detail/review evidence |
| 推荐理由 | 必须能映射到证据或决策理由 |
| 不可用信息 | 应表达“暂无数据/没查到”，不能编造 |

## 4. Context 检验重点

答案层需要正确呈现上下文，不要把历史信息说成当前轮新查到的信息。

检查点：

1. 多轮追问回答要说明“基于刚才几家”。
2. 新增约束后要体现约束变化。
3. 澄清回答要列候选，不要直接替用户选。
4. 工具失败时要说明哪些信息暂时没查到。
5. 历史候选过期或换话题后不能继续引用。
6. 回答不能泄露内部 trace、prompt、debug 字段。

## 5. 测试用例矩阵

| 场景 | 期望 |
|---|---|
| grounded 正常推荐 | 自然表达，包含排序和理由 |
| 工具无券 | 不说“有券” |
| 营业状态 unknown | 表达不确定，不编造营业 |
| 距离工具失败 | 不给具体距离 |
| LLM 编造店铺 | verifier 拦截，fallback |
| LLM 编造 coupon | verifier 拦截，fallback |
| LLM 过度泛化 | verifier 或 linter 标记 |
| 对比回答 | 给 tradeoff，不绝对化 |
| 澄清回答 | 列候选并请用户选择 |
| 模板 fallback | 可读、事实安全 |

## 6. Verifier 检验标准

建议检查 5 类边界：

1. **店铺实体边界**：回答中所有店铺必须来自候选或工具结果。
2. **属性事实边界**：券、营业、距离、评分、价格必须有证据。
3. **未知信息边界**：unknown/empty/failed 不得被说成确定。
4. **决策理由边界**：推荐理由必须来自 score breakdown / evidence。
5. **上下文边界**：不得把上一轮过期候选当成本轮结果。

## 8. 通过标准

严格通过需要满足：

- LLM verbalizer 不直接接触未验证工具 raw data。
- Verifier 能拦截主要幻觉类型。
- verifier 失败后 fallback 可用。
- 回答自然，不是全模板拼接。
- unknown/failed/empty 有诚实表达。
- 多轮上下文在回答中不混乱。

## 9. 常见 P0/P1/P2

| 等级 | 问题 |
|---|---|
| P0 | 工具失败后 LLM 编造事实并通过 |
| P0 | 回答出现 evidence 中不存在的店 |
| P1 | unknown 被说成确定 |
| P1 | verifier 只检查格式，不检查事实 |
| P1 | fallback 是空实现 |
| P2 | 回答过度模板化、口语性不足 |

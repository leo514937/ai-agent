# 03 工具执行层全面检验

> 适用范围：`tools/gateway.py`（`ToolCallGateway` / `BatchToolExecutor`）、`tools/registry.py`、`tools/executor.py`（`MockToolExecutor`、`JavaToolExecutor`）、`tools/java_client.py`、`tools/normalizer.py`、`domain/enums.py` 中的 `ToolResultStatus`、批量执行、熔断/超时/fallback。

> 说明：这里没有单独的 `ToolGateway` 类名，实际统一入口是 `ToolCallGateway`，批量并发执行由 `BatchToolExecutor` 承担。

## 0. 命名纠偏与功能判断

| 项目 | 结论 |
|---|---|
| 模块名写错 | `ToolGateway` 应改为 `ToolCallGateway`；`tools/enums.py` 不存在，`ToolResultStatus` 在 `domain/enums.py`；`JavaToolClient` 实际位于 `tools/java_client.py`；`BatchToolExecutor` 位于 `tools/gateway.py`。 |
| 功能等价存在 | 是。工具注册、统一执行、normalize、fallback、超时、异常、批量执行都能在现有工具层找到对应实现。 |
| 真缺口 / 细节不到位 | 暂未发现需要新增工具执行模块的硬缺口。当前问题主要是文档抽象名与真实代码命名不一致。 |

## 1. 检验目标

工具执行层是事实入口。它必须保证：

1. 工具只通过 registry + gateway 执行。
2. 所有工具返回统一 ToolResult shape。
3. ToolResultStatus 和业务 data.status 不混用。
4. mock/java/db/fallback 的 backend metadata 清楚。
5. 超时、异常、熔断、后端不可用、partial、empty 都有稳定语义。

## 2. 核心契约

所有 ToolResult 必须包含以下字段：

```text
success
result_status
data
error_code
error_message
source
degraded
call_id
shop_id
tool_name
tool_backend
backend_source
fallback_from
http_status
endpoint
```

`result_status` 只表示工具执行状态：

```text
ok / partial / empty / unknown / failed / error / circuit_open / backend_unavailable
```

如果工具是 `resolve_shop`，其业务解析状态必须在：

```text
data.status = RESOLVED / AMBIGUOUS / LOW_CONFIDENCE / NOT_FOUND
```

典型合法组合：

```json
{
  "result_status": "ok",
  "data": {
    "status": "NOT_FOUND"
  }
}
```

含义：工具执行成功，但店铺没有解析到。不能把它当作工具失败。

## 3. 代码走查清单

| 文件/模块 | 检查重点 |
|---|---|
| `tools/gateway.py` | 正常、异常、fallback、batch timeout/exception 是否统一 normalize |
| `tools/normalizer.py` | 所有 normalize 函数是否输出完整 shape |
| `tools/registry.py` | 非注册工具是否拒绝；schema 是否校验 |
| `tools/result_semantics.py` / `domain/enums.py` | ToolResultStatus 是否集中定义 |
| `tools/executor.py` 中的 `MockToolExecutor` | mock 返回是否模拟真实异常/empty/partial |
| `tools/executor.py` 中的 `JavaToolExecutor` | HTTP status、endpoint、fallback_from 是否保留 |
| `tools/java_client.py` 中的 `JavaToolClient` | 超时/错误是否转成统一 ToolResult |
| `tools/gateway.py` 中的 `BatchToolExecutor` | 并发路径是否不绕过 normalize |

## 4. AI Harness 检验重点

工具层本身不应该依赖 LLM，但 AI Agent 的 harness 必须能模拟工具不稳定。

### 4.1 必备 fake tool 类型

| Fake Tool | 目的 |
|---|---|
| AlwaysOkTool | 验证正常 path |
| EmptyTool | 验证 empty path |
| PartialTool | 验证 degraded/partial path |
| ErrorTool | 验证 error path |
| TimeoutTool | 验证 timeout + normalize |
| CircuitOpenTool | 验证熔断 path |
| BackendUnavailableTool | 验证后端不可用 |
| MalformedDataTool | 验证 data shape 异常 |
| JavaFallbackTool | 验证 java -> mock fallback metadata |

### 4.2 Harness 必须断言

- 每个结果都有完整 15 字段。
- exception 路径不丢 `call_id / tool_name / shop_id`。
- fallback 路径带 `fallback_from`。
- `source / tool_backend / backend_source` 语义不乱。
- 批量执行的 timeout/exception 不返回裸 dict。

## 5. Context 检验重点

工具执行层不负责上下文推理，但必须正确接收上下文补齐后的参数。

检查点：

1. shop_id 必须来自 resolver/planner，不能由工具层猜。
2. 用户位置如北京邮电大学海淀校区必须作为参数或配置传入，并可 trace。
3. 多轮上下文恢复后的 shop_id / candidate ids 不应在工具层被改写。
4. 工具层只执行，不承担业务决策。

## 6. 测试用例矩阵

| 场景 | 期望 |
|---|---|
| 正常工具调用 | 完整 ToolResult，result_status=ok |
| 工具返回空列表 | result_status=empty 或 ok+empty data，语义明确 |
| 工具抛异常 | result_status=error，字段完整 |
| Java 后端不可用 | backend_unavailable 或 fallback 到 mock，metadata 完整 |
| Java fallback mock | tool_backend=mock，fallback_from=java_api |
| 批量超时 | normalized timeout result |
| 批量异常 | normalized error result |
| 非注册工具 | validation_error，字段完整 |
| resolve_shop NOT_FOUND | result_status=ok，data.status=NOT_FOUND |
| partial | degraded=True，不默认 failed |

## 8. 通过标准

严格通过需要满足：

- 所有工具结果 shape 一致。
- 所有执行路径都经过 normalize。
- 工具执行状态与业务解析状态不混用。
- mock/java/fallback metadata 可追踪。
- batch executor 不返回裸 dict。
- 工具层不承担上下文决策。

## 9. 常见 P0/P1/P2

| 等级 | 问题 |
|---|---|
| P0 | 非注册工具可执行 |
| P0 | 工具异常返回裸异常或不完整 dict |
| P1 | `ok + NOT_FOUND` 被当作工具成功且解析成功 |
| P1 | `error/backend_unavailable` 未纳入失败判断 |
| P1 | fallback metadata 丢失 |
| P2 | `source/tool_backend/backend_source` 命名重复但语义不明 |

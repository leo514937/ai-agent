# 04 证据与决策层全面检验

> 适用范围：`answer/evidence_builder.py`、`answer/candidate_decision.py`、`answer/ranking_policy.py`、`answer/generator.py`、推荐/对比统一管线。

> 说明：这里没有单独的 `CandidateDecision` 服务类，推荐和对比的候选收集、评分、映射逻辑集中在 `answer/candidate_decision.py`、`answer/evidence_builder.py` 与 `answer/generator.py`。

## 0. 命名纠偏与功能判断

| 项目 | 结论 |
|---|---|
| 模块名写错 | `CandidateDecision` 不是独立服务类；候选收集/评分/映射实际在 `answer/candidate_decision.py`、`answer/evidence_builder.py` 和 `answer/generator.py`。`ranking_policy.py` 也不是 `answer/` 下的文件，而是规划侧的评分策略。 |
| 功能等价存在 | 是。证据收集、候选评估、推荐/对比合流、DecisionPlan 输出在现有代码里已实现。 |
| 真缺口 / 细节不到位 | `ranking_policy.py` 的权重目前是硬编码策略，不是配置化权重；如果文档要求“权重可配置”，这是当前真实缺口。 |

## 1. 检验目标

证据与决策层要把工具结果转换为可解释、可验证、可排序的 Evidence / DecisionPlan。

必须证明：

1. 推荐和对比使用统一 Candidate Decision 管线，而不是两套散落规则。
2. 决策只基于工具事实和结构化证据，不基于 LLM 编造。
3. 评分公式、权重、过滤条件可追踪。
4. 工具失败、partial、empty、NOT_FOUND 能被正确处理。
5. 最终输出给回答层的是 DecisionPlan，而不是未约束 tool raw data。

## 2. 代码走查清单

| 文件/模块 | 检查重点 |
|---|---|
| `answer/evidence_builder.py` | 是否统一处理 ToolResultStatus；是否保留 evidence source |
| `answer/candidate_decision.py` | 推荐/对比是否合流；失败状态判断是否完整 |
| `answer/ranking_policy.py` | 权重是否配置化；是否可解释 |
| `answer/candidate_decision.py` 中的 `CandidateEvidenceCollector` | 是否并发收集多店证据；失败是否降级 |
| `answer/candidate_decision.py` 中的 `CandidateEvaluator` | 是否只基于 EvidencePack 打分 |
| `domain/schemas.py` 中的 `DecisionPlan` | 是否包含理由、排序、证据引用、不可用字段 |

## 3. AI Harness 检验重点

本层 AI 风险是：LLM 可能在证据不足时“替系统做决策”。正确设计应该是：

```text
ToolResult → EvidencePack → CandidateDecision / Ranking → DecisionPlan → LLM verbalizer
```

而不是：

```text
ToolResult → LLM 自由总结并排序
```

### 3.1 必测 fake evidence 场景

| 场景 | 期望 |
|---|---|
| 所有候选都有完整证据 | 正常排序，理由可解释 |
| 某个候选 coupon 工具失败 | 不应编造有券；可降级 |
| 某个候选距离缺失 | 距离维度标 unknown，不应参与精确比较 |
| 某个候选 partial | 可以保留，但标 degraded |
| 某个候选 NOT_FOUND | 剔除或澄清，不进入最终推荐 |
| 多候选评分接近 | 输出不确定性/并列理由 |
| 权重变化 | 排序可解释变化 |

## 4. Context 检验重点

决策层要正确使用上下文，但不能污染当前决策。

检查点：

1. 上一轮推荐候选可以作为当前追问候选池。
2. 用户新增约束应重新筛选或重排，而不是只改话术。
3. 对比追问只比较上下文中明确目标。
4. 用户说“便宜一点”应修改 price 权重或过滤条件。
5. 用户说“环境更好”应切换到 environment facet。
6. 不应该把历史已淘汰候选继续拿来推荐。

## 5. 测试用例矩阵

| 场景 | 输入/条件 | 期望 |
|---|---|---|
| 推荐基础排序 | 评分、距离、券、营业状态完整 | 产生排序与理由 |
| 价格追问 | `便宜一点的呢` | 价格权重上升或过滤更便宜候选 |
| 场景追问 | `适合约会的` | scene suitability 参与排序 |
| 对比基础 | 2 家完整证据 | 输出 winner / tradeoff |
| 3-5 家对比 | 多候选 | 排序 + 维度理由 |
| >5 家对比 | 超限 | 上游应裁剪/澄清，本层不放大 |
| coupon 工具失败 | result_status=error | 不说有券，标未知/降级 |
| resolve NOT_FOUND | ok + data.status=NOT_FOUND | 不进入候选 |
| partial evidence | result_status=partial | degraded=True，理由谨慎 |

## 6. 推荐评分验收

检查 ranking policy 是否满足：

- 权重可配置。
- 每个分数维度可解释。
- 缺失字段不会被当成 0 分硬伤，除非业务定义如此。
- partial/degraded 证据有降权或标记。
- 场景偏好能影响权重。
- 推荐理由能追溯到具体 evidence。

建议评分输出结构：

```json
{
  "shop_id": "900001",
  "score": 0.86,
  "score_breakdown": {
    "rating": 0.25,
    "distance": 0.20,
    "coupon": 0.15,
    "scene_fit": 0.26
  },
  "evidence_refs": ["call_1", "call_2"],
  "degraded": false
}
```

## 8. 通过标准

严格通过需要满足：

- 推荐和对比共用 Candidate Decision 思路。
- 决策层不依赖 LLM 自由判断事实。
- 每个推荐/对比结论都有 EvidencePack 支持。
- 失败、partial、empty、NOT_FOUND 都有明确处理。
- 评分和 tradeoff 可解释、可测试。

## 9. 常见 P0/P1/P2

| 等级 | 问题 |
|---|---|
| P0 | 决策层让 LLM 编造排序或事实 |
| P1 | 工具失败后仍生成确定性推荐理由 |
| P1 | partial/empty/NOT_FOUND 混用 |
| P1 | 推荐和对比两套逻辑不一致 |
| P2 | score breakdown 不可观测 |

# 02 执行规划层全面检验

> 适用范围：`planning/execution_plan_builder.py`、`planning/task_router.py`、`planning/plan_validator.py`、`planning/llm_tool_planner.py`、`planning/tool_plan_adapter.py`、推荐/对比 execution plan、LangGraph 规划节点。

> 说明：这里检验的是“执行规划能力”而不是某个单独的 `ExecutionPlanner` 类。当前代码库把这层职责拆到了 `task_router`、`llm_tool_planner`、`tool_plan_adapter`、`execution_plan_builder`、`plan_validator` 和 `graph_builder`。

## 0. 命名纠偏与功能判断

| 项目 | 结论 |
|---|---|
| 模块名写错 | `ExecutionPlanner` 不是单独类；执行规划实际分散在 `planning/task_router.py`、`planning/llm_tool_planner.py`、`planning/tool_plan_adapter.py`、`planning/execution_plan_builder.py`、`planning/plan_validator.py`。 |
| 功能等价存在 | 是。语义帧接入、计划生成、计划适配、计划校验、对比裁剪、fallback/clarify 都有对应实现。 |
| 真缺口 / 细节不到位 | `plan_validator` 不是所有兜底逻辑的唯一承接点，空 query 和对比数量裁剪主要由 `tool_plan_adapter` / `llm_tool_planner` 前置处理；如果文档把这些都归给 validator，这是职责划分写得不准，不是功能缺失。 |

## 1. 检验目标

执行规划层负责把语义帧变成可执行计划。它是 LLM 与工具执行之间的安全边界。

必须证明：

1. LLM 只能产出候选计划，不能直接调用工具。
2. 最终执行计划由代码层 adapter / planner / plan_validator 生成。
3. 所有工具调用都必须经过 ToolCallGateway。
4. 推荐、对比、单店多 facet 的计划边界明确。
5. 参数补齐、数量裁剪、fallback、clarify 都可观测。

## 2. 核心架构验收

| 问题 | 期望 |
|---|---|
| LLM ToolPlanner 是否可直接执行工具？ | 不允许 |
| LLM plan 是否必须经过 adapter？ | 必须 |
| plan_validator 是否是执行前最终守门？ | 必须 |
| ENABLE_LLM_TOOL_PLANNER=false 是否完全走旧链路？ | 必须 |
| 推荐空 query 是否被拦截？ | 必须 |
| 对比超过 5 家是否被裁剪/澄清/reject？ | 必须 |
| 非法工具名是否可执行？ | 不允许 |
| 参数缺失是否能下沉到 gateway？ | 不应下沉 |

## 3. 代码走查清单

| 文件/模块 | 检查重点 |
|---|---|
| `planning/llm_tool_planner.py` | 是否只输出候选 ToolPlan；是否无 gateway/db/java 调用 |
| `planning/tool_plan_adapter.py` | 是否将候选 plan 转成既有执行计划；是否补齐/裁剪/回退 |
| `planning/plan_validator.py` | 是否拦截非法工具、非法参数、数量超限、空 query |
| `planning/execution_plan_builder.py` | 是否是代码层最终计划来源之一 |
| `planning/task_router.py` | 是否只路由任务，不承担工具执行 |
| `engine/graph_builder.py` | 接入点是否在 semantic_frame 之后、gateway 之前 |
| `domain/schemas.py` | ToolPlan / ToolIntent 是否枚举收敛、forbid extra |

## 4. AI Harness 检验重点

执行规划层需要重点防 LLM 越权。

### 4.1 必备 fake plan 场景

| Fake LLM Plan | 期望 |
|---|---|
| 合法单店 plan | 通过 adapter + validator |
| 合法推荐 plan | 通过 adapter + validator |
| 合法对比 plan，5 家以内 | 通过 adapter + validator |
| 非法工具名 | reject/fallback |
| 非法参数 | reject/fallback |
| 空 query 推荐 | adapter 恢复 query 或 fallback/clarify |
| 6 家以上对比 | 裁剪/clarify/reject，不得进入最终执行 |
| 非 JSON | parse_error + fallback |
| 声称“已执行工具” | prompt/schema/adapter 阻断 |
| LLM plan 与 semantic_frame 冲突 | 以代码层 validator 为准 |

### 4.2 必须记录的 trace 字段

```text
tool_plan_source: rule_based / llm_tool_planner / llm_tool_planner_fallback
tool_plan_validated: true / false
tool_plan_fallback_reason: string
plan_validation_status: ok / invalid
invalid_reason: string
selected_tools: list
trimmed_targets: list
clarify_required: true / false
```

## 5. Context 检验重点

执行规划层要检查上下文是否被正确用于“补齐”，而不是“幻觉”。

检查点：

1. 当前轮显式 shop_id 优先。
2. 推荐追问可以继承上一轮推荐候选和约束。
3. 对比追问可以继承 anchor shop，但不能默认拿第一家，除非上下文唯一。
4. pending clarification 的序号选择可以恢复候选。
5. 多候选单店查询默认澄清，不应直接选第一家。
6. recommendation 与 comparison 的候选数量上限统一配置。

## 6. 测试用例矩阵

| 场景 | 期望 |
|---|---|
| `ENABLE_LLM_TOOL_PLANNER=false` | 不调用 LLM ToolPlanner |
| 合法单店计划 | 产生 get_shop_detail/get_coupon_list 等计划 |
| 合法推荐计划 | 产生 search/get cards/review/deal 等只读计划 |
| 合法对比计划 | 产生多店详情/距离/评价证据计划 |
| LLM 输出交易工具 | reject |
| LLM 输出空 query | 不生成 `search_shops(query="")` |
| LLM 输出 6 家对比 | 最终计划 <=5 或 clarify |
| 缺 shop_id 的单店工具 | validator reject 或 resolver 补齐 |
| 已解析 shop_id 与 LLM mention 冲突 | 以 resolver / validator 为准 |

## 8. 通过标准

严格通过需要满足：

- LLM ToolPlanner 不能绕过 adapter / validator / gateway。
- 关闭开关后旧链路完全不受影响。
- 空 query、数量超限、非法工具、非法参数都有安全处理。
- Trace 能区分 plan 来源、是否校验、fallback 原因。
- 推荐/对比/单店多 facet 的计划边界清楚。

## 9. 常见 P0/P1/P2

| 等级 | 问题 |
|---|---|
| P0 | LLM plan 直接执行工具 |
| P0 | 非注册工具进入 gateway |
| P1 | 对比数量上限可绕过 |
| P1 | 推荐空 query 下沉到 validator/gateway |
| P1 | LLM plan 与语义冲突时未校验 |
| P2 | fallback reason 粒度不够 |
